들어가며#

이전 글에서 strategy_v3 구현을 마무리하며 매수 전면 중단 Critical 버그를 발견·수정했다. 이어서 실제 운영을 위해 v3를 웹 대시보드에 통합하는 작업으로 넘어갔는데, 여기서 훨씬 더 근본적인 문제 하나를 발견하게 된다.

결론부터 말하면, v3는 웹 대시보드에서 전략 버전 선택 자체가 불가능했다. 원인을 조사하다가 v3 활성화 시 트레이딩 파라미터 프리셋이 전혀 적용되지 않고 있었다는 것을 확인해 프리셋 파일을 신설했다. 이어서 전략확인 페이지에 v3 탭을 추가하던 중, strategy_sell.yaml의 모든 설정값이 이중 중첩 버그 때문에 실제로는 전혀 반영되지 않고 있었다는 훨씬 심각한 문제도 발견했다.

v3가 웹 대시보드에서 선택 안 되던 문제#

사용자 확인 결과 v3는 웹 대시보드에서 전략 버전 선택이 아예 불가능했다. _list_strategy_versions()가 strategy_v{n}/settings/presets/ 존재 여부로 버전을 판별하는데, v3는 프리셋 디렉토리가 없어 선택지에서 빠져 있었던 것이다.

조사 중 이 누락이 단순 UI 문제를 넘어 실제 설정 로딩 공백이었음을 확인했다. utils/config_loader.py의 load_config()는 버전 무관하게 항상 strategy_{version}/settings/presets/{preset}.yaml을 읽는데, v3 활성화 시 프리셋 파일이 없으니 “프리셋 파일 없음” 경고만 남기고 트레이딩 파라미터(손절/익절/보유기간 등) 프리셋 오버라이드가 전혀 적용되지 않는 상태였다.

수정:

  • strategy_v3/settings/presets/{neutral,conservative,aggressive}.yaml 신규 추가 — v2 프리셋과 동일한 trading: 구조 그대로 복사(v3도 동일한 shared 모듈들을 사용하므로 손절/익절/보유수/스프레드 등 knob은 v2와 동일)
  • web/routers/config_router.py에 v3 설명(_STRATEGY_VERSION_DESCRIPTIONS) 추가 — 웹 대시보드 “전략 버전” 드롭다운에 v3가 정상적으로 나타나게 됨
  • web/templates/settings.html에 v3 전용 “2차 스크리닝 프로파일(그룹 정규화 점수)” 카드 신규 추가 — 사용자 결정에 따라 조회 전용(프로파일 전환으로 다른 프로파일 보기는 가능, 가중치/파라미터 편집 UI는 없음 — YAML 직접 편집만 허용). 그룹(G1~G5)별로 묶어 그룹 비중 + 개별 조건 가중치 막대 표시, 목표가 방식(즉시/할인/기술적)도 함께 표시

테스트는 tests/test_config_router_v3.py(_list_strategy_versions/_list_presets/_load_preset_summary 실제 파일 기준 검증 3건), tests/test_config_loader.py(load_config()가 v3 프리셋을 실제로 병합하는지 격리된 tmp_path 검증 1건), tests/test_web_pages.py::TestSettingsPage(v3 활성 시 설정 페이지가 실제로 렌더링되는지, 프리셋 3종이 반영되는지, v1 활성 시에도 회귀 없이 렌더링되는지 3건)를 추가해 전체 848건 통과를 확인했다. uvicorn 기동 후 /settings 실제 요청으로 500 없이 정상 리다이렉트(로그인 게이트)되는지도 직접 확인했다.

조사 중 발견했지만 이번 요청과 무관해 범위 밖으로 남긴 항목도 있다 — strategy_v3/settings/strategy_sell.yaml에 프로파일별 hold_days 값이 아예 정의돼 있지 않아(min_hold_days/profit_target_pct/score_exit_ratio만 있음) “보유기간 상한 초과 시 강제청산” 타임스탑 로직이 모든 v3 프로파일에서 사실상 비활성 상태로 보였다.

보유기간 강제청산 활성화#

바로 위에서 범위 밖으로 남겨뒀던 항목을 이어서 수정했다. strategy_v3/trading/strategy_sell.py의 우선순위 ②(기회비용 타임 스탑)·⑥(보유기간 상한 초과)가 strategy_cfg.get("hold_days")를 읽는데, strategy_v3/settings/strategy_sell.yaml에 5개 프로파일 모두 hold_days 키가 없어서(min_hold_days와 이름이 비슷해 혼동되기 쉽다) 두 우선순위가 사실상 항상 비활성 상태였다.

수정: strategy_v3/settings/strategy_sell.yaml에 5개 프로파일(trend_following/momentum/reversal/fear_driven/balanced) 전부 hold_days를 추가했다 — v2의 값(20/10/15/10/15)을 그대로 채택했다. 매도 판단 로직 자체는 v3 전용이지만 보유기간 상한은 전략 성격이 v2와 동일해 재사용할 수 있었다.

tests/test_v3_strategy_sell.py에 4건을 추가해, 실제 YAML 파일 기준으로 time_stop/opportunity_cost_stop 각각 발동/미발동 케이스를 검증했다. 수정 전 YAML로 되돌려 KeyError로 RED를 확인한 뒤 수정 후 GREEN을 확인했다. pytest tests/ 852건 전체 통과를 확인했다.

config_loader 이중 중첩 버그#

“전략확인”(/strategy) 페이지에 v1/v2와 동일한 방식으로 v3 매수/매도 흐름 Mermaid 다이어그램 탭을 추가하는 작업 중, 훨씬 심각한 버그를 발견했다.

  • web/strategy_flow.py: build_v3_buy_flow()/build_v3_sell_flow() 신규 — v2 공유 4그룹(A/B/C/D) 1차 스크리닝, 5개 프로파일 min_score/목표가 모드, v2 공유 dynamic_stop/fear_filter, v3 전용 hold_days/opportunity_cost_stop을 실제 YAML에서 그때그때 읽어 Mermaid 그래프 생성
  • web/routers/pages.py/web/templates/strategy.html: v3 탭 추가
  • strategy_v3/specs/strategy_v3_flow.html(정적 설계 문서) 갱신: 실제 값과 달랐던 dynamic_stop 수치 정정(momentum/reversal/fear_driven 손절폭, ATR배수), “구현 체크리스트” 탭에 실제 구현 완료 현황 + 최종 리뷰에서 발견된 Critical/Important 버그 요약 + 웹 대시보드 통합 내역 추가

작업 중 발견한 더 심각한 버그: utils/config_loader.py::_load_screening_configs_v3()가 strategy_v3/settings/strategy_sell.yaml을 로드할 때 이 파일 자체의 최상위 strategy_sell: 키를 언랩하지 않아 config["strategy_sell"]["strategy_sell"]로 이중 중첩되던 버그를 발견했다.

이 때문에 바로 앞서 고친 hold_days 값을 포함해 min_hold_days, score_exit_ratio, profit_target_pct 등 이 파일의 모든 설정값이 실제 봇에는 전혀 반영되지 않고 있었다. 코드의 하드코딩 기본값과 우연히 같은 값이라 겉으로 드러나지 않았고, 기본값이 없는 hold_days만 증상이 나타났던 것이다 — 방금 고친 버그가 사실은 이 이중 중첩 버그의 증상 중 하나였던 셈이다.

수정: v3_cfg.get(key, v3_cfg)로 양쪽 파일(하나는 wrapper 있음, 하나는 없음) 모두 안전하게 처리하도록 했다.

tests/test_config_loader.py에 회귀 테스트 1건(이중 중첩 KeyError로 RED → 수정 후 GREEN), tests/test_strategy_flow.py에 v3 빌더 테스트 4건, tests/test_web_pages.py::test_strategy_page_renders_all_flows 갱신(6개 다이어그램 확인)을 추가했다. pytest tests/ 857건 전체 통과를 확인했다.

작은 UI 문제(드롭다운에 v3가 안 보인다)를 따라가다 보니, 실제로는 훨씬 큰 범위의 설정 로딩 버그로 이어졌다. “증상을 고쳤는데 원인은 따로 있었다"는 패턴이 이번 v3 개발 과정에서 계속 반복되고 있다. 다음 글에서는 7월 2일, v3의 핵심 기능인 매시간 재선정을 구현하고 메인 전략을 v1에서 v3로 전환하는 과정을 다룬다.
