자동매매 Bot 전환 및 개발 · KIS (3) — superpowers 플러그인을 통째로 도입하지 않은 이유

이미 자체 작업 게이트가 있는 저장소에 범용 개발 워크플로 플러그인(superpowers)을 그대로 얹으면 어떻게 될까. 전면 도입 대신 쓸 만한 관행 세 가지만 이식하고, 읽기 전용 리뷰 서브에이전트 두 개를 만든 과정을 정리한다.

들어가며#

기존 봇 저장소(kis-auto-trading-bot)에서는 Claude Code의 superpowers 플러그인(브레인스토밍, 계획 작성, 서브에이전트 개발 같은 범용 워크플로)을 잘 쓰고 있었다. 그래서 새 저장소(kis-auto-trading)에도 그대로 도입하는 게 자연스러워 보였다. 그런데 도입 전에 “충돌하지 않는가"를 먼저 검토했고, 결론은 전면 도입은 하지 않는다였다.

1. 전면 도입을 권하지 않은 이유#

새 저장소에는 이미 자체 작업 게이트가 있다. 개발요청서를 먼저 쓰고, 정해진 세 절차(시작·종료·문서 최신화)를 따르는 방식이다. 여기에 범용 워크플로를 겹치면 두 가지 문제가 생긴다.

  • 세션 시작 게이트가 두 개가 된다. 어느 쪽이 먼저 실행되는지, 충돌하면 무엇이 우선인지가 모호해진다.
  • 저장소 고유 규칙이 밀려날 수 있다. 전략 폴더 범위 제한, 기존 코드와의 회귀 대조, 프리셋 3종 같은 이 프로젝트만의 규칙은 범용 워크플로가 알지 못한다. 범용 절차가 앞서면 이런 규칙이 조용히 빠질 위험이 있다.

그래서 결정은 이랬다. 두 게이트가 충돌하면 이 저장소의 CLAUDE.md와 전용 스킬이 항상 우선한다. 대신 쓸 만한 관행만 골라 직접 이식했다.

2. 이식한 관행 세 가지#

  1. 우선순위 명시: CLAUDE.md 최상단과 전용 스킬 맨 앞에 “외부 플러그인보다 이 저장소 규칙이 우선"이라는 문장을 넣었다.
  2. TDD RED-GREEN 고정: 전략 개발 가이드의 검증 절차를 “테스트를 먼저 쓰고 실패를 확인한 뒤 구현"으로 못박았다. 기존의 판단 회귀(fixture) 검증과 결합했다.
  3. 근본원인 디버깅 문서: 재현 → 가설 → 검증 → 수정과 회귀 테스트의 4단계, 그리고 이 저장소 특화 체크포인트(코어 버그인지 전략 버그인지 구분, 이식한 코드는 기존 저장소와 대조)를 문서로 만들었다.

서브에이전트 위임은 범위를 좁혀 허용했다. 기계적이고 반복적인 이식(같은 모양의 조건 모듈 20여 개를 옮기는 작업)에 한해 두 단계 리뷰(스펙 준수 → 코드 품질)를 쓰게 했고, 프롬프트에 범위 제한(전략 폴더 밖 금지, 코어는 읽기 전용, 재작성 금지)을 반드시 적고 사람이 최종 diff를 확인하도록 했다.

3. 읽기 전용 리뷰 서브에이전트 2종#

추천 플러그인을 조사한 뒤 서브에이전트를 두 개 만들었다.

에이전트 역할 도구
스펙 리뷰어 이식 1단계: 목적지 경로, 로직 보존, 범위 위반만 검토 Read, Grep, Glob
품질 리뷰어 이식 2단계: 타입 힌트, 예외 처리, 로깅 규약, 하드코딩, 캔들 규약 Read, Grep, Glob

핵심은 도구를 읽기 전용으로 제한한 것이다. 리뷰어가 “고치는 쪽"으로 넘어갈 경로 자체가 없으니, 실수로 코드를 바꾸는 사고가 구조적으로 막힌다.

조사한 외부 플러그인 중에서는 타입 힌트를 실시간 검사하는 LSP 플러그인(프로젝트의 “타입 힌트 필수” 규칙을 자동으로 강제할 수단)과, 변경마다 보안 취약점을 점검하는 플러그인(토큰·주문을 다루는 프로젝트에 특히 유효)이 눈에 띄었다. 코드 리뷰·디버그 쪽은 이미 직접 만든 것과 겹쳐서 추천하지 않았다.

알아 둘 점#

  • 서브에이전트가 저장소의 CLAUDE.md와 스킬을 얼마나 실제로 상속하는지는 아직 검증하지 못했다. 처음 실전에 쓸 때 결과 diff로 반드시 확인해야 한다.
  • 스킬 폴더는 일부 편집 도구가 보호 경로로 막아서, 셸을 통해 수정해야 했다. 다음 세션에서도 같은 증상이 나올 수 있다.

정리#

교훈: 좋은 도구라고 통째로 들여오지 않는다. 이미 성숙한 규칙이 있는 곳에서는, 도구가 규칙을 덮어쓰지 못하도록 우선순위를 문서로 못박고 쓸모 있는 관행만 옮기는 편이 안전하다. 다음 글에서는 실제 코드 이식에 앞서 기존 저장소의 운영 교훈을 새 설계에 반영한 과정을 다룬다.
