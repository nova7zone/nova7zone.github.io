들어가며#

이전 글에서 market_context_log와 candidate_outcome을 완료했다. 오늘은 Phase 2의 마지막 테이블을 연결하고, docs 전체를 다시 한번 점검한 뒤 릴리즈까지 마무리하는 날이다.

결론부터 말하면, holdings_snapshot을 journal_writer.py에 연결해 next-tasks.md에 남아있던 Phase 2 마지막 항목을 끝내고 T2-1~T2-5 전체를 완료했다. 이어서 docs/ 폴더와 CLAUDE.md/README.md를 코드와 다시 대조해 stale 항목 여러 건을 정정하고, orphan 상태로 방치돼 있던 문서 하나를 archive로 옮겼다. 마지막으로 v0.7.1을 정식 릴리즈했다.

next-tasks.md 오래된 항목 정정#

사용자가 “남은 작업"을 물어 next-tasks.md를 훑던 중, 6월 29일에 요청된 “투자원금 입출금 이력(ledger) + 원금 직접수정 잠금” 항목이 “다음 세션 시작” 상태로 미완료 표시돼 있었다. 그런데 실제 코드는 이미 전부 구현·배포돼 있었다(어느 세션에서 구현됐는지는 work-log.md에 별도 기록이 남아있지 않은 문서 갱신 누락 케이스였다).

db/schema.py의 capital_ledger 테이블, db/repository.py::add_capital_ledger_entry()/get_capital_ledger()/get_capital_balance(), web/routers/config_router.py::_resolve_capital_flow()(봉/추가계좌 공통, 최초등록 중복·미등록 입출금 모두 400 거부), web/templates/settings.html의 최초등록/입출금 폼 전환까지 코드로 직접 확인했다. next-tasks.md의 해당 섹션을 1~3번 완료로 갱신하고, 실제로는 미구현 상태로 남아있는 4번(계좌별 일별 평가액 history — 그래프용)만 남은 항목으로 명확히 분리 표시했다. 코드 변경은 없이 문서만 정정했다.

holdings_snapshot 연결 — Phase 2 완료#

next-tasks.md에 남아있던 Phase 2 마지막 항목이었다. --update-journal(15:35 cron)이 이미 종목별로 계산 중인 code/name/qty/avg_price/current_price/unrealized_pnl/sector 값을 재사용해 holdings_snapshot 테이블에 적재하도록 연결했다(추가 API 호출 없음). insert_holdings_snapshot()은 같은 (mode, snapshot_date) 재호출 시 기존 행을 삭제 후 재삽입하도록 했다 — 스냅샷 성격상(로그가 아니라 “그날의 현재 상태”) 재실행 시 중복 적재를 막기 위함이다(수정 전까지 호출부가 전혀 없어 회귀 위험은 없었다).

tests/test_db.py에 재실행 시 교체 확인 회귀 테스트 2건, tests/test_journal_writer.py를 신규 추가했다(DB 연결 시 정상 삽입/값 일치, DB 미설정 시 스킵, 보유 종목 없을 때 빈 스냅샷, DB 실패해도 Excel 저장은 유지 4건). pytest tests/ 전체 통과를 확인했다.

최종 whole-branch 리뷰에서 발견한 Important 1건 (커밋 474c8bb로 해결): 보유 종목이 없는 날 insert_holdings_snapshot(..., [])을 호출하면 오늘 날짜 행은 정확히 0개가 되는데, get_latest_holdings_snapshot()은 MAX(snapshot_date)로 “행이 존재하는 가장 최근 날짜"를 찾는 구조라서 오늘이 0개면 어제(혹은 그 이전) 데이터로 폴백한다 — 설계 문서의 “전날 스냅샷이 남아 있는 것처럼 보이는 걸 방지” 표현이 부정확했던 것이다. 현재 이 함수를 실제로 호출하는 웹 대시보드 소비자가 없어서(web/routers/api.py가 import만 하고 미사용) 당장 영향받는 사용자는 없었다 — 사용자 결정으로 동작 변경 대신 설계 문서를 정확히 수정(알려진 한계로 명시, 향후 소비자 연결 시 필요한 대응 방안 2가지 기록)하고, 테스트도 완전히 빈 DB가 아니라 전일 데이터가 있는 실제 시나리오로 재작성했다.

이로써 Phase 2(T2-1~T2-5) 전체가 완료됐다. Phase 3(수익률 로직 보완)으로 진행할 수 있는 상태가 됐다.

docs/ 전체 + CLAUDE.md/README.md staleness 점검#

사용자 요청: “docs/ 폴더의 문서와 claude.md, readme.md를 최신화 업데이트 해줘.” docs-sync skill의 재작성 절차는 이미 6월 23일 전후로 완료된 상태(docs/README.md 21개 문서 전부 [x])라, 전면 재작성이 아니라 staleness 점검·수정으로 범위를 잡았다. 5개 카테고리로 나눠 Explore 성격의 general-purpose subagent 5개를 병렬 디스패치해, 각각 코드/설정/work-log.md와 직접 대조해 stale 내용을 찾아 보고하도록 했고, 발견된 항목은 컨트롤러가 직접 수정했다.

발견·수정한 실제 코드 버그도 있었다(문서 밖 결함): journal/journal_writer.py의 docstring이 --update-journal 실행 시각을 “15:35"로 기록하고 있었지만 실제 cron은 6월 23일에 16:15로 변경된 뒤 docstring만 갱신이 누락돼 있었다. docs/APP_SETTINGS.md가 max_calls_per_run 초과 시 “경고 로그만 기록(차단 아님)“이라고 설명했는데, 실제 api/kis_api.py는 경고 로그 후 None을 반환하는 하드 스톱이었다 — 정정했다. db/schema.py docstring의 테이블 목록에 capital_ledger가 누락돼 있던 것도 발견했다.

문서 내용 갱신도 여러 건 진행했다. docs/WORKFLOW.md의 데이터 흐름 다이어그램에 Phase 2 신규 테이블 4종과 capital_ledger 노드를 추가하고, journal_writer.py → holdings_snapshot 엣지도 추가했다. docs/TESTING_GUIDE.md의 테스트 파일 표가 50개만 나열하고 있어 실제 62개 전체와 diff해 누락된 11개를 추가하고, 최종 diff로 62/62 전부 문서화됨을 확인했다. docs/STRATEGY_V2_trading_flow.md/STRATEGY_V3_trading_flow.md에는 v2/v3 공존 시 매도 로직 비대칭(v2는 managed_by='v3' 종목 매도 자체를 skip, v3는 매도는 하되 managed_by='v2' 종목만 로그 기록을 skip)을 명시했다.

orphan 문서 archive: docs/STRATEGY_V2_full_detail.md(6월 25일 작성, 677줄 코드 레벨 v2 전수 점검 — docs/README.md 인덱스에 없던 미등록 문서)를 재검증한 결과, config/weights/threshold 수치는 여전히 정확했지만 매도 흐름 서술이 이후 3개 변경사항을 전혀 반영하지 못해 docs/archive/로 이동하고, 문서 최상단에 archive 사유와 최신 문서 링크를 추가했다.

문서 개수 변경도 반영했다 — orphan archive로 docs/(development 제외) 문서가 22개→21개로 줄어 README.md/CLAUDE.md의 개수 표기를 정정하고, DB 테이블 개수(9→14개)·테스트 파일 개수(42→62개) 표기도 정정했다.

pytest tests/ 전체 1035개 통과를 확인했다(문서·주석만 변경, 코드 로직 변경 없음).

v0.7.1 릴리즈#

사용자 요청: “릴리즈업 해줘.” 버전 번호를 확인했다 — v0.8.0 vs v0.7.1 중, Phase 0/1 리스크 버그 수정 + Phase 2 데이터 수집 계층 완료를 v0.7.0(v3 전환)의 후속 안정화·계측 성격으로 판단해 v0.7.1을 사용자가 확정했다.

v0.7.0 이후 merge된 PR #85~#89(v3 운영 로그 Critical 버그 3건 수정 → VKOSPI 긴급 수정+리스크 버그 5건(Phase 0/1) → 데이터 수집 테이블 3종(T2-1~T2-3) → candidate_outcome(T2-4) → holdings_snapshot 연결(T2-5, Phase 2 완료) → docs staleness 점검(#89)) 기준으로 release-notes-draft-v0.7.1.md를 작성했다.

git tag -a v0.7.1(origin/master HEAD 0e5c987) → git push origin v0.7.1 → gh release create로 정식 GitHub Release를 발행했다. “github에 태그 생성해줘"라는 후속 요청으로 정식 발행까지 이어졌다. GitHub 정식 릴리즈 노트 본문의 “# v0.7.1 (draft)” 헤더에서 “(draft)“를 제거해 발행했다(관례대로 로컬 draft 파일명·본문은 “draft” 표기 유지). 코드 변경은 없었고(릴리즈 발행 전용), pytest tests/ 영향도 없었다.
