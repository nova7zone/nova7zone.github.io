자동매매 V2 개발 · Upbit (1) — 코드 없이 문서부터 쓰고, 데이터를 직접 열어 보고, 임시 서버에 올리다

크론 운영의 한계를 겪고 데몬 기반 V2를 새로 시작한 첫 주. 코드 한 줄 쓰기 전에 요구사항과 결정 16건을 문서로 확정하고, 공개 과거 시세 데이터를 실물로 검증해 '생존 편향은 해결할 수 없다'는 결론을 내린 뒤, 임시 서버에 첫 기동까지 마친 과정을 정리한다.

들어가며#

V1(크론 기반 Bot)은 운영하면서 한계가 분명해졌다. 15분 주기 점검은 청산 반응이 느렸고, 전략 실험이 쌓일수록 운영 코드가 실험 코드와 섞였다. V2는 신규 구축으로 결정했다. 상시 데몬, 4시간봉 신호, 1~10초 간격 감시, 추가 매수 금지, 24시간 운영, 단일 진입점, 웹은 설정만 쓰고 주문은 하지 않는다는 요구사항 10건이 출발점이다.

이 글은 7월 28일 착수부터 8월 4일 첫 서버 기동까지의 기록이다.

1. 첫 주는 문서만 썼다#

7월 28일에는 코드가 없었다. 개발 문서 세트(착수 요청서, 아키텍처, 규약, DB 스키마, 로드맵, V1 교훈, 결정 기록 등 10여 종)를 먼저 썼다. 이유는 V1에서 배웠기 때문이다. 같은 실패를 반복한 곳은 코드가 아니라 합의되지 않은 가정이었다.

몇 가지 설계 결정이 이때 정해졌다.

  • 청산 값 전달 계약. 전략이 청산 조건을 자유 형식 딕셔너리로 넘기는 방식을 버리고 타입이 있는 청산 계획 객체로 올렸다. 절대 가격 원칙, 코어의 검증 규칙, 우선순위 9단계를 문서화했다. 불변식도 하나 정했다. 손절선은 내려가지 않는다(저장 계층이 거부한다).
  • 모든 단계에서 같은 엔진. 연구의 1·2단계(스모크, 엄격 검증)와 3단계(운영 코드 재현)가 서로 다른 구현이면 단계 사이의 괴리가 “구현 차이"인지 “전략 문제"인지 분간할 수 없다. 그래서 전 단계를 같은 백테스트 엔진으로 통일하고 옵션 프리셋만 다르게 했다. 검증 에이전트는 신호 함수만 구현한다.
  • 회차 누적 다중 검정. 연구 시도가 쌓일수록 우연히 좋아 보이는 후보가 나올 확률이 커진다. 누적 시도 횟수를 관리하고 봉인 구간의 문턱을 이에 연동해 올린다. 수정 루프도 시도로 센다.
  • 분류 체계(taxonomy) 8개 클래스. 후보마다 클래스를 태깅하고, 같은 클래스가 연속으로 기각되면 그 클래스를 봉인한다.
  • 운영 문서 세트. 개발 문서와 별도로 운영 문서 5분류 22종의 목록과 공통 양식을 정했다.

착수 전 최종 점검에서 결정 16건을 확정해 DECISIONS.md에 번호를 붙여 쌓기 시작했다.

2. 공개 시세 데이터를 실물로 검증하다#

백테스트는 데이터가 전부다. 거래소가 제공하는 과거 시세 다운로드를 쓰기로 했는데, 문서를 믿지 않고 사용자가 파일을 직접 받아 열어 보았다.

  • 체크섬 파일은 해시 64자만 담고 파일명이 없다. 검증 통과.
  • 출시 공지는 “2022-05-01부터"라고 했지만 2017년 데이터가 실제로 있었다. 캔들은 거의 전 구간을 덮는다.
  • 봉 경계가 UTC 00·04·08·12·16·20시이고, 이를 한국 시간으로 바꾸면 우리가 쓰는 앵커 시각(01·05·09·13·17·21시)과 정확히 일치했다.
  • 컬럼 순서가 대금이 먼저고 수량이 나중이다. 이름이 헷갈리기 쉬운 지점이라 매핑에 명시했다.
  • 일 단위 파일은 하루 6봉짜리라 종목당 3,200개, 270종목이면 86만 개가 된다. 월 단위로 받으면 종목당 약 105개다. 월 단위로 확정했다.
  • 상장 초기의 저유동성 구간이 필터 없이 들어온다. 유동성 티어에서 걸러야 한다.

가장 큰 기대가 무산됐다#

상장폐지된 종목의 데이터는 제공되지 않는다. 이 데이터가 있으면 백테스트의 생존 편향(살아남은 종목만 보는 오류)을 줄일 수 있다고 기대했는데 무산됐다. 그래서 결정을 바꿨다.

생존 편향은 해결하지 않고 막고, 줍고, 밝힌다.

  • 막는다: 폐지 감시자를 만든다. 사이클마다 마스터 목록을 대조해서 사라진 종목을 기록하고 즉시 캔들 스냅샷을 남긴다. 스냅샷 실패는 CRITICAL이다. 되돌릴 수 없는 손실이기 때문이다. 지금 넣지 않으면 1년 뒤 같은 문제를 다시 겪는다.
  • 줍는다: V1의 2018~2020년 데이터에서 현재 미상장 종목을 폐지로 살린다.
  • 밝힌다: 백테스트 리포트에 생존 편향 배너를 강제한다. “폐지 종목 N개 미포함, 편향 방향은 낙관.”

없는 것을 있는 척하지 않는 것이 이 결정의 핵심이다.

3. 단계별로 쌓은 코어#

로드맵은 단계마다 게이트(통과 조건)가 있다. 8월 34일에 단계 04를 연속으로 마쳤다.

단계 내용
0 저장소 골격, 검증 게이트(린트, 타입, 의존성 규칙, 테스트), CI, 스킬 3종
1 실측, 설정/API/데이터 계층, 백필 스크립트, 오케스트레이터
2 지표 8종, 거시 국면, 시장 미시 국면 5축, 공포 게이트, 거래 적격성, 폐지 감시자, 종료 게이트
3 리스크 순수 함수 계층, 식별자, DB 연동, 실행기, 대조(reconcile), 포지션 저장
4 데몬, 스케줄러, 배포 스크립트, 운영 문서

실측으로만 드러난 문제도 있었다.

  • 백필이 403에서 죽었다. 없는 달이 404가 아니라 403으로 응답하는데 첫 백필이 일시 오류로 보고 3회 재시도하다가 전체가 중단되었다. 403·404는 즉시 건너뛰고, 재시도는 429·5xx·네트워크 예외에만 걸도록 분리했다. 테스트 5건을 추가했다. 상태 파일이 저장되기 전에 죽은 것도 확인해서 부분 상태 정리 없이 처음부터 재실행하면 되었다.
  • 도구 쪽 사소한 함정도 있었다. 셸의 출력 리다이렉션이 표준 오류를 오류 객체로 감싸 읽기 어려워서, 로그를 파일 핸들러로 직접 쓰도록 바꿨다.
  • 국면 분류기의 품질을 진단하는 지표 6종을 별도 스크립트로 만들어 종료 게이트에 넣었다.

4. 임시 서버 배포#

8월 4일에는 배포 스크립트를 실제 서버에서 돌려 보았다. 명시적으로 임시(트라이얼) 배포다. 등록된 실전략이 없어서 주문 리스크는 없고, “설치와 기동이 죽지 않는가"만 본다.

  • 실행 권한 비트 버그. 로컬(Windows)에서는 core.filemode=false라 chmod +x가 저장소에 기록되지 않는다. 배포 스크립트 7개가 비실행 모드로 커밋되어 서버에서 Permission denied가 났다. git update-index --chmod=+x로 모드를 명시 기록했다. V1에서도 같은 문제를 겪었는데, 이번에는 결정 문서에 원인과 해법을 남겼다.
  • 인증 문제. 서버에서 저장소를 가져올 때 기존 접근 토큰이 권한 오류로 거부되어 새로 발급해 해결했다. 이 과정에서 비밀값은 항상 서버 터미널에 직접 입력하고 채팅에는 붙여넣지 않는다는 원칙을 세워 계속 적용하고 있다.
  • 설치 스크립트가 가상환경, 의존성, DB 스키마 초기화, 서비스 유닛 배치까지 정상 완료했다. 웹 서비스는 아직 앱이 없어서 활성화를 보류했다.
  • 시장 DB 반입. 운영 상태 DB와 시장 데이터 DB를 구분해, 시장 데이터 파일 하나만 올리고 운영 DB는 절대 로컬 사본으로 덮어쓰지 않는다. 업로드 후 무결성 검사 통과.
  • 데몬 기동 후 하트비트 테이블에서 프로세스 ID 일치, 틱 카운트 증가, 킬스위치 꺼짐을 확인했다. 거래소 계좌 조회도 정상 응답했다.
  • 백업 스크립트가 두 DB의 사본을 만드는 것까지 확인했다.

남은 일도 정직하게 적었다. V1 크론을 주석 처리하고 V1 데몬을 정지했는지는 대화에서 명시적으로 재확인되지 않았다. 72시간 연속 구동이라는 로드맵 게이트는 아직 미완이다. 이번은 1차 확인일 뿐이다.

정리#

영역 결정
문서 코드 전에 요구사항·결정 16건을 문서화
청산 타입 있는 청산 계획, 손절선 하향 금지
연구 전 단계 같은 엔진, 누적 시도 관리, 클래스 봉인
데이터 월 단위 확정, 생존 편향은 막고 밝힌다
배포 임시 서버로 설치·기동만 확인, 실전략 없음

배운 점: 외부 데이터 문서는 실물을 열어 보기 전까지 가설이다. 공지의 기간 서술이 틀렸고(좋은 쪽으로), 폐지 종목 데이터가 없다는 사실은(나쁜 쪽으로) 실물에서만 드러났다. 그리고 해결할 수 없는 문제는 해결한 척하지 말고 한계를 리포트에 박아 두는 편이 이후의 모든 결과를 정직하게 만든다.
