AI를 이용한 자동매매 프로그램 작성 (38) — CLAUDE.md 분리, 문서 재구성, v0.6.3 릴리즈

매 세션 전체 로드되는 CLAUDE.md 520줄을 181줄로 줄이며 개발 문서를 docs/development 폴더로 재구성하고, PR #63~#74 구간 docs 재점검·v0.6.3 릴리즈, 그리고 스크리닝 로그가 v2 전환 이후 한 번도 기록되지 않았던 원인을 조사한 하루를 정리한다.

들어가며#

이전 글에서 Alpine.js 반응성 버그와 캐시 날짜 버그를 고쳤다. 6월 29일 후반은 문서 구조 자체를 손보는 작업으로 이어졌다.

결론부터 말하면, 매 세션 전체 로드되는 CLAUDE.md 520줄이 부담이 커서 프로젝트 구조/아키텍처 섹션을 별도 파일로 분리해 181줄로 줄였다. 개발 문서 전체를 docs/development/ 아래로 재배치하고, PR #63~#74 구간의 docs stale 점검과 v0.6.3 릴리즈까지 진행했다. 마지막으로 스크리닝 로그가 v2 전환 이후 한 번도 기록되지 않은 이유도 조사했다.

CLAUDE.md 분리 + 문서 재구성#

CLAUDE.md(520줄)가 매 세션 전체 로드되는 부담을 줄이기 위해 구조를 나눴다.

  • build-docs/, docs/superpowers/ → docs/development/build-docs/, docs/development/superpowers/
  • AI_PROJECT_PROMPT.md → docs/development/AI_PROJECT_PROMPT.md
  • CLAUDE.md의 프로젝트 구조/아키텍처/Claude Code harness/알려진 주의사항 섹션을 docs/development/{PROJECT_STRUCTURE,ARCHITECTURE,HARNESS,KNOWN_ISSUES}.md로 분리, CLAUDE.md는 520→181줄로 축소(자주 필요한 내용만 유지 + 링크 표)

개발 명세 문서도 모듈별 specs/ 폴더로 재배치했다.

  • strategy_v1/DEVELOPMENT_SPEC.md → strategy_v1/specs/DEVELOPMENT_SPEC.md(코드 대조 검증 후 stale 10건 정정)
  • strategy_v2/DEVELOPMENT_SPEC.md → strategy_v2/specs/DEVELOPMENT_SPEC.md — 삭제는 보류했다. 감사 결과 기존 strategy_v2/specs/ 6개 파일이 DB 스키마·v1→v2 마이그레이션 계획만 다루고 실제 매매 로직·점수체계·운영 YAML은 전혀 없어서, 삭제하면 영구 손실 위험이 있었다. conn↔db_path 시그니처·--pre-market 분리·cache_manager 조건·revive_position_registry* 등 stale 4건을 직접 수정하고, 완료된 phase 기획 문서 5개는 strategy_v2/specs/archive/로 보관했다.
  • web/DEV_REQUEST_v2_TRADING_SETTINGS.md → web/specs/, web/specs/DEVELOPMENT_SPEC.md 신규 작성(미들웨어·인증·라우터·백테스트 백그라운드·설정쓰기 패턴)

저장소 전체의 경로 참조(.claude/skills/*, README.md, docs/*.md, 코드 docstring 등)를 새 경로로 갱신했다. /simplify 4관점(reuse/simplification/efficiency/altitude) 병렬 리뷰로 PROJECT_STRUCTURE.md의 잘못된 진입점 안내(archive로 옮긴 00_INDEX.md → DEVELOPMENT_SPEC.md로 정정)와, docs/README.md에 docs/development/ 상호 링크 추가도 반영했다.

docs/ 21개 문서 전체를 현재 코드와 6개 영역 병렬 대조해 stale 5건을 추가로 발견·정정했다(strategy_v2 sector_max_count 3→12 누락, AI_CODE_SAFETY_CHECKLIST.md 매수/매도 잔고 재조회 체크 분리, KNOWN_ISSUES.md에 누락된 6/24~25 qty_before 로컬화·cancel_order 3-state 처리 인시던트 추가, UPDATE.md/USAGE.md 보강). 나머지는 모두 코드와 일치를 확인했다.

코드 동작 변경은 없었고(문서 재구성 + 경로/주석 문자열 수정만), pytest tests/ 764개 전체 통과를 확인했다.

PR #75 머지 + v0.6.3 릴리즈#

PR #75(docs-sync 재점검 + 계좌별 수익그래프 다음 작업 기록) CI 통과를 확인한 뒤 사용자 지시로 gh pr merge --squash를 진행하고, master 머지 확인 후 git fetch origin master && git merge origin/master로 feature/build를 동기화했다.

v0.6.2 이후 머지된 PR #71~#75 기준으로 release-notes-draft-v0.6.3.md를 작성했다(모두 버그 수정 + 문서 정리, 신규 기능이 없어 patch 버전으로 제안 → 사용자 확인). pytest tests/ 764개 전체 통과를 다시 확인했다. 사용자 확인 후 git tag v0.6.3(origin/master HEAD, PR #75 포함 커밋) push + gh release create로 GitHub Release 게시를 완료했다.

docs-sync 재점검: PR #63~#74#

6월 23일 docs-sync 전체 재작성 이후 머지된 PR #63~#74(18개 커밋)와 docs/ 21개 문서를 5개 영역(strategy_v1/v2 흐름, 설정, 워크플로우, README/UPDATE/TESTING_GUIDE)으로 나눠 병렬 Explore 서브에이전트로 대조해 stale 콘텐츠 7건을 발견·수정했다.

문서 발견·수정 내용
STRATEGY_V1/V2_trading_flow.md buy_amount_per_stock → total_asset_buy_ratio 동적 계산(PR #68) + 현금 하한선 강제매도 흐름 반영, VWAP 목표가 손실 중 발동 버그(PR #70, 이제 수익 중일 때만) 반영, cache_manager.load() 날짜 불일치 버그(PR #72) 반영, v2 screening_log DB 미기록 한계 명시
SETTINGS_GUIDE.md 가격범위/보유종목한도가 v1/v2 공통 전역 설정으로 이동(PR #70)했다는 내용 추가
WORKFLOW.md 주문 체결 판단(qty_before/holdings-diff, cancel_order 3-state 좀비주문 방지, PR #69/#71) 섹션 신설
README.md/CLAUDE.md 테스트 41→42개, README.md DB 8→9개 테이블 정정
TESTING_GUIDE.md 누락된 테스트 파일 2개 표에 추가

추가로 사용자 질문(장 종료 후 --reconcile로 보유 계좌 예치금·평가액을 확인 중인데 계좌별 일별 수익금/수익률 그래프를 그릴 수 있는지)에 답했다 — 현재는 불가능하다(accounts.current_eval이 reconcile마다 덮어쓰기만 되고 이력이 안 남는다)는 것을 확인하고, build-docs/next-tasks.md의 “투자원금 입출금 이력(ledger) 테이블” 작업 항목에 4번으로 추가했다. 입출금 이력과 같이 설계해야 수익률이 왜곡되지 않으므로 같은 다음 세션에서 함께 진행하기로 했다.

스크리닝 로그 v2 미기록 원인 조사#

사용자 제보: /screening 대시보드 페이지에 2026-06-18 이후 기록이 없다.

systematic-debugging으로 조사한 결과, insert_screening_log() 호출처가 strategy_v1/trading/buy.py 단 한 곳뿐이고 strategy_v2(screening/first_stage_groups.py, trading/buy.py)는 git 전체 히스토리상 이 함수를 호출한 적이 한 번도 없었다 — 오류가 아니라 v2에 애초부터 빠져 있던 기능이었다. work-log.md 6월 17일 기록상 OCI가 이미 active_strategy_version=v2로 운영 중이었고, 마침 6/18(커밋 a5e4bb8) v2 매수흐름이 09시 4그룹 통합 선정 방식으로 개편되며 운영 전환이 맞물려 그 시점부터 기록이 끊긴 것으로 추정했다.

사용자 결정으로 지금은 구현에 착수하지 않고, OCI 확인 방법과 구현 시 권장 방향(strategy_v2/trading/buy.py에 insert_screening_log() 호출 추가, 매매 로직 변경이라 5단계 필수)만 next-tasks.md에 기록했다. Claude는 OCI SSH 접근이 불가능해 실제 운영 중인 active_strategy_version 값과 후보 풀 캐시 파일 생성 여부는 코드 레벨 추정일 뿐 확인하지 못한 상태로 남겨뒀다.
