자동매매 Bot 전환 및 개발 · KIS (4) — 기존 봇의 운영 사고를 새 설계의 '계약'으로 옮기다

코드를 한 줄도 이식하지 않은 채 기존 저장소의 사고 이력·리뷰·릴리스 노트를 전수 대조했더니, 사고로 확정된 집행 규칙이 새 설계 문서에 하나도 없었다. 분석 데이터 축적, 안전장치, 집행 계약, 릴리스 태깅 규칙을 문서에 명문화한 과정.

들어가며#

새 저장소 kis-auto-trading은 7월 7일 이후 코드 이식을 시작하지 않았다. 대신 7월 8일부터 11일까지는 문서만 고쳤다. 이유는 하나다. “검증된 로직은 재작성하지 않고 그대로 옮긴다"는 원칙이 있는데, 무엇이 검증된 동작인지가 문서에 적혀 있지 않았기 때문이다.

1. 판단 근거를 DB에 항상 남기는 설계 (7월 8일)#

코인 자동매매 파생 프로젝트에서 확정한 “매매 분석 데이터 축적” 설계를 이 저장소에 역으로 반영했다. 기존 봇은 판단 근거가 DEBUG 로그에만 남았는데 운영 기본 레벨이 INFO라 사실상 사라졌다.

핵심 원칙은 한 줄이다. 판단 스냅샷은 로그 레벨과 무관하게 DB에 항상 기록한다. 로그는 관제용이고, DB가 분석의 정본이다.

  • 기록 시점 네 가지: 후보 선정, 진입, 청산, 사후 추적
  • 스키마 요건: 결측 종가를 -100%로 오기록하지 않고 NULL로 둔다, 청산 사유는 고정 열거형으로 둔다, 60일을 넘긴 후보는 제외한다, paper와 백테스트가 같은 스키마를 쓰도록 모드 컬럼을 둔다
  • 완료 기준: 왕복 매매 1건이 네 종류 레코드를 모두 남기는지 검증하는 테스트

일지(사람이 읽는 것)와 스냅샷(집계용)은 역할이 달라서 별도 단계로 유지하기로 했다.

2. 첫 주 운영 리뷰와의 갭 대조 → 안전장치 8건 (7월 10일)#

기존 저장소의 첫 주 운영 리뷰를 읽고 새 설계와 대조했다. 이미 설계가 커버한 것은 8건 중 2건뿐이었다. 나머지를 전략과 무관하게 코어가 지켜야 하는 안전장치로 문서에 추가했다.

영역 요구사항
주문 집행 오래된 가격으로 주문 금지, 청산 사유별 주문 유형 구분, 미체결 시 재시도 간격 늘리기
리스크 손절 후 재진입 쿨다운, 일일 손실 한도 회로 차단기, 기업 이벤트로 인한 가격 괴리 가드
데이터 우선주·저유동성 필터, 업종 해석 정상화

여기서 중요한 구분이 하나 생겼다. 원칙상 이식은 로직을 고치지 않지만, 운영에서 결함으로 증명된 두 항목은 문서화된 예외로 이식 시 수정하기로 했다. 대신 회귀 테스트에서 그 케이스의 기대값이 기존 코드와 의도적으로 다르다는 것을 주석으로 남긴다. 그래야 나중에 회귀가 어긋났을 때 이식 결함과 의도된 수정을 구분할 수 있다.

3. 운영 교훈 전수 대조 → ‘집행 계약’ 10개 항 (7월 10일 두 번째 세션)#

“기존 운영 코드의 오류와 개선 사항이 새 설계에 정말 반영됐는지 깊게 확인해 달라"는 요청으로 더 넓게 훑었다. 대상은 사고 이력 문서, 6~7월 두 차례의 코드 리뷰, AI 코드 안전 체크리스트, 릴리스 노트였다.

핵심 갭은 이거였다. 사고를 겪고 확정된 집행 규칙이 코드에는 있었지만 새 설계 문서에는 전혀 없었다. 예를 들면 다음과 같다.

  • 체결 판단은 잔고 증감(holdings-diff) 기반으로 한다
  • 주문·취소 재시도를 하지 않는다
  • 매도 수량 기준은 로컬 보유량이다
  • 취소는 3가지 상태(성공, 실패, 이미 체결)로 구분한다
  • 레지스트리는 체결 시점에 기록한다
  • 보정 로직은 대기 주문을 건드리지 않는다
  • 시각은 항상 한국 시간 헬퍼로 얻는다

이런 규칙이 문서에 없으면, 나중에 누군가 코어를 개정하면서 “더 깔끔한 구조"로 바꾸는 순간 사고 방지 장치가 조용히 사라진다. 그래서 ARCHITECTURE에 “집행 계약 — 기존 운영 사고로 확정된 설계 결정” 절을 새로 만들어 열 가지 항으로 명문화하고, 이식 대상 파일마다 어느 사고에서 온 규칙인지를 표시했다. 주문 관리자처럼 사고가 몰린 모듈에는 “재작성 절대 금지"를 붙였다.

데이터 계약도 보강했다. 일봉 첫 항목을 버리기 전에 날짜를 확인할 것(앞 글의 지수 캐시 버그), 종목명은 캐시 사전이 정본이라는 점(조회 API에 이름 필드가 없다), 파일 열기는 인코딩을 명시할 것이 그것이다.

기존 저장소의 미해결 항목 9건은 “승계 확인 목록"으로 따로 정리했고, 이식 시점에 원본 상태를 다시 확인하도록 규칙을 정했다. 기존 저장소가 계속 수정되고 있어서, 목록은 2026-07-10 시점의 스냅샷일 뿐이기 때문이다.

4. 개발요청서 거버넌스 대조와 릴리스 태깅 규칙 (7월 11일)#

실제로 작성된 개발요청서 1건을 거버넌스 문서 전체와 대조했다. 발견은 이랬다.

  • 요청서는 “코어 이식 1단계 착수"를 전제로 쓰였다.
  • 그런데 이틀 뒤 “코인 파일럿이 끝날 때까지 코드 착수를 유예한다"는 결정이 내려졌고, 이 사실이 요청서에도, 작업 시작 절차가 정독하는 인수인계 문서에도 반영되지 않았다.
  • 결과적으로 절차를 그대로 따르면 “착수 가능"으로 오인할 틈이 있었다.

이 유예를 요청서에 배지로 표기하는 건 사용자 확인을 기다리는 제안 상태로 두었다. 대신 릴리스 태깅 규칙을 신설했다.

태그 의미
v0.1.0 ~ v0.7.0 이식 1단계 완료부터 7단계(웹) 완료까지
v0.8.0 섀도 병행 개시
v0.9.0 실거래 신규 진입
v1.0.0 이후 발견된 오류 수정·안정화 완료

단계 사이의 소규모 변경은 패치 태그(v0.1.1 등)를 허용하고, 문서만 바뀐 커밋은 태깅 대상이 아니다.

정리#

날짜 작업 결과
7/8 매매 분석 데이터 축적 설계 역반영 “판단 스냅샷은 DB에 항상” 원칙
7/10 첫 주 리뷰 갭 대조 코어 안전장치 8건, 동작 보존 예외 문서화
7/10 운영 교훈 전수 대조 집행 계약 10개 항, 승계 확인 목록 9건

배운 점: 잘 돌아가는 시스템을 다시 세울 때 가장 쉽게 유실되는 건 코드가 아니라 “왜 이렇게 하는지"의 이력이다. 사고로 얻은 규칙을 코드에만 두면 구조를 바꾸는 순간 사라진다. 코드를 옮기기 전에 그 규칙을 계약으로 문서에 올려 두는 편이 안전하다.
