자동매매 Bot 전환 및 개발 · Upbit (11) — 전략의 '기억'을 코어에 두고, 크론을 다섯 줄로 줄이다

4단계 청산 상태머신을 가진 전략을 붙이려니, 15분마다 새 프로세스로 도는 구조에서 포지션 상태를 다음 사이클로 넘길 방법이 없었다. 범용 상태 영속 메커니즘을 코어에 만든 설계 판단, 서브에이전트가 엉뚱한 브랜치에 커밋한 사고의 복구, 그리고 전략×단계 조합마다 한 줄씩이던 크론을 단계당 한 줄로 바꾼 과정을 정리한다.

들어가며#

새 전략(여기서는 충격 후 반등 계열)을 운영 코드에 붙이는 작업이 코어의 구조적 공백에서 멈췄다. 이 전략의 청산은 4단계 상태머신이다. 진입 후 상태는 OPEN에서 PARTIAL_1, PARTIAL_2로 넘어가고, 트레일링 기준이 되는 고점도 계속 갱신된다. 그런데 이 시스템에는 상태를 다음 사이클로 넘길 수단이 없었다.

1. 왜 상태를 넘길 수 없었나#

가드 사이클은 15분마다 새 프로세스로 실행된다. 메모리에 남는 것이 없다. 그러면 포지션 정보는 매번 장부에서 다시 만들어진다.

  • 포지션 뷰의 메타 정보는 진입 시점에 한 번 기록한 스냅샷에서 재구성된다. 이후 갱신되지 않는다.
  • 부분 청산 경로도 실현 손익, 최대 유리/불리 변동폭, 남은 수량만 갱신하고 임의 상태는 저장하지 않는다.

앞서의 전략들은 청산 규칙이 “현재 가격과 진입 정보"만으로 결정되어서 상태가 필요 없었다. 이 전략이 처음 상태 있는 청산을 요구한 것이다.

2. 방향 결정: 최소 수정 vs 범용 메커니즘#

사용자에게 두 가지를 제시했다.

  1. 초기 수량을 노출하는 정도의 최소 변경 + 캔들로 상태를 근사하기
  2. 코어에 범용 상태 영속 메커니즘을 새로 만들기

근사는 빠르지만 근사 로직이 틀리면 청산 판단이 틀어진다. 사용자는 2번을 택했다. 순서는 기획(brainstorming) → 설계 문서 → 구현 계획(7개 태스크) → 격리 작업 브랜치에서 태스크별 구현·리뷰 두 단계였다.

3. 만든 것: 두 개의 메타를 분리한다#

핵심은 청산 결정 객체에 “다음 사이클로 이월할 상태"를 담는 새 필드를 추가한 것이다. 기존 메타 필드는 “청산 시점의 로그 근거"용이라 용도가 달라서 섞지 않았다.

  • 장부에 strategy_state 컬럼을 추가하고, 기존 수량 컬럼 때와 같은 방식의 조건부 마이그레이션을 붙였다. 운영 중인 DB에서도 안전하다.
  • 상태 갱신은 전체 교체이고 병합이 아니다. 어떤 키가 사라져야 할 때 애매함이 없다.
  • 사이클 실행부는 보유 유지 결정에서도 상태를 영속한다. 청산이 아닌 사이클에서 고점이 갱신되기 때문이다.
  • 포지션 뷰를 만들 때 진입 스냅샷 위에 저장된 상태를 덮어써서 전략이 이어 받는다.

기존 두 전략은 이 필드를 채우지 않아서 빈 딕셔너리가 된다. 이 경우 DB 쓰기 자체를 건너뛰므로 회귀가 없다.

의존성 규칙이 만든 제약#

의존성 검사기가 전략끼리 서로를 import하지 못하게 한다. 그래서 신규 전략은 유니버스 구성 같은 공통 패턴을 기존 전략에서 가져오지 못하고 자체 구현했다. 중복처럼 보이지만 전략 간 독립성 계약을 지키는 대가다. 계약의 개수는 그대로 유지하고 기존 계약의 대상만 확장했다.

4. 사고: 서브에이전트가 엉뚱한 곳에 커밋했다#

태스크 구현은 서브에이전트에게 맡겼는데, 한 구현자가 지정된 격리 작업 브랜치가 아니라 메인 저장소 체크아웃에서 작업했다. 그 결과 커밋이 그대로 주 브랜치에 올라갔고, 포맷팅만 다른 불필요한 파일 두 개도 생겼다.

오케스트레이터가 상태와 차이를 확인하다 발견해서 복구했다.

  1. 문제 커밋을 cherry-pick으로 작업 브랜치에 옮기고, 전체 테스트와 의존성 검사를 다시 돌려 확정했다.
  2. 주 브랜치는 사고 이전 커밋으로 reset --mixed한 뒤, 영향받은 파일만 개별 복구했다.
  3. 불필요한 파일을 삭제했다.
  4. 사용자의 기존 미커밋 변경(에이전트 설정 파일 등)은 전 과정에서 건드리지 않고 diff로 대조해 보존했다.

복구에 reset --hard를 쓰지 않은 이유가 그것이다. 사용자의 작업 중인 변경이 섞여 있으면 하드 리셋은 되돌릴 수 없다. 서브에이전트에게 작업 위치를 지정해도 지켜지지 않을 수 있다는 점은 이후 구현 지시에 “작업 디렉터리를 먼저 확인"하는 단계를 넣는 계기가 되었다.

이어서 그 전략의 백테스트 재현(동일 코드)이 끝나고, 사용자 판단으로 두 전략에 자금을 나눠 실거래를 시작했다. 배분 비율은 공개하지 않는다.

5. 크론 재설계: 전략마다 한 줄이던 것을 단계마다 한 줄로#

신규 전략을 실거래에 올리자마자 사용자가 요청했다. “크론에 전략 ID를 변수로 주지 말고 한 번씩 실행시키고, 투자 비율에 따라 투자하게 해 줘. 크론은 한 번 설정해 놓으면 수정하지 않는 방향으로.”

기존 크론은 전략 3개 × 단계 5개 = 15줄이었고, 새 전략마다 줄을 추가해야 했다.

구현#

  • 이미 모니터링과 웹이 쓰던 “등록된 전략 목록” 함수를 재사용해, 전략 ID가 생략되면 등록된 전체를 정렬·중복 제거해 순회하는 순수 함수를 만들었다 (TDD).
  • 전략 ID 인자를 필수에서 선택으로 바꿨다. 기존 15줄 형태가 남아 있어도 깨지지 않는 하위호환이다.
  • 한 전략의 오류(API 오류, 예기치 못한 예외)는 해당 전략만의 문제로 보고 CRITICAL 로그와 알림을 남긴 뒤 다음 전략으로 계속 진행한다.
  • 단 하나, 거래소 요청 차단(418) 응답이 오면 순회 전체를 즉시 중단한다. 계좌 전체 차단인 상태에서 다른 전략으로 요청을 이어가면 상황만 악화되기 때문이다.
  • 락은 전략별 분리에서 단계 그룹별 공유 락 하나로 단순화했다. 이전에 전략별로 나눈 이유는 서로 다른 전략이 별도 프로세스로 동시에 스케줄되었기 때문인데, 이제는 한 프로세스가 순차 처리하므로 동시성이 없다.

순회로 바뀌면서 미리 잡은 버그#

하나의 프로세스가 여러 전략을 순회하게 되자 로그 필터가 문제가 될 것을 사전에 발견했다. 로그 레코드에 전략 ID를 붙이는 필터가 생성자에서 받은 값을 인스턴스에 고정하는 구조였고, 로깅 설정은 같은 파일에 핸들러를 한 번만 붙인다. 그대로 두면 두 번째 전략부터 모든 로그의 전략 ID 필드가 첫 번째 전략 이름으로 찍힌다. 기존 호출부 전부가 필터의 기본값에 의존하기 때문이다.

재현 테스트를 먼저 작성해 실패를 확인하고, 필터가 모듈 전역 값을 참조하며 로깅 설정 호출 때마다 그 값을 갱신하도록 고쳤다. 아직 어느 서버에서도 일어나지 않은 문제였다. 구조를 바꿀 때 “이 변경이 기존 가정을 깨는가"를 훑어 본 덕분이다.

설치 문서의 크론 예시는 15줄에서 5줄로 줄었다. 새 전략은 레지스트리 등록과 배분 설정만 하면 크론 수정 없이 자동 포함된다.

서버의 실제 크론은 이 세션에서 원격 접근 수단이 없어 사용자가 직접 갱신해야 한다. 기존 형태도 하위호환으로 동작하지만, “다시 수정하지 않는다"는 목표는 새 형태로 바꿔야 실제로 달성된다.

정리#

영역 변경
상태 청산 결정에 이월 상태 필드, 장부 컬럼과 마이그레이션
구조 전략 독립성 계약 유지를 위해 공통 패턴을 자체 구현
사고 서브에이전트가 잘못된 브랜치에 커밋 → cherry-pick과 선택적 복구
크론 15줄 → 5줄, 전략 ID 선택 인자
안전 418은 순회 중단, 일반 오류는 해당 전략만 격리

배운 점: 시스템에 처음 “상태 있는 전략"이 들어올 때는 그 전략만 위한 우회로를 만들기보다 범용 메커니즘을 코어에 두는 편이 낫다. 다음 전략이 같은 문제를 다시 만나지 않는다. 그리고 실행 구조를 바꾸는 변경에서는 코드의 의도가 아니라 기존 코드가 암묵적으로 기대하던 가정을 찾아야 한다. 로그 필터의 고정 값처럼 한 프로세스에 한 전략이 있다는 가정이 대표적이다. 마지막으로 에이전트에게 위임한 작업은 결과의 위치까지 검증해야 한다. 복구 때 사용자의 미커밋 변경을 보존하는 것이 가장 먼저 지킬 조건이다.
