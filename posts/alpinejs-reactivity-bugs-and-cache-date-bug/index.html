자동매매 코드 개발 (37) — Alpine.js 반응성 버그, 캐시 날짜 불일치 버그

들어가며#

이전 글에서 29시간 좀비 주문 사고를 해결했다. 6월 29일은 프론트엔드 버그 두 건과 로깅·캐시 관련 버그 두 건, 총 네 건을 하루에 몰아 처리한 날이다.

결론부터 말하면, 추가 계좌 투자원금 입력칸이 영구히 비활성화되는 버그를 브라우저 콘솔로 직접 추적해 Alpine.js의 반응성 엣지케이스임을 확인했다. 이어서 LOG_LEVEL=DEBUG가 콘솔에 전혀 반영되지 않던 버그, 그리고 cache_manager가 배포 이후 한 번도 “오늘 날짜” 캐시를 못 찾고 있던 구조적 버그도 함께 고쳤다.

저장 버튼이 요청 실패 시 영구 잠기는 버그#

사용자 제보: “웹 대시보드 - 설정 - 추가 계좌 투자원금” 카드의 입력칸/버튼이 회색으로 눌리지 않는다.

web/templates/settings.html의 setCapital/setExtraAccountCapital/applyCapitalFlow/applyExtraAccountCapitalFlow 4개 함수 모두 저장 시작 시 capitalSaving/extraCapitalSaving[account_id]를 true로 설정한 뒤 try/catch 없이 fetch→res.json()을 호출하고 있었다. 세션 만료(로그인 페이지로 리다이렉트되어 응답이 JSON이 아님)나 네트워크 오류로 예외가 발생하면, 그 플래그를 다시 false로 되돌리는 코드가 실행되지 않아 새로고침 전까지 버튼이 영구히 비활성화 상태로 남는 구조였다.

수정: 4개 함수 모두 try/catch/finally로 감싸 요청 성공/실패/예외 어떤 경로든 saving 플래그가 항상 풀리도록 했다. 예외 발생 시 “요청 실패 — 세션 만료 또는 네트워크 오류일 수 있습니다…” 에러 메시지도 표시하게 했다. 즉시 우회법은 /settings 새로고침(Ctrl+F5)이었다 — saving 플래그는 페이지 로드 시 초기화되기 때문이다.

고쳤는데도 여전히 비활성 — Alpine.js 반응성 엣지케이스#

문제는 여기서 끝나지 않았다. PR #73(위 try/catch/finally 수정) 배포 후에도 “추가 계좌 투자원금” 카드의 입력칸이 여전히 비활성이었다. update_oci.sh로 최신 커밋 배포 확인, kis-web 서비스 재시작 확인, 브라우저 완전 재시작·로그아웃 후 재로그인·시크릿 모드까지 모두 시도해도 동일하게 재현됐다 — 앞의 수정과는 별개의 근본 원인이 있다는 뜻이었다.

근본 원인은 브라우저 콘솔로 직접 추적했다. extraCapitalSaving: {}라는 별도 객체에 계좌ID를 키로 써서 저장 중 상태를 추적하는 방식이 문제였다. 콘솔에서 Alpine.$data(root).extraCapitalSaving이 빈 객체 {}로 정상인데도 실제 DOM의 disabled 속성은 true로 고착돼 있었다. 콘솔로 강제로 extraCapitalSaving[account_id] = true → false를 한 번 써주면 그 즉시 정상화됐다 — Alpine.js가 빈 반응형 객체에서 존재하지 않는 키를 처음 읽는 순간에는 반응성 추적이 제대로 안 걸리는 엣지케이스였다. 새로고침마다 이 “최초 읽기” 상황이 재현되어 매번 비활성 상태로 멈췄던 것이다.

수정: 계좌별 저장 상태를 별도 사이드 객체(extraCapitalSaving[account_id]) 대신 각 계좌 객체 자체의 saving 속성으로 이동(acc.saving)했다. init()에서 extraAccounts를 매핑할 때 saving: false를 미리 박아둬서 “존재하지 않는 키"라는 상황 자체가 생기지 않도록 했다. web/templates/settings.html의 데이터 정의·init()·HTML 바인딩 5곳·저장/입출금 함수 2개 전부 acc.saving으로 교체했다.

디버깅은 브라우저 DevTools Console에서 사용자와 함께 실시간으로 진행했다 — Elements 패널 $0 + Alpine.$data()로 실제 반응형 상태를 직접 읽고 강제 조작해 반응성 자체를 테스트하는 방식이었다. 정적 코드 분석만으로는 찾기 어려운 프레임워크 레벨 엣지케이스였다.

pytest tests/test_web_pages.py tests/test_config_router_v2.py 75개는 통과했지만, 프론트엔드 JS 전용 수정이라 이 버그 자체는 pytest로 검증할 수 없었다 — OCI 배포 후 실제 화면에서 재확인이 필요했다.

LOG_LEVEL=DEBUG가 콘솔에 적용되지 않는 버그#

사용자 제보: “crontab에 LOG_LEVEL=DEBUG가 실질적인 역할이 없다.”

systematic-debugging으로 확인한 결과, utils/logger.py::setup_logging()의 콘솔 핸들러 레벨이 max(effective_level, logging.INFO)로 항상 INFO 이상에 고정돼 있어 LOG_LEVEL=DEBUG를 줘도 cron.log(콘솔 출력)에는 DEBUG 로그가 전혀 찍히지 않았다. trader.log는 _TRADING_LOGGER_PREFIXES 6개 모듈(매매/스크리닝)로만 필터링돼 있어서, api/kis_api.py·runner.py 등 나머지 대다수 모듈의 debug() 호출은 콘솔(floor로 차단)·trader.log(필터로 차단) 어디에도 남을 곳이 없었다.

수정: 콘솔 핸들러 레벨에서 INFO floor를 제거하고 effective_level을 그대로 적용했다. trader.log 필터는 유지(매매 결정 중심 그대로)했다 — 콘솔엔 필터가 없으므로 LOG_LEVEL=DEBUG 시 전체 모듈의 debug 로그가 cron.log로 노출되고, 기본(INFO)일 때는 기존과 동일하게 동작한다.

TDD로 진행했다. tests/test_logger.py에 TestSetupLoggingLevel을 추가해 RED를 확인한 뒤 1줄 수정으로 GREEN 전환했다. pytest tests/ 764개 전체 통과를 확인했다.

캐시가 배포 이후 한 번도 정상 작동하지 않던 버그#

사용자 제보: “06-25 18:00 next-pre-market에서 캐시 생성 확인했는데 06-26 09:00에 캐시 없음.”

logs/cron_next_pre.log/logs/cron.log 06-22~06-26 5일치 전체를 대조한 결과, 매일 09:00 빠짐없이 재현되는 구조적 버그였다.

근본 원인은 strategy_v2/cache_manager.py::load()가 date_str 미지정 시 now_kst()(호출 시점 = 오늘) 날짜로 캐시 파일을 찾는데, 캐시는 전날 18:00 생성되어 생성일 기준 파일명(cache_YYYYMMDD.json)으로 저장된다는 데 있었다. strategy_v2/trading/buy.py가 09:00에 인자 없이 호출하면 그날 18:00에야 생성될 파일을 찾으므로 항상 None이었다 — 그룹 A(avg_volume)/C(sector_top40)/D(rsi)가 배포 이후 한 번도 캐시 기반으로 동작하지 못하고 그룹 B(fallback_relative_strength)만 작동하고 있었던 것이다. expiry_hours: 72(주말 갭 대비 설정)는 정상이라 만료 문제가 아니라 파일을 못 찾는 단계의 문제였다.

수정: 사용자 확인(2개 옵션 중 “가장 최근 캐시 파일 자동 탐색” 선택)에 따라 load()가 date_str 없을 때 cache_dir 내 cache_*.json 중 파일명 날짜 기준 가장 최근 파일을 자동 탐색하도록 변경했다. 만료 판단은 기존처럼 호출자의 is_expired()가 별도 수행한다(동작 분리 유지).

TDD로 RED(신규 테스트가 “오늘 날짜만 찾던” 기존 동작에서 실패) 확인 후 GREEN 전환했다. tests/test_cache_manager.py에 회귀 테스트 3건을 추가했다(최근 파일 탐색, 빈 디렉터리 None, 깨진 최신 파일 → 오래된 정상 파일 폴백 — 마지막 항목은 코드 리뷰 권고로 추가). 코드 리뷰(general-purpose subagent)는 Critical 없음, Important 1건(깨진 파일 폴백 테스트 누락)을 반영 완료했고, Minor(날짜 정렬이 고정폭 파일명 가정에 의존한다는 점 주석화)도 반영했다.

작업 시작 시 미커밋 상태로 남아있던 두 파일(web/templates/backtest.html 날짜 기본값 갱신, docs/STRATEGY_V2_full_detail.md 677줄 문서)도 사용자 확인 후 함께 커밋했다. .gitignore에 빠져 있던 런타임 파일 패턴(token_cache_appkey_*/token_cache_extra_*/*.json.lock/*.bak.*/backtest_result_*.json/initial_capital.json/data/cache/)도 추가해 다수의 토큰 캐시·lock·백업 파일이 untracked로 누적되던 문제를 해소했다.

pytest tests/ 762개 전체 통과를 확인했다.

정리#

버그 원인 수정
저장 버튼 영구 잠김 try/catch 없는 fetch, 예외 시 플래그 미복구 try/catch/finally로 전체 감싸기
입력칸 영구 비활성(재발) Alpine.js 빈 객체 최초 키 읽기 반응성 누락 사이드 객체 대신 계좌 객체 자체 속성(acc.saving)
LOG_LEVEL=DEBUG 무효 콘솔 핸들러가 INFO floor 강제 effective_level 그대로 적용
캐시 매일 09:00 미스 load()가 “오늘” 날짜로만 파일 탐색 가장 최근 캐시 파일 자동 탐색

네 버그 모두 “고쳤다고 생각했는데 증상이 남아있다"는 패턴이 하나씩 있었다 — 저장 버튼은 1차 수정 후에도 재발했고, 캐시는 배포 이후 계속 조용히 실패하고 있었다. 브라우저 콘솔에서 실시간으로 반응형 상태를 직접 조작해본 게 정적 분석으로는 안 보이던 원인을 찾는 데 결정적이었다. 다음 글에서는 여전히 6월 29일, CLAUDE.md를 분리하고 개발 문서를 재구성한 뒤 docs-sync를 재점검하고 v0.6.3을 릴리즈하는 과정을 다룬다.
