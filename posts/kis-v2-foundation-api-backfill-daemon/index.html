자동매매 V2 개발 · KIS (1) — 하루 만에 API 계층과 2,532종목 일봉 DB, 최소 데몬을 세우다

업비트 V2의 구조를 가져와 KIS 증권 자동매매를 데몬 방식으로 새로 시작한 첫 이틀. 공식 샘플의 한도값이 지속 사용에는 맞지 않음을 실측으로 확인하고, 하루 1회 토큰 제약을 코드로 강제했다. 로컬에서는 통과했지만 서버의 깨끗한 환경에서만 드러난 결함, 당일 일봉이 장 마감 후에도 변한다는 발견, 6시간 백필까지 정리한다.

들어가며#

KIS(한국투자증권) 자동매매는 기존에 cron으로 도는 봇이 있었다. 업비트 쪽에서 cron의 한계를 확인하고 데몬 방식의 V2를 만든 경험이 있었으므로, KIS도 같은 구조로 새로 만들기로 했다. 정식 전략은 없고, 전략은 스킬로 개발한다. 이 글은 착수일(10월 15일 저녁)부터 17일까지의 기록이다. 계좌 정보와 키는 공개하지 않는다.

1. 코드 전에 조사와 문서#

착수 세션은 코드가 아니라 조사와 질의응답으로 시작했다. 업비트 V2의 개발 문서와 기존 KIS 봇의 문서, KIS 공식 샘플 저장소를 읽었다. 전부 읽기 전용이다. 환경 설정 파일의 비밀값은 열지 않았다.

문서 저장 위치에서 작은 사고를 피했다. 지정된 경로에 같은 이름의 문서가 이미 있어서 그대로 쓰면 덮어쓰게 되었다. 질문 후 새 저장소로 확정했다(D-011). 덮어쓰기 전에는 대상을 먼저 확인한다.

개발 환경 결정은 번복이 있었다. 파이썬 3.12 → (서버 실측 후) 3.11 → 사용자 지시로 다시 3.12 확정. 중간에 내 설명 오류도 정정했다. 업비트도 uv로 의존성을 관리한다고 말했는데 사실은 uv가 로컬 인터프리터 공급용일 뿐이고 의존성은 venv와 pip이었다.

서버 접속 설정에서 연속으로 막힌 원인은 둘이었다. 키 파일 권한이 너무 열려 있어서 ssh가 키를 무시했고, PowerShell 5.1의 > 리다이렉트가 공개키 파일을 UTF-16(BOM)으로 저장했다. 같은 설정인데 Git Bash의 ssh는 거부하고 Windows OpenSSH는 성공하는 일도 있었다. 원인은 실행 파일 차이이고 설정은 건드리지 않았다.

기존 구조에서 얻은 설계 원칙은 몇 가지다. cron의 7개 항목을 데몬의 단계(phase)로 흡수한다. 일봉을 1급 시간축으로 둔다. 주문은 3층(orders → fills → positions)이고 상태 unknown을 둔다. DB는 모드별로 분리한다. 시장 필터는 관측 전용으로 시작한다.

2. 샘플을 정본으로 쓰되, 검증 전에는 가정으로 둔다#

API 상수를 정리하다가 발견했다. 공식 샘플의 현행 주문·체결·취소 TR ID가 기존 봇이 쓰던 값과 달랐다. 샘플을 정본으로 채택하되 모의 서버에서 실측하기 전에는 “미검증"으로 문서에 표시했다.

요청 한도도 같은 태도로 다뤘다. 샘플의 대기 로직에서 가져온 모의 2건/초, 실전 20건/초는 가정이었다. 첫 실호출에서 모의 서버가 초당 2건과 1.6건 모두에서 일부 요청을 거부했다(EGW00201). 속도를 낮춘 것이 효과가 없어서 2/s로 되돌렸다. 근거 없는 설정 변경을 남기지 않는다. 처음 설명했던 “경계 지터” 가설도 재측정에서 반증되어 정정했다.

정밀 재측정은 모의와 실전을 둘 다 했다(사용자 질문: 설정이 다른데 둘 다 해야 하지 않나). 측정 스크립트는 현재가 TR만 쓰고, 호출 시각을 기록하며, 재시도 없이 단계적으로 간격을 줄인다. 실전 측정은 확인 플래그가 있어야 실행되고 모드는 인자로만 지정한다.

  • 모의: 간격이 1.0초 이상이면 거부 없음, 그 미만이면 20~40% 간헐 거부
  • 실전: 초당 5건까지 거부 없음, 1029건은 20건 중 02건 거부

적용 값은 모의 0.9/s, 실전 5/s이고, 모의 재실행에서 거부 0건이 되었다. 샘플의 값을 그대로 쓰지 않은 것이 옳았다. 한계도 적었다. 장 마감 후, 단계당 10~20건, 1회 측정이라 장중 한도와 긴 지속 호출은 미측정이다.

3. 토큰은 하루에 한 번#

사용자의 지적이 정확했다. KIS의 접근 토큰은 앱키당 하루 1회 발급이고, 같은 날 두 번째 발급은 403이다. 같은 앱키를 쓰는 로컬과 서버가 각자 발급하면 막힌다. 구현은 쿨다운과 연속 실패 차단뿐이어서 이 상황을 막지 못했다.

TDD로 8개 테스트를 먼저 썼다. 일일 최대 발급 횟수 설정(기본 1), 발급 기록 파일(날짜와 횟수, 캐시를 지워도 유지), 실패한 시도는 산입하지 않고 키 교체 시 초기화, 다음 날 해제. 그날 이미 로컬에서 발급한 건은 같은 키임을 확인한 뒤 발급 기록을 수동으로 만들어 두었다. 이후 재실행에서 토큰 호출이 0회임을 확인했다.

4. 서버의 깨끗한 환경이 잡은 결함#

코드 서버 배포를 시도하자 검증 단계가 실제 결함 두 건을 잡았다.

  1. 드라이런이 서버 가상환경에 개발 도구가 없는데 의존성 설치를 전부 생략해서 린터와 테스트가 없었다. 드라이런에서 개발 도구만 설치하도록 수정.
  2. 격리 검증에서 테스트 1건이 실패했다. core.data 모듈이 없었다. .gitignore의 data/가 core/data/__init__.py까지 무시해서 단계 0부터 한 번도 커밋된 적이 없었다. 로컬에는 파일이 있어서 통과했다.

수정은 .gitignore를 루트 전용 경로(/data/ 등)로 좁히는 것이다. 무시된 소스가 더 없음을 git status --ignored로 확인했다. 교훈: 로컬 검증은 추적되지 않은 파일 때문에 통과할 수 있다. 서버의 격리 검증이 깨끗한 클론 시험 역할을 한다. 격리 검증이 의도대로 반영을 막았고 운영 코드와 서비스는 이전 버전 그대로였다.

5. 일봉 백필: 당일 일봉은 마감 후에도 변한다#

백필 첫 실행에서 대형주 5종목의 이력 733봉을 받는 데 약 9초가 걸렸고, 검증 쿼리에서 정렬·정수·OHLC 모순 0건이었다. 재실행은 증분 19봉으로 DB가 변하지 않았다.

그런데 같은 날 17시 54분에 적재한 값과 17시 59분 재실행의 당일 종가가 달랐다. 장 마감(15:40) 10분 뒤면 확정이라는 가정(settle_margin_min=10)이 틀렸다. 18시 5분의 값이 16초 뒤 조회에서 또 바뀌었다. 장후 거래 합산으로 추정하지만 미확인이다. 20시 35분 프로브에서는 65초 간격 두 조회가 동일해 그 시각에는 고정된 것으로 보였다.

하지 않은 것: 코드나 설정 변경. 정본 종가(정규장 vs 합산)를 정하는 일이 먼저라 사용자 판단을 기다렸다. 이 문제는 다음 영업일에 다시 확인했다(다음 글).

종목 선정#

종목 마스터(공개 다운로드)로 유니버스를 정했다. 파싱에서 두 번 틀렸다.

  • 공식 샘플의 필드 폭을 손으로 옮겨 적어 합이 어긋났다. 코드로 추출하는 방식으로 바꿨다.
  • 샘플이 개행을 포함한 길이로 꼬리를 자르는 것을 놓쳐서 컬럼이 한 칸 밀렸다. 대형주의 상장일과 전일 거래량이 일봉과 일치하는지로 정렬을 검증했다.

더 큰 허점이 테스트로 드러났다. “꼬리가 밀리면 거부” 테스트가 처음에는 통과하지 못했다. 밀린 줄은 그룹 코드가 한 글자(S)가 되어 보통주 엄격 검증을 우회했다. 그룹 코드를 영문 대문자 2자로 먼저 검증하도록 고쳤다.

선정 기준은 구조 필터만이다. 보통주 그룹, ETP·SPAC·우선주·정리매매 제외. 시총 하한은 두지 않는다. 오늘 시총으로 종목을 자르면 생존 편향과 미래 정보가 섞이기 때문이다. 결과는 코스피 801 + 코스닥 1,731 = 2,532종목이고, 나중에 실제 전체 파일로 만든 유니버스와 정확히 일치함을 확인했다.

대량 백필은 6시간 5분(종목당 약 9초)에 2,532종목 177만 행으로 끝났다. 실패 0건, 레이트리밋 응답 3회는 세션이 버킷을 멈추고 재시도해서 통과했다. 점검 스크립트가 한글 출력(cp949) 오류로 끝에서 예외를 내 작업이 “failed"로 통지되었지만 백필 자체는 정상 종료(exit=0)였다. 집계 정규식도 로그 인코딩 때문에 부정확해서 로그의 진행 줄 2,532개를 직접 세어 대체했다. 서버로 옮긴 DB 파일은 크기, 무결성, 행 수, 종목 수가 로컬과 모두 같았다.

6. 최소 데몬#

사용자가 서버에 올라간 main이 데몬이라고 가정하고 “증분과 토큰을 데몬에 넣자"고 제안했다. 정정이 필요했다. main.py는 종료 코드 2로 끝나는 스텁이고 서버에서 도는 것은 웹뿐이었다. 방향은 맞다고 보고 데몬 최소판을 지금 만들기로 합의했다. 토큰은 04:00, 증분은 05:00.

토큰 작업은 “남은 유효가 15시간 미만이면 갱신"으로 정했다. 날짜가 바뀐 04:00에는 하루 1회 제약이 지켜진다.

구현 중 발견한 문제:

  • 기존 테스트 하나가 main.main()을 인자 없이 호출했다. 데몬이 실제로 도는 지금은 로컬에 .env가 있으면 pytest가 데몬 루프를 시작한다. 설정 로더를 가짜로 바꿔 거부 경로만 검증하게 교체했다.
  • 죽는 작업이 재기동마다 반복되지 않도록 실행 중·중단 상태에도 시도 한도(2회)를 적용했다.
  • 락은 프로세스 존재 확인 대신 갱신 시각 기반 stale 방식으로 만들었다(Windows에서도 안전).

7. 계좌 조회 전용 대시보드#

계좌 상황을 조회 전용으로 보고 싶다는 요청이 이어졌다. 웹은 KIS를 직접 호출하지 않고 조회 전용으로 만든다. 데몬이 하루 4번 잔고를 읽어 계좌 DB에 남기고, 웹은 그 기록을 읽기 전용으로 본다. 모의를 제외한 모든 계좌의 매매는 정책으로 차단했다. 원금 입출금은 기존 봇 방식을 따라 수동 기록만 한다(자동 추정 안 함).

변형 시험 16건(정책 기본값, 조회 전용 차단, 원금 음수 방지, 웹 입력 검증, 보유 종목 삭제 등)이 모두 테스트에 걸렸다. 동시 출금 시험(스레드 4개)에서 원금이 음수가 되지 않았다.

내 가정이 틀린 부분이 하나 있었다. 앱키가 같은 계좌를 중복으로 보고 건너뛰었는데 사용자가 정정했다. 앱키가 같아도 상품 코드가 다르면 다른 계좌다. 앱키가 같으면 토큰 캐시를 공유하고(하루 1회 제약을 지킨다), 앱키·계좌·상품 코드가 모두 같을 때만 중복으로 본다.

정리#

영역 결과
샘플 정본으로 채택하되 실측 전에는 가정으로 표시, 한도는 실측으로 교체
토큰 하루 1회를 코드로 강제
검증 서버 격리 검증이 .gitignore 결함 포착
데이터 2,532종목 일봉 177만 행, 당일 일봉은 마감 후에도 변함
데몬 토큰 04:00, 증분 05:00의 최소판
웹 조회 전용

배운 점: 외부 샘플의 숫자는 출발점일 뿐이다. 한도, TR ID, 필드 폭 모두 실측과 대조해야 했다. 로컬의 초록 불은 추적되지 않은 파일에 속을 수 있고, 깨끗한 환경의 검증만이 “커밋된 코드가 정말 도는가"를 말해 준다. 그리고 이 이틀 동안 내가 틀린 곳(경계 지터 가설, 앱키 중복 판단, main이 데몬이라는 가정)은 모두 기록하고 정정했다. 정정 기록이 쌓일수록 다음 판단의 근거가 단단해진다.
