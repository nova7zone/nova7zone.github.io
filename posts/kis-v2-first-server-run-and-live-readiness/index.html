들어가며#

10월 19일부터 21일까지는 서버에서 데몬이 실제로 돌기 시작한 사흘이다. 한 일이 많아서 주제별로 묶는다. 계좌 식별자, 주문 번호, 가격은 공개하지 않는다.

1. 첫 가동 점검: 내 추정이 틀렸다#

월요일 아침, 서버를 읽기 전용으로 점검했다. 토큰 갱신(04:00), 시세 증분(05:00~07:30, 2,532종목 실패 0), 계좌 수집(08:50)이 모두 정상이었다. 그런데 증분에서 이상한 것이 보였다. 금요일 일봉 763종목이 분할 소급 수정으로 탐지되어 전체 재적재가 일어난 것이다.

처음에는 금요일 저녁에 받은 잠정값이 원인이라고 추정했다. 틀린 추정이었다. 확정은 읽기 전용 비교로 했다.

  • 서버와 로컬의 금요일 전 종목 일봉을 CSV로 받아 비교했다.
  • 그 전날(목요일)은 2,532개가 전부 같았고, 금요일은 763개의 고가·저가·종가만 달랐다. 거래량과 거래대금은 전부 같았다.
  • 백필 로그의 조회 시각과 대조하니 차이는 새벽 00:38 조회분부터 시작했다. 그 앞 1,593종목은 차이 0건이었다.

결론은 이랬다. KIS가 자정 직후새벽(관측 00:3802:47)에 전일 값을 일시적으로 다르게 돌려줬다. 분할이 아니다. 05:00 이후 값은 저녁 값과 일치했다. 현재 DB는 정상이고 재조치는 필요 없다. “잠정값 vs 확정값"이라던 앞선 추정을 문서에서 정정했다.

이후 며칠 사이 이 문제는 두 번 더 비용을 냈다. 직전 거래일 종가 하나만 달라도 이력 전체를 다시 받아 3시간이 걸렸다(84% 재적재). 최근 3봉만 다를 때는 겹친 구간만 덮어쓰도록 바꿨다(D-074).

2. 퇴직연금 계좌: 차감으로는 구할 수 없다#

세 번째 계좌가 건너뛰어지고 있었다. 이 계좌는 퇴직연금(IRP)이다. v2 설계가 그 상품 코드를 일부러 건너뛰게 해 놓았고, 이전 봇은 퇴직연금 전용 API 두 개를 썼다.

사용자의 제안은 이랬다. “총액에서 보유 종목과 예수금을 빼면 디폴트옵션(펀드) 평가액이 나오지 않을까?” 서버에서 조회 전용 프로브로 실제 응답을 확인했다. 잔고 API의 총액 필드는 예수금 + 보유 ETF 평가일 뿐 펀드를 포함하지 않았다. 다른 API에도 펀드나 총액 필드가 없었다. 그러므로 차감은 항상 0이고 불가능하다. 수동 입력으로 가는 것이 맞았다. 퇴직연금 조회 클라이언트, 수동 자산 입력 저장소, 웹 입력 폼을 만들었다.

부수적으로 시간 의존 테스트 하나를 찾았다. 토큰 공유 테스트의 만료일이 특정 날짜로 고정되어 있어서 날짜가 지나자 실패했다. 실제 시계 기준 만료로 바꿨다.

3. 모의 주문을 실제로 넣었다 취소했다#

공식 샘플이 정본이라고 했지만 모의 서버에서 실측하기 전까지는 가정이었다. 조회 전용이 아닌 첫 실측이므로 방침을 정했다. 가격이 체결될 수 없는 지정가 1주를 접수하고, 내역을 조회하고, 취소하고, 다시 조회한다. 체결도 예수금 변화도 없어야 한다. 매수, 취소, 체결 내역, 주문 가능 조회의 모의용 TR이 모두 정상 동작했다. 지연은 주문 0.6초, 취소 0.4초, 내역 0.3초, 잔고 1.4~2.0초였다.

여기서 중요한 파서 사실을 발견했다. 취소하면 체결 내역에 취소 요청이 별도 행으로 생기는데, 매수/매도 구분 값은 원주문의 매수 그대로다. 구분 값만 보면 취소 행이 두 번째 매수로 보인다. 취소 확인 수량과 취소 행 여부 필드를 추가하고, 실응답을 픽스처로 저장해 파서를 고정했다.

다음 실측은 체결까지 갔다. 시장가 1주 매수와 매도 왕복이다(매수가 불명이면 매도하지 않는다). 얻은 사실:

  • 체결 내역 반영 1.71.8초, 잔고 반영 2.83.8초
  • 예수금 필드는 체결해도 그대로이고, D+2 정산 예정 필드가 즉시 변한다. 가용 현금의 기준은 후자여야 한다.
  • 왕복 비용은 소액이었다.

내 실수도 있었다. 실측 스크립트의 마스킹이 계좌번호뿐 아니라 상품 코드(‘01’)와 같은 모든 값을 가렸다. 그래서 응답 속의 ‘01’(매도 구분, 시장가 코드)이 ***이 되었다. 픽스처에서 복원하고 마스킹 대상을 계좌번호로 좁혔다. 퇴직연금 프로브도 같은 문제(수량 29가 가려졌었다)가 있었다. 마스킹은 필요한 것만 가려야 한다. 과하면 데이터를 오염시킨다.

4. 실전 전환 갭 19건과 그림자 운행#

사용자가 정식 전략이 나오기 전에 실매매 전환 배선을 미리 갖춰 두자고 했다. 코드를 조사해 갭 분석 문서(LIVE_READINESS)를 만들었다. 갭이 19건이었다. 모드 분리, 무장, 절대 상한, 계좌 소유, 그림자 운행, 실서버 검증, 백업, 장애 대응이 포함된다. 코드 변경 없이 live_orders_enabled는 꺼 둔 채였다.

사용자의 결정(실전 계좌만 자동매매, 추가 계좌는 조회 전용, 모의와 실전은 동시 운영하지 않음, 총자산은 실매매 계좌만)에 따라 배선을 했다. 주문은 모드 설정과 live_orders_enabled 두 문을 모두 통과해야 나간다. 모드별 설정 DB, 같은 앱키의 속도 제한기 공유, 웹의 모드 배지·배너를 추가했다.

이어서 체결 알림, DB 백업과 외부 백업(오프사이트), 일 주문 수 가드, 복구 시험, 보유 종목 이벤트 알림, 모드별 거래 비용 모델을 만들었다. 비용은 블로그가 아닌 증권사 공식 수수료 표에서 확인했다.

그림자 운행 리허설#

실제로 모드를 바꿔 보았다. 순서는 이랬다.

  1. 실전 설정 DB에서 전략을 끈다(서버 DB 쓰기).
  2. 사용자가 서버 환경 설정의 모드를 바꾸고 데몬을 재시작한다. 서버를 바꾸는 일은 사람이 직접 하는 것이 이 프로젝트의 경계다.
  3. 읽기 전용으로 확인한다.

결과: 기동 시 “주문 차단(그림자 운행)” 경고, 켜진 전략 없음, 이후 장 마감 후 처리, 계좌 수집(7개 성공), 대조(어긋남 0), 일일 보고 모두 정상, 주문·포지션 0건. 사용자가 텔레그램의 전환 메시지를 확인했다. 이후 원복했다.

확인하지 못한 것을 적었다. 실전 주문 시도가 정책으로 거부되는 실제 동작(단위 테스트로만), 장중 틱, 웹의 실전 모드 화면.

5. 백테스터: TDD를 지키지 못했다#

로컬에서 전략을 개발하기 위한 백테스터를 만들었다. 설계는 실전 코어의 함수를 그대로 호출하고 체결만 가상 브로커가 대신하는 구조다. 일봉만 있으므로 하루 안의 순서를 정해야 한다. 스크리닝 → 보유 종목 시가 틱 → 시가 진입 → 눌림 진입 → 저가·고가·종가 틱 → 마감 후. 저가와 고가 중 무엇이 먼저였는지는 알 수 없어서 경로 가정을 설정으로 두고 둘 다 돌려 범위로 낸다. 4개월 스모크에서 손절 76%가 가정 영향인지 보려고 보수/낙관 두 경로 비교를 추가했다.

작업 로그에는 이렇게 적었다. 구현은 RED-GREEN을 거치지 않았다. 엔진을 먼저 쓰고 골든 시나리오와 단위 테스트를 뒤에 붙였다. 규약(TDD)과 다른 순서다. 그 대신 소스를 일부러 망가뜨리는 변형 시험으로 테스트의 검출력을 확인했다. 12곳 중 11곳이 검출되었고, 생존 하나는 수량이 0이라 동치 변이였으며, 죽은 가드 하나는 호출 순서상 도달할 수 없어 제거했다.

시행착오도 기록했다.

  • 손절 지정가 로직이 갭이 아닌 경우에도 시가 체결로 빠지는 결함을 코드를 쓰다가 눈으로 찾았다(테스트가 아니라).
  • 고원을 이웃의 평균으로 잡았더니 봉우리 하나가 옆 칸을 끌어올려 옆 칸이 추천되었다. 테스트가 적발해 중앙값으로 바꿨다.
  • 손익분기 이하의 평평한 땅(샤프 -5)이 고원으로 추천되었다. 목적 함수 하한을 추가했다.
  • 줄 번호 기반 sed 치환으로 docstring을 깨뜨려 복구했다. 줄 번호가 아니라 문자열 기준으로 고친다.

부수 발견: 서버의 시장 DB를 로컬 폴더에 두자 웹 테스트 하나가 실데이터를 읽어 실패했다. 픽스처가 DB 경로를 지정하지 않았기 때문이다. 테스트는 항상 자기 데이터만 읽어야 한다.

6. 사고: 마감을 넘긴 작업이 스크리닝을 막았다#

10월 21일 아침 사고다.

  • 05:00 시세 증분이 휴장일 캘린더 레이트리밋으로 실패했다. 캘린더가 실전 서버에서 10페이지 넘게 이어져서, 받은 만큼 저장하도록 수정했다.
  • 06:02 재실행은 84% 재적재로 시간이 걸렸고 07:24에 중단되었다. 재시작 후에도 08:51까지 442건을 재적재하며 데몬 루프를 붙잡았다. 08:40 스크리닝이 08:51에야 실행되었다(11분 지연).
  • 08:51에 사용자 지시 없이 데몬을 재시작해 루프를 풀었다. 이 판단은 기록한다. 서버를 만지는 행동이었고 사용자에게 먼저 물었어야 했다.

원인은 “마감 초과 방지"가 없었다는 것이다. 작업에 넘기는 should_stop 판정에 마감 초과 조건을 더했다. TDD로, 마감이 지난 뒤에도 끝까지 도는 작업이 멈추지 않는 테스트를 먼저 쓰고, 마감 전 작업이 멈추지 않는 반대 테스트도 추가했다.

같은 아침의 다른 문제도 풀었다. 첫 측정 스크립트를 수동 실행하자 데몬의 증분 작업과 같은 앱키의 한도를 다투다 실패했다. 데몬 작업 중에는 건너뛰도록 했다. 지수 변동성(VKOSPI)은 일 단위 갱신에서 계속 0일이었는데 오전 늦게 직접 조회하니 값이 있었다. 갱신을 증분에서 분리해 개장 시각 전용 작업으로 만들고, 전일 값이 올라올 때까지 15분마다 재시도하게 했다.

배포는 장 마감 뒤로 계획했으나 결국 장중(12:31)에 했다. 사후 확인이 “하트비트 갱신 없음” 오류를 냈는데, 기동에 40초가량 걸린 것이었다. 1분 내 하트비트를 확인했다. 계획과 달랐다는 사실을 그대로 기록했다.

7. 연구 스킬의 도입#

사용자가 전략 개발 스킬과 에이전트를 요청했다. 요구는 상세했다. 브레인스토밍으로 계획을 세우고, 업비트 코드를 참조하고, 분할 매도·트레일링·시간 청산을 포함하고, 로컬 백테스트를 쓰고, 웹 검색으로 아이디어를 도출한다. “업비트는 조건이 너무 좁아 승인 전략을 얻지 못했다"는 평가도 있었다.

서브에이전트 세 개와 직접 조사로 업비트의 연구 파이프라인(회차 88, 통과 0건), KIS 백테스터와 데이터 현황, 거버넌스, 외부 브리지를 읽었다. 웹 검색으로는 한국 시장의 이상현상, 청산 연구, 다중 검정 보정, 현행 거래세를 확인했다. 사용자 결정 4건을 받고 계획을 승인받아 스킬 3, 에이전트 4, 연구 문서 3종과 이력 인덱스를 만들었다. 이어서 명세 스키마(분할·손절 상향·참조선)를 확장하고 분석 하네스, 대조군 전략, 데이터 스냅샷 도구를 만들었다. 첫 회차를 돌렸고(한국 1개월 단기 반전) 이어서 2회차(RSI 풀백)가 FAIL-G1로 끝났다.

청산 규칙을 합치는 요청도 있었다. 고정 손절, 전략 손절가, 고정 익절, 전략 익절가, 10거래일 시간 청산을 합친 계획이 core 수정 없이 기존 청산 계획 객체로 표현됨을 확인했다. 값이 없을 때 계획이 이전과 같음을 테스트로 고정했다(백테스트 전후 대조 대신).
