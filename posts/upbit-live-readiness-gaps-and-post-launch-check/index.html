자동매매 Bot 전환 및 개발 · Upbit (5) — 실거래 개시 전 운영 공백을 메우고, 개시 후 첫 로그를 점검하다

백테스트 기준을 통과하지 못한 채 소액 실거래를 시작하기까지 이틀. 전략 코드가 아니라 운영 공백(손실 한도, 실체결가, 로깅, 락, 알림, cron 환경)을 감사해 메우고, 개시 직후 서버 로그에서 배포 스크립트의 오탐과 실제 버그를 가려낸 과정을 정리한다.

들어가며#

7월 11~12일의 백테스트로 전략 후보들은 실거래 전환 기준(수익 팩터·최대 낙폭)에 미달한다는 결론이 나와 있었다. 그런데 이 프로젝트에는 한 가지 특수한 사정이 있다. 업비트에는 증권사의 모의투자 서버 같은 중간 단계가 없다. 안전하게 미리 검증할 수 있는 수단은 백테스트뿐이고, 크론 등록이 곧 실거래 개시다.

이 글은 7월 12~13일, “전략은 아직 기준 미달이지만 소액으로 라이브를 시작하겠다"는 결정이 내려지기 전후에 코드가 실제로 운영 가능한 상태인지를 감사하고, 개시 후 첫 로그를 읽은 기록이다.

1. 운영 공백 감사: 전략이 아니라 주변부#

“전략을 운영할 수 있게 부족한 것을 찾아 달라"는 요청이 시작이었다. 실제 자본을 염두에 둔다는 전제를 먼저 확정하고, 라이브 컴포넌트 10개를 조사해 진짜 코드 공백 4건을 추렸다.

공백 해결
일일 손실 한도 없음 하루 실현 손실이 한도를 넘으면 신규 진입만 차단하는 회로 차단기. 킬 스위치와 같은 위치(유니버스 구성 이전)에서 확인
체결가를 주문가로 추정 주문 후 체결 내역을 재조회해 체결량 가중평균으로 실체결가 계산
공포 게이트가 항상 통과하는 스텁 크론은 무상태 제약이 있어서, 매 사이클 과거 데이터를 다시 조회해 변동성 이력을 재구성하는 방식으로 실배선
스테이블코인 제외 목록이 미검증 실제 마켓 목록과 시세를 조회해 사라진 항목 제거, 새로 상장된 것 추가

체결가 처리에서는 두 가지 실패를 구분했다. 조회에 성공했는데 미체결이면 거래를 기록하지 않는다(유령 포지션 방지). 조회 자체가 실패하면 주문가로 잠정 기록하고 오류 로그를 남긴다. 추적이 누락되는 것보다 잠정치가 안전하다는 판단이다.

2. 로깅: 로그가 파일에 남지 않고 있었다#

운영 점검을 하다 가장 놀란 공백이다. 코드의 로그 호출은 이미 “이벤트 key=value” 형태로 잘 쓰여 있었는데, 파일 핸들러 설정이 어디에도 없었다. 크론으로 실행하면 로그가 전부 사라지는 상태였다.

크기 기준 로테이션 파일 핸들러와 콘솔(경고 이상) 핸들러를 만들고, 시각을 한국 시간으로 명시 변환하는 포매터와 전략 ID 필터를 붙였다. 기존 호출부는 한 곳도 고치지 않았다. 메시지 규약이 이미 맞아 있었기 때문이다.

개발 PC(Windows)에는 시간대 데이터베이스가 없어서 시간대 객체 생성이 모듈 import 시점에 실패했다. 기존 테스트는 고정 오프셋으로 우회하고 있었는데, 새 모듈은 프로덕션 코드가 직접 시간대를 만들어서 우회가 통하지 않았다. 이 문제는 최소 구성 리눅스 이미지에서도 생길 수 있어서, 우회가 아니라 시간대 데이터 패키지를 의존성에 추가하는 쪽으로 해결했다.

이어서 로그 레벨을 환경 변수로 뺐다. 그런데 코드 전체에 디버그 로그 호출이 단 1건뿐이었다. 레벨만 올려도 늘어날 내용이 없다는 뜻이다. 그래서 전략 코드는 부작용 없는 순수 함수로 유지하는 원칙에 따라 전략은 건드리지 않고, 모든 전략이 거치는 스케줄러 호출 지점 네 곳에 판단 근거(후보 점수, 진입·청산 여부와 이유)를 디버그로 남기게 했다.

3. 크론 환경이 만든 함정들#

락 파일이 전략 전체를 막는 구조#

크론 문서를 쓰다가 락 경로가 전략과 무관한 공유 파일임을 발견했다. 설계상 두 전략의 4시간 사이클은 정확히 같은 시각에 실행된다. 공유 락이면 먼저 잡은 쪽만 일하고 나머지는 조용히 사이클 전체를 건너뛴다. 재시도도 없다. 락 파일을 전략 ID별로 분리했다. 같은 전략의 가드와 사이클은 여전히 같은 락으로 직렬화된다.

크론은 .env를 읽지 않는다#

프로그램 본체는 환경 변수를 직접 읽을 뿐 .env 파일을 읽지 않는다. 크론은 셸 프로필도 로드하지 않는다. 그래서 .env를 불러온 뒤 본체를 실행하는 래퍼 스크립트와, 재부팅 시 헬스체크를 하는 스크립트를 만들었다.

예외가 아무에게도 가지 않는 문제#

크론의 메일 전송을 꺼 둔 상태라, 실행 중 예외가 나면 알아챌 방법이 없다. 텔레그램 알림을 배선하면서 최상위 실행부를 예외 종류별(차단 응답, API 오류, 기타) 3단으로 감싸 오류 로그와 알림을 남기고 정상 종료하게 했다. 알림 모듈은 전송 함수를 주입받아 네트워크 없이 테스트한다.

4. “paper 모드” 전제가 틀렸다#

알림을 배선하다 이상한 점을 발견했다. 실행 인자의 모드 값과 무관하게 항상 진짜 API 클라이언트를 주문 객체로 쓰고 있었다. 모드는 DB 기록용 라벨일 뿐이었다. 즉 paper라고 적어도 실제 키가 있으면 실주문이 나가는 구조였다.

이 공백을 알린 직후 사용자의 정정이 왔다. “업비트에는 paper 모드가 없다. 운영은 live와 backtest 둘뿐이다.” 코드 버그가 아니라 “paper가 안전한 중간 단계"라는 문서 쪽 전제 자체가 틀렸던 것이다. 코드는 그대로 두고 문서를 정정했다. 모의 서버가 없다는 사실을 설치 문서에 박스로 명시하고, 크론 예시의 모드 표기를 실제 동작과 일치시켰다. 안전장치는 “합격 전에는 크론을 등록하지 않는다"는 절차 하나뿐이라는 점도 문서화했다.

5. 전략 개명과 부수 발견#

효과가 없던 구 전략을 삭제하고, 그 자리에 후속 전략을 번호만 바꿔 승계시켰다. 코드를 지우고 폴더를 옮기는 단순한 작업이었는데, 그 과정에서 숨은 버그가 나왔다. 실행 진입점이 애초에 후속 전략 모듈을 import한 적이 없어서, 크론에서 그 전략 ID로 실행하면 레지스트리 조회가 실패했을 것이다. 개명으로 우연히 해소되었다. 이름 정리 작업이 이런 잠재 결함을 드러내기도 한다.

6. 기준 미달 상태에서 실거래를 시작한다는 결정#

크론 등록이 곧 실거래 개시이고, 후보 전략 모두 합격 기준에 못 미친다는 사실을 안내하고 확인을 받았다. 사용자는 위험을 알고 소액으로 시작하기로 했다. 이 결정을 문서에 “사용자가 위험을 알고 감수한 결정"이라고 명확히 기록했다. “기준을 통과했다"는 기록과 섞이면 나중에 근거가 흐려지기 때문이다. 전략을 한 번에 둘 다 켜지 말고 하나씩 먼저 검증하길 권했다.

7. 개시 후 첫 로그 점검#

크론을 등록한 뒤 서버 로그를 받아 점검했다.

  • 개시 직후 몇 번의 CRITICAL/ERROR는 모두 그날 오전에 고친 과거 캔들 조회 버그(조회 시각 파라미터에 마이크로초가 포함되어 400 응답)가 서버에 반영되기 전의 실행분이었다. 이 버그는 가드와 사이클이 매번 조용히 실패하고 있던 실제 운영 결함이었고, 서버 반영 이후에는 모두 정상이었다.
  • 텔레그램 전송이 처음 두 번 실패한 뒤 자연히 정상화되었다. 원인은 불명이고 재발이 없어 관찰 항목으로 남겼다.
  • 배포 스크립트가 DB 무결성: corrupt를 경고했다. 실제로는 서버에 sqlite3 명령행 도구가 설치되지 않아서 command not found가 난 것이었다. 스크립트가 두 경우를 구분하지 못하고 모두 “손상"이라 표시했다. 도구 없음과 실제 손상을 구분하도록 수정했다. 실거래 중 DB 손상 오경보는 특히 위험하므로 바로 고쳤다.

그 전날의 배포 실패도 같은 계열이었다. 새로 추가한 웹 폼 기능이 요구하는 의존성 패키지가 requirements.txt에서 빠져 있었다. 개발 환경에는 다른 경로로 이미 설치돼 있어서 어떤 테스트에서도 드러나지 않았다. 패키지를 제거해 오류를 재현하고, 의존성 파일에 추가한 뒤 재설치해 해소를 확인했다.

또 하나, 스크립트 실행 권한 비트가 커밋되지 않아 매 배포마다 로컬 변경이 생기고, 배포 스크립트의 안전검사를 영구히 막고 있었다. 권한 비트를 저장소에 반영해 해결했다.

정리#

영역 발견 조치
안전 일일 손실 한도 없음 신규 진입 차단 회로 차단기
데이터 체결가 추정 체결 내역 재조회로 실체결가
관측 로그 파일 미기록 파일 핸들러, 레벨 외부화, 판단 근거 로그
동시성 전략 간 공유 락 전략별 락
환경 크론이 환경을 모름 래퍼 스크립트
문서 “paper 먼저” 전제 오류 문서 정정
배포 오탐 경고, 의존성·권한 누락 스크립트 수정

배운 점: 전략이 아무리 좋아도 주변부가 비어 있으면 운영은 시작할 수 없다. 손실 한도, 실체결가, 로그, 락, 알림 같은 항목은 전략 코드가 아니라 운영 코드의 일이다. 그리고 “개발 환경에서는 우연히 되는 것"이 가장 늦게 드러난다. 의존성 누락, 시간대 데이터, 실행 권한은 모두 개발 PC에서 통과하고 서버에서 터졌다. 배포 후 첫 로그를 읽는 습관이 이 둘을 가장 빨리 잡는다.
