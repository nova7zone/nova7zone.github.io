자동매매 V2 개발 · Upbit (3) — 막힌 연구를 뚫으려고 체결 흐름을 상시 기록하는 인프라를 만들다

봉 데이터만으로는 새 후보가 나오지 않는다는 결론에서, 체결 흐름(order flow)을 1분 단위로 상시 기록하는 인프라를 데몬에 얹었다. 설계 가정이 틀렸음을 구현 계획 단계에서 SDK 소스로 발견한 일, 최종 리뷰가 잡은 디스크 고갈 위험, 백업 보관 정책의 구조적 결함과 서버 실측 검증까지 정리한다.

들어가며#

연구 8회차까지 봉(candle) 기반 후보는 거의 소진되었다. 탐색 에이전트의 결론은 “막힌 것을 뚫는 길은 문헌이 아니라 새 데이터“였다. 사용자는 체결 흐름(어느 쪽이 공격적으로 사고팔았는지 부호가 붙은 체결 기록)을 상시 기록하는 인프라를 만들기로 확정했다. 과거 체결 흐름은 구할 수 없으므로 지금부터 쌓아야 나중에 쓸 수 있다.

1. 설계: 입자, 범위, 위치를 정한다#

기획(brainstorming) 질문 세 개로 설계를 확정했다.

질문 결정
저장 입자 1분 집계 버킷 (틱 원본은 저장하지 않는다)
수집 범위 전체 원화 마켓 유니버스
실행 위치 기존 데몬에 통합 (별도 프로세스를 만들지 않는다)

거래소의 체결 틱 조회는 초당 10회 제한이 있다. 그래서 종목을 순환하며 배치로 조회한다(틱당 15종목, 전체 한 바퀴 약 37초). 각 종목은 sequential_id를 커서로 저장해 유실 없이 이어받는다.

2. 구현 계획에서 설계 가정이 깨졌다#

구현 계획을 쓰는 동안 실제로 설치된 SDK의 소스를 열어 보았다. 설계 문서의 핵심 가정은 “커서가 앞으로 이어지는 forward-continuation“이었는데, 실제 커서는 뒤로 거슬러 가는(backward) 방식이었다. 이 가정으로 구현했다면 누락 구간을 메우는 알고리즘 전체가 틀렸을 것이다.

같은 시점에 규약 위반도 하나 정정했다. 매 틱 로그를 남기는 것은 로깅 규약에 어긋나서 DEBUG로 내렸다.

교훈은 단순하다. 설계 단계의 외부 API 가정은 구현 전에 소스나 실측으로 한 번 더 확인한다. 설계 승인은 가정이 맞다는 보증이 아니다.

3. 서브에이전트로 8개 태스크, 그리고 최종 리뷰#

구현은 8개 태스크를 TDD로 서브에이전트에게 맡겼다.

  1. DB 스키마
  2. 클라이언트의 체결 틱 조회와 데이터 타입
  3. 순수 함수 (버킷 집계, 배치 회전)
  4. 저장소 계층
  5. 수집 오케스트레이션 (증분 폴링, 누락 구간 메우기)
  6. 설정
  7. 틱 루프 배선
  8. 메인 실배선

태스크별 리뷰는 모두 통과했다. 마지막 태스크는 세션 사용량 한도로 구현 에이전트가 중간에 멈췄고, 두 번째 에이전트가 이어받아 끝냈다(코드 결함이 아니라는 것을 재검토로 확인했다).

최종 브랜치 리뷰가 잡은 것#

가장 강한 모델로 한 번 더 전체를 리뷰했더니 태스크별 리뷰가 놓친 것이 나왔다.

  • 치명(Critical): 1분 집계 테이블이 무제한으로 증가한다. 배포 직전 서버 상태(디스크가 이미 부족했던 이력)와 연결 지어 발견했다. 보관 기간 정리 로직이 필요했다.
  • 중요(Important) 3건: 요청 제한 수치의 문서·코드 불일치, 418(차단)과 인증 예외가 삼켜지는 것, 비원자적 쓰기로 크래시 시 이중 집계가 될 수 있는 것.

전부 하나의 수정 묶음으로 고치고 범위를 좁힌 재검토로 깨끗함을 확인했다. 신규 테스트는 45건이다. 이 결정과 구현 중 정정 5건, 리뷰 정정 4건을 모두 결정 문서에 기록했다.

4. 같은 날의 실제 사고: 디스크 91%#

설계 승인 직후 사용자가 서버 디스크 사용량이 91%라고 알려 왔다. 원인은 백업 폴더(수 GB)였다. 이미 30일 기준의 보관 정책이 있었지만, 배포 테스트를 하루에 여러 번 돌린 날에는 중복 백업이 쌓였고 30일이 지나기 전까지 무한히 늘어나는 구조였다. 시간 기준의 보관 정책은 쓰기 빈도가 높은 날에 무력하다.

데이터 본체(살아 있는 DB와 WAL 보조 파일)는 절대 지우면 안 된다고 먼저 안내했다. 정리 대상은 백업 폴더뿐이다. 사용자 요청으로 보관 정책을 DB별 최신 N개 유지(개수 기준, 기본 3, 환경 변수로 조정)로 바꿨다. 합성 파일로 삭제 대상 목록만 출력해서 로직을 확인했다. 배포 후 여유 공간이 4.3GB에서 9.6GB로 회복되었고, 배포 자체가 만든 신규 백업에도 정책이 정상 동작했다.

5. 배포 후 실측 검증과 점검 스킬#

데이터는 배포되어야 쌓인다. 배포 후 확인 절차를 매번 말로 설명하지 않도록 점검 스킬(server-check)을 만들었다. 절차는 헬스체크 → 서비스 로그의 필수 이벤트와 CRITICAL 확인 → 시장 DB를 로컬로 가져와 수집 테이블 실측 → 이상 시 조정표 → 요약 보고 순서다.

이 스킬로 처음 서버 접속을 실제로 실행했다. 접속 설정이 의외로 오래 걸렸다(약 한 시간). 막힌 지점 세 곳은 서비스 관리자 권한, 파일 권한, 셸 변수 보간이었고, 그 뒤에도 Git Bash의 ssh가 Windows 네이티브 에이전트를 읽지 못하고 설정의 IdentitiesOnly가 에이전트 키 사용을 막는 문제가 있었다. 네이티브 ssh를 전체 경로로 호출하는 방식으로 우회했고, 같은 시행착오를 반복하지 않도록 이 내용을 저장소 문서(스킬 §0)에 명시했다. 개인 메모리가 아니라 커밋된 문서에 둔 이유는 다른 머신에서도 바로 참고할 수 있게 하기 위해서다.

실측 결과:

  • 헬스체크 전 항목 통과, CRITICAL 0건
  • 전체 유니버스 283종목 중 283종목 정상 수집 (커서 전부 1분 이내 갱신)
  • 마켓별 수집 실패 0건, 저유동성 마켓의 누락 미복구 1건은 설계대로의 정상 동작

배포 후 약 31시간 데이터로 실제 증가율을 재서 보관 기간을 30일에서 180일로 상향했다(하루 약 10MB 증가, 180일이어도 디스크의 20% 이하). 보수적으로 잡은 숫자는 실측으로 고친다.

6. 같은 날, 연구 방향 상담 세 건#

데이터를 기다리는 동안 연구 방향 상담이 있었다. 모두 코드 변경 없이 근거 문서로 답했다.

  1. “유동성과 무관한 다른 전략은 가능한가” → 분류 9개 전체가 봉인되었거나 문헌·데이터가 소진된 상태. 닫힌 고리다.
  2. “봉인 정책을 완화할 수 있는가” → 봉인 횟수 기준에 별도 유도 근거는 없고 초기 판단값이다. 그러나 결과가 안 나온다고 규칙을 푸는 것은 사후 스누핑과 구분되지 않는다. 실행하지 않았다.
  3. “볼린저+스토캐스틱+RSI 과매도 확인 매수” → 같은 메커니즘이 이미 두 번 시도되어 기각되었다. 지표 AND 대신 가중 점수화는 희소성 문제만 피할 뿐 메커니즘은 같아서 봉인이 그대로 적용된다. 봉인이 풀릴 때 참고할 아이디어로만 기록했다.

정리#

항목 내용
목적 봉 데이터로는 안 나오는 후보를 새 데이터로
설계 정정 커서 방향 가정이 반대였음을 SDK 소스로 발견
리뷰 최종 리뷰가 디스크 무제한 증가·예외 삼킴·비원자 쓰기를 포착
운영 백업 정책을 시간 기준에서 개수 기준으로
검증 283/283 종목 수집, 보관 180일로 상향

배운 점: 새 데이터 수집 인프라는 코드가 아니라 쌓이는 시간이 비용이다. 그러므로 배포가 늦어지는 만큼 데이터가 사라진다. 그래서 리뷰를 강하게 하고(디스크, 예외, 원자성), 배포 후 곧바로 실측으로 확인하는 것이 중요했다. 그리고 규칙을 풀어 달라는 요청에는 “풀면 사후 스누핑과 구분되지 않는다"는 이유를 문서 근거로 설명하는 것이 가장 정직한 답이었다.
