들어가며#

이전 글에서 매시간 재선정을 구현하고 메인 전략을 v3로 전환했다. 새 전략 엔진이 실거래에 들어가기 전, 문서를 정리하고 정식 버전을 릴리즈하는 마무리 작업이 이어졌다.

결론부터 말하면, docs/STRATEGY_V3_trading_flow.md를 신규 작성하고 기존 12개 문서에 v3 내용을 반영했다. v0.6.4 이후 머지된 PR 7건을 정리해 v0.7.0(minor)을 릴리즈했다. 그 직후 v3 로그가 trader.log에 전혀 남지 않는다는 것과, 날짜 계산 방식이 서로 다른 두 테스트가 타임존 경계에서 우연히 통과하고 있었다는 것도 함께 발견해 고쳤다.

docs 전면 최신화 (PR #84)#

  • docs/STRATEGY_V3_trading_flow.md 신규 작성 — v1/v2와 동일한 공통 메타 양식으로 그룹 정규화 스크리닝·목표가 3모드·매시간 재선정을 요약
  • CLAUDE.md의 “Strategy V3 개발 규칙” 섹션을 strategy_v3/specs/DEVELOPMENT_SPEC.md로 분리(v1/v2와 동일 패턴), CLAUDE.md에는 참조만 유지
  • 루트 README.md — 전략 버전 2종→3종 반영, strategy_v3 서브섹션 신설, 프로젝트 구조·상세 문서 표 갱신
  • 기존 docs/*.md의 v1/v2 전용 서술에 v3 반영(APP_SETTINGS/SETTINGS_GUIDE/CONDITIONS_GUIDE/WORKFLOW/TESTING_GUIDE/OCI_QUICKSTART/INSTALL/UPDATE/AI_CODE_SAFETY_CHECKLIST/HOW_TO_ADD_CONDITION_V1·V2/SETTINGS_REFERENCE)
  • 문서 간 링크·앵커(fragment)를 전수 검증 스크립트로 점검한 뒤 누락된 상호참조를 수정(BACKTEST_DATA_GUIDE.md 중복 “관련 문서” 섹션 정리, USAGE.md 공통메타 도입 + docs/README.md 인덱스 신규 등록 등)

코드 변경은 없었고(문서 전용), pytest tests/ 영향도 없었다.

v0.7.0 릴리즈#

v0.6.4 이후 merge된 PR #78~#84(strategy_v3 신규 구현 → 웹 대시보드 통합 → Critical 버그 3건 수정 → 매시간 재선정 → 메인 전략 전환 → 문서 갱신) 기준으로 release-notes-draft-v0.7.0.md를 작성했다. minor 버전으로 결정했다 — 신규 전략 엔진 구현 + 메인 전략 전환이라는 기능 추가 성격에 따라 v0.6.5(patch) 대신 v0.7.0으로 사용자가 확정했다.

git tag v0.7.0(origin/master HEAD 34e2cc7, 이전 태그와 동일한 lightweight 태그 방식) → git push origin v0.7.0 → gh release create로 정식 GitHub Release를 발행했다. GitHub 정식 릴리즈 노트 본문의 “# v0.7.0 (draft)” 헤더에서 “(draft)“를 제거(gh release edit --notes-file)했다 — 로컬 draft 파일명·본문은 관례대로 “draft” 표기를 유지하고, GitHub 상 정식 발행본만 draft 문구를 제거하는 패턴을 계속 지켰다.

trader.log에 v3 로그가 안 남던 버그#

로그 레벨 동작 방식을 사용자에게 설명하던 중, utils/logger.py의 _TRADING_LOGGER_PREFIXES에 strategy_v3.trading/strategy_v3.screening이 빠져 있는 것을 발견했다. v3 매수/매도/스크리닝 로그가 logs/trader.log에 기록되지 않고 콘솔(cron.log)에서만 확인 가능했던 문제다. daily_reeval.py는 strategy_v2.daily_reeval로 로거 이름이 고정(버전 분기 방식)돼 있어 이미 필터를 통과하고 있어서 별도 수정이 필요 없음을 확인했다.

  • utils/logger.py: _TRADING_LOGGER_PREFIXES에 v3 prefix 2개 추가

타임존 경계에서 흔들리던 date rot 테스트#

이어서 PostToolUse pytest 훅이 tests/test_v3_strategy_sell.py::test_min_hold_days_blocks_strategy_trigger 실패를 보고했다. systematic-debugging 절차로 근본 원인을 확인했다.

entry_date="2026-06-30"을 하드코딩하고 “오늘"로 가정했는데, 실제 날짜가 2026-07-02로 넘어가면서 hold_days가 2로 계산돼 min_hold_days=2 가드를 통과 못하고(2 < 2 = False) score_drop 트리거가 발동하고 있었다. 같은 파일의 다른 테스트들은 이미 datetime.date.today() - timedelta(...) 동적 계산 패턴을 쓰고 있었는데, 이 테스트만 절대 날짜를 하드코딩한 date rot 버그(V2_LESSONS_LEARNED.md BUG-09류)였다.

  • tests/test_v3_strategy_sell.py: entry_date를 datetime.date.today().isoformat()로 동적 계산하도록 수정

그런데 PR #81 CI에서 같은 파일의 다른 두 테스트가 새로 실패했다. 이 역시 근본 원인은 date 경계 불일치였다. 테스트가 datetime.date.today()(서버 로컬/UTC)로 entry_date를 계산하는데, production 로직(_hold_days())은 now_kst()(KST 명시)로 경과일을 계산한다 — UTC 15:0023:59(KST 자정08:59) 구간에 CI가 실행되면 두 “오늘” 날짜가 하루 어긋나 경계값 테스트(hold_days_limit - 1, half - 1)가 뒤집혔다. 방금 위에서 넣은 수정도 같은 결함을 안고 있어서 함께 수정해야 했다.

  • tests/test_v3_strategy_sell.py: 5곳 전부 datetime.date.today() → now_kst().date()(utils.time_utils)로 통일 — production과 동일한 타임존 기준으로 “오늘"을 계산하도록 수정

pytest tests/test_logger.py tests/test_v3_strategy_sell.py 통과를 확인했다. production 매매 로직 변경은 없었다(로그 필터 설정 + 테스트 date rot 수정).
