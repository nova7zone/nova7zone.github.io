자동매매 Bot 전환 및 개발 · Upbit (4) — 라이브 코드를 그대로 재생하는 백테스트 엔진

백테스트용 로직을 따로 만들지 않고, 운영 스케줄러가 쓰는 실행 경로에 가짜 증권사(SimBroker)만 끼워 넣어 과거 데이터를 재생하는 엔진을 만든 과정. import 규칙 검사기가 조건부 import까지 잡아낸 일, 미래 데이터 누수를 막는 캔들 합성 방식을 정리한다.

들어가며#

전략 이식이 끝나자 다음 단계는 백테스트였다. 실거래로 넘어가기 전에 “이 전략이 과거 데이터에서 어떻게 움직이는가"를 확인해야 한다. 그런데 백테스트 코드를 따로 만들면 늘 같은 문제가 생긴다. 백테스트에서 검증한 코드와 실제로 도는 코드가 달라진다. 기존 KIS 쪽에서 “same-code” 원칙(검증과 운영이 같은 코드를 쓴다)을 세워 두었기 때문에, 이번에도 그 원칙을 그대로 승계했다.

규모가 커서 바로 코드를 쓰지 않고 먼저 계획을 세웠다. 저장소 구조(레지스트리, 리스크, 설정)를 한 번 훑어 사실관계를 확인하고, 설계 초안을 만든 뒤 직접 검토·수정해 최종 계획을 확정했다. 그리고 엔진 골격(1단계)과 실데이터 수집·실행 스크립트(2단계)를 나누어 만들었다.

1. 핵심 발견: 새로 만들 게 거의 없었다#

운영 스케줄러의 단계 실행 함수는 이미 필요한 의존성(계좌 조회, 포지션 조회, 가격 조회, 주문 등)을 주입받는 구조로 일반화되어 있었다. 그렇다면 리플레이 엔진은 사이클 로직을 다시 구현할 필요가 없다. 가짜 증권사로 채운 의존성 묶음을 만들어서 같은 실행 함수를 시간 순서대로 반복 호출하면 된다.

이 판단으로 설계가 단순해졌다.

  • 백테스트 전용 진입·청산 로직: 없음 (운영 코드 재사용)
  • 새로 만드는 것: 가짜 증권사 쪽 부품들과 시간을 흘려보내는 드라이버

계좌·포지션·가격 조회 팩토리가 비공개(언더스코어) 함수였는데, 백테스트가 재사용할 공유 유틸리티로 이름만 공개로 바꿨다. 동작은 바꾸지 않은 순수한 이름 변경이다.

2. 만든 부품 (TDD, 테스트 먼저)#

부품 역할
인메모리 원장 거래소의 계좌 응답과 같은 모양으로 잔고를 흉내 낸다
가짜 주문 API 진입은 주문가(+슬리피지)로 체결, 청산은 운영과 같은 시세 원천을 콜백으로 받아 체결
데이터 제공자 과거 캔들을 운영의 캔들 제공자 인터페이스로 감싸 경계 검증과 빈 구간 채우기를 재사용
공포 게이트 재생 기존 순수 함수를 그대로 써서 게이트를 조립, 지수 조회에서 미래 항목은 제외
드라이버 리플레이 루프 오케스트레이션
리포트 수익 팩터, 낙폭, 승률, 국면별 분리 집계

청산 체결가를 운영과 같은 시세 원천에서 가져오게 한 이유가 있다. 원장의 잔고와 레지스트리의 손익 계산이 서로 다른 가격을 쓰면 두 숫자가 어긋난다. 운영에서 이미 겪은 종류의 불일치라서 처음부터 같은 출처로 묶었다.

미래 데이터 누수 방지#

가장 신경 쓴 부분은 룩어헤드(미래를 미리 보는 오류)였다. 새 4시간 창이 열린 시점에는 그 봉의 시가만 알 수 있다. 그래서 가장 최근 캔들은 “새 창의 시가"만으로 합성하고, 고가·저가·종가는 숨긴다. 진입 판단이 아직 닫히지 않은 봉의 값을 보지 못하게 하는 장치다.

봉 안에서의 손절 판정은 보수적으로 했다. 보유 포지션 전체를 저가 기준으로 먼저 확인하고, 살아남은 것만 고가 기준으로 다시 확인한다. 같은 봉 안에서 고가와 저가 중 무엇이 먼저였는지 알 수 없을 때, 불리한 쪽부터 가정하는 방식이다.

3. import 규칙 검사기가 잡아낸 것#

이 프로젝트는 의존 방향을 import 규칙 검사기로 강제한다. 코어는 전략 폴더를 import하면 안 된다. 드라이버는 전략 객체가 필요하지만, 호출자가 주입하게 하면 import 없이 해결된다.

처음에는 타입 힌트만 쓰려고 TYPE_CHECKING 가드 안에서 전략 타입을 import했다. 실행 시점에는 import되지 않으니 괜찮다고 생각했다. 그런데 검사기는 조건부 import도 정적 분석 대상으로 보고 위반으로 잡았다. 실제로 실행해서 확인한 사실이다. 결국 타입 힌트를 Any로 바꿔 해소했다.

작업 초반에는 반대 방향의 예방도 했다. 본격적으로 쓰기 전에 빈 스텁 파일로 “백테스트 → 스케줄러 → 전략” 같은 간접 경로가 기존 예외 설정으로 억제되는지 먼저 돌려 봤다. 구조 규칙은 코드를 다 쓴 뒤보다 뼈대 단계에서 확인하는 편이 되돌릴 일이 적다.

4. 2단계: 실데이터 수집과 실행 스크립트#

엔진이 있어도 먹일 데이터가 없으면 소용이 없다.

  • 과거 캔들 수집 모듈: 거래소 API의 to 파라미터로 한 페이지씩 과거로 거슬러 올라가며 다년치 4시간봉을 모은다. 페이지 경계의 캔들이 중복 조회되지 않게 한 봉 앞에서 끊고, 페이지마다 경계 검증을, 전체 수집 후 빈 구간 채우기를 적용한다. 로컬 JSON 캐시를 두어 같은 구간을 다시 받지 않는다. 운영 경로(최신 N개 조회)는 건드리지 않고 별도 모듈로 분리했다.
  • 실행 스크립트: 실제 전략을 import해 드라이버를 조립하는 최상위 진입점이다. 저장소 루트에 두어서 import 규칙의 검사 범위 밖에 놓고, 코어가 전략을 모른다는 1단계 설계를 지켰다. 조립 로직은 main()에서 분리해 네트워크 없이 배선만 단위 테스트한다. 마켓 목록을 직접 지정하면 생존 편향이 생길 수 있다는 점은 사용 설명에 명시했다.
  • 공포 게이트의 기여도를 보는 옵션도 넣었다. 게이트를 켠 실행과 변동성 단독 실행을 두 번 돌려 차이를 비교하는 단순한 방식이다. 개별 후보를 반사실로 재현하는 복잡한 구현은 하지 않았다.

정리#

단계 결과
1단계 운영 실행 경로에 가짜 증권사를 끼우는 리플레이 엔진, 신규 테스트 29건
2단계 과거 캔들 수집·캐시, 실행 스크립트, 신규 테스트 9건

배운 점: 백테스트 엔진을 만들 때 가장 값진 결정은 “무엇을 새로 만들까"가 아니라 “무엇을 만들지 않을까"였다. 운영 코드가 이미 의존성 주입 구조라서 엔진은 얇은 어댑터 몇 개로 끝났고, 검증과 운영이 같은 코드를 쓴다는 보장도 구조적으로 얻었다. 그리고 구조 규칙 검사는 조건부 import까지 본다는 것을 기억해 둘 만하다. 다음 글에서는 이 엔진으로 첫 전략을 실제로 재생해 보고 엔진 자체의 버그를 발견한 이야기를 다룬다.
