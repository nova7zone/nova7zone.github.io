자동매매 V2 개발 · KIS (3) — 일봉 이력 확장, 모의투자 대시보드, 그리고 병렬 에이전트 7개로 한 전체 코드 리뷰

주말마다 일봉 이력을 늘리는 데몬 작업, 새로고침 기준으로 전략별 성과를 보는 모의투자 화면과 자동 갱신, 홈 화면 설치용 PWA를 만들었다. 저장소 전체를 읽기 전용 에이전트 7개로 병렬 리뷰해 High 15건을 TDD로 고친 과정과, 사용자 질문 한 줄로 연구 설계의 학습/검증 비율을 결과를 보기 전에 폐기하고 다시 사전등록한 일을 정리한다.

들어가며#

10월 22일부터 26일까지의 기록이다. 공통 주제는 “눈으로 확인할 수 있게 만들고, 확인한 것을 바로 고친다"이다. 네트워크 구성이나 계좌 정보는 다루지 않는다.

1. 일봉 이력을 주말에 늘린다#

연구에는 더 긴 이력이 필요했다. 일봉 이력 확장은 KIS 호출 규모로 약 2만 회가 필요해서 모의 서버의 일일 상한을 넘는다. 그래서 주말 이틀에 나누어 데몬 작업으로 돌리기로 했다.

  • 거래대금 순으로 종목을 처리한다. 실행 예산, 종료 시각, 연속 실패 중단 조건을 둔다.
  • 제한기의 일 카운터가 24시간 슬라이딩 창이라 ‘하루 예산’을 ‘실행당 증가분 + 창 상한’ 둘로 나눴다.
  • 상태표에 진행을 기록해 재실행이 이어받는다.

구현 중에 어제 발생한 문제의 원인을 찾았다. 전체 재적재가 오늘 - history_days 창부터 받기 때문에 일봉 시작일이 잘려서 어제 905개 종목이 첫 3봉을 잃었다. 재적재 시작일을 min(창, 저장된 첫날)로 고쳤다(RED 확인 후).

첫 주말에 720종목, 약 54만 봉을 처리했다. 남은 것은 수동 실행으로 마무리했다. 이때 함정이 하나 있었다. 이력 확장이 도는지 확인하려고 pgrep -f를 썼는데 자기 자신의 명령줄을 잡아서 돌고 있는 것으로 오판했다. ps | grep "[x]" 방식으로 재확인하니 로그는 이미 끝나 있었다. 프로세스 점검 명령이 자기 자신을 세는 오류는 흔하다.

2. 모의투자 대시보드#

사용자가 전략별 선정·매수·청산 개수, 수익금과 수익률, 보유 종목(보유일, 금액, 수수료, 수익률, 현재 상황)을 볼 수 있는 메뉴를 요청했다. 새로고침 시점 기준이다.

웹에는 거래 키가 없어서 현재가를 직접 가져올 수 없다. 해법은 이렇다. 청산 감시가 어차피 조회하는 시세를 position_marks 표에 남기고(실패해도 감시는 계속, 청산된 포지션은 정리), 웹은 거래 DB와 시세 DB를 읽기 전용으로 읽어 요청마다 계산한다. 보유 평가손익은 실현 손익과 같은 순손익 기준이다(매수 수수료와 추정 매도 수수료·세금 반영).

테스트 중에 내 기대값 계산 실수가 있었다. 코드가 아니라 테스트를 고쳤다. 기대값이 틀렸을 때는 기대값을 먼저 의심한다.

자동 갱신과 모바일 카드#

반응형과 자동 갱신 가능 여부를 묻는 사용자의 요청에서 “10분"이라고 한 것은 내가 제안한 10초의 오타로 보고 주기 선택(10초·30초·1분·10분, 기본 10초)으로 처리했다.

  • 자바스크립트 하나가 영역 교체 방식으로 갱신한다. 필터 폼과 홈 그래프는 영역 밖이라 영향이 없다. 입력 포커스 중에는 건너뛰고, 탭이 숨겨지면 멈추고, 로그인 만료를 감지해 멈춘다. 설정은 localStorage.
  • CSS로 640px 이하에서 표를 카드로 바꾼다. 각 칸에 data-label 이름표를 둔다.

서버는 2단계 인증 로그인이라 에이전트가 열 수 없다. 합성 데이터로 로컬 웹 앱을 띄워 Chrome으로 확인했다. 10초 갱신으로 값이 바뀌었고, 로그아웃 뒤 다음 주기에 “로그인이 만료되었습니다"로 정지했다. 모바일 카드는 CSS와 이름표만 확인했고 실제 폰 확인은 사용자가 했다. 확인하지 못한 것을 구분해서 적었다.

PWA#

홈 화면 설치용 매니페스트와 아이콘을 넣었다(서비스워커는 없다). 서버의 자체 서명 인증서가 한계라 폰에서 설치 가능한지는 사용자 확인 사항으로 남겼다.

문서 정정이 하나 있었다. 상태 문서와 할 일 문서가 여러 항목을 “서버 미배포"로 적고 있었는데 모두 이미 배포되어 있었다. 문서를 고치고 끝난 항목 3개를 지웠다. 배포 직후 문서 갱신이 빠지는 문제는 두 프로젝트에서 모두 반복되었다.

3. 저장소 전체를 7개 에이전트로 리뷰한다#

범위를 “저장소 전체"로 선택해 코드 리뷰를 요청받았다. 읽기 전용 에이전트 7개가 병렬로 영역을 맡았다.

영역
API
집행
리스크
데몬·배포
데이터·계좌
백테스트·명세
웹

결과는 Critical 0, High 15, Medium 약 30, Low 약 55였다. 오케스트레이터는 그중 두 건(EMA 참조선의 워밍업 부족, 워크포워드 검증 창 겹침)을 직접 재현해서 확인했다. 에이전트의 보고를 그대로 믿지 않는다.

High 수정: 묶음별 TDD#

묶음별로 RED를 확인한 뒤 구현했다.

  1. 연구 도구: 검증 창이 겹치면 거부, EMA 워밍업을 기간의 8배로 하고 모자라면 값 없음, 다중 검정에 회차 누적 시도 횟수 반영.
  2. 주문·체결: 원장 계열 500 오류는 모호로 취급하고 허용 목록에 있는 것만 “확정 거부”, 접수 기록을 3회 재시도한 뒤에도 실패하면 unknown으로 승격, 만료 주문 취소 재시도, 체결 반영 재시도(스키마 v4), 메모 덧붙이기.
  3. 데몬·배포: 작업 중 틱 훅, 락을 DB 앞에 두기, 설정·스키마 오류는 종료 코드 2, 점검이 환경 설정의 백업 대상을 보기, 배포 스크립트의 미완 배포 표지.
  4. 두 건은 구조를 고치는 대신 리포트에 고지를 자동 포함하는 것으로 처리했다.

옛 테스트가 옛 계약을 고정하고 있는 경우가 있었다(접수 기록이 실패하면 예외를 던지고 의도를 남긴다는 계약). 새 계약(재시도 → unknown, 둘 다 실패해야 의도 남김)에 맞게 고쳤다. 새 테스트의 결함도 두 개 있었다. 무조건 실패하게 둔 목킹이 복구 채택까지 막았고, 포지션 없는 매도가 사전 검사에서 거절되었다.

이어서 Medium(웹 입력 검증과 인증 처리, 집행의 재심사, 서킷의 HIGH 우선순위 통과, 락 소유 확인, 배포 스크립트의 장중 차단 등)과 Low를 이어서 처리했다. Low 약 80건 중 약 60건은 코드를 직접 읽어 확인했고, 보고 오류가 2건 있었다. 하나는 이미 있는 확인 문구, 다른 하나는 사용처가 없는 모듈이라는 지적이었다.

고치지 않은 것도 있었다. 매수 사전 검사(B5)는 기존의 추가 매수 테스트 두 개를 깨서 되돌렸다. 이미 다른 게이트가 막고 있었다. 소급 입금이 최초 등록일보다 앞서지 못하게 하는 규칙은 기존 테스트가 허용하는 동작이라 빼고 날짜순 잔액 음수 검사만 남겼다. 린터가 한글을 폭 2로 세어서 긴 주석 줄 25개를 줄였다.

사용자 판단이 필요한 네 건(손익 NULL 처리, 두 개의 고지 항목, 시도 횟수의 가족 단위)은 결정 문서에 남기고 물었다. 사용자가 답한 대로 구현했다(추정 손익, 종목 상태 이력, 눌림 체결 보수화, 시도 횟수 가족 단위 누적). 그리고 “확인만 하고 안 고친 것도 수정해 달라"는 요청에 안전하게 고칠 수 있는 것만 고치고 나머지는 이유와 함께 결정 문서에 남겼다.

배포는 데몬이 idle임을 확인한 뒤 했다(데몬 재시작, 스키마 v3 → v4 확인, 사후 점검 이상 없음). 옛 스크립트 본문이 돌아서 새 배포 표지는 다음 배포부터 적용되었다.

4. 연구 4회차와 “학습을 줄이고 검증을 늘려야 하지 않나”#

연구 4회차(추세 추종, 신고가 창 100일)는 이력 확장이 끝난 뒤 재개했다. 스냅샷과 연구 가드를 시작하고 명세 → 검증 순서로 갔다. 첫 검증 실행 중 사용자가 이렇게 지적했다. “학습 구간을 줄이고 검증(OOS) 구간을 늘려야 하지 않나?”

그 말이 맞다고 판단했다. 이미 돌린 첫 검증을 결과를 열람하기 전에 중단하고 폐기했다. 학습/검증 분할을 60/40으로 바꾸고, 검증을 “이미 본 구간"과 “깨끗한 구간"으로 나눠 보고하며 깨끗한 구간의 수익 팩터 1.0 초과를 추가 조건으로 재사전등록했다. 재실행 결과는 순 수익 팩터가 1.0 미만이고 플라시보 대조군보다 열세여서 FAIL-G1이었다. 원인은 신호이고 수정 루프는 없다. 검증 구간은 열람하지 않았다.

중단한 첫 실행이 시도 횟수 장부에 남았으나 설정 지문이 같아서 하나로 합쳐졌다. 이 장부 파일이 이 회차에서 처음 생겼다.

유니버스 분해와 그 결과를 쓰지 않는 규칙#

사용자가 “유니버스에 따라 검토할 수 있나"를 물어서 분해 기능을 리포트에 추가했다(TDD). 4회차 학습 구간으로 한 번 돌려 보니 시장별, 거래대금 분위별, 규모별로 성과가 크게 달랐다. 거래대금 상위와 대형주가 훨씬 좋아 보였다.

이 결과를 어떻게 쓰는가가 규칙이다(D-095). 이 결과로 유니버스를 정하지 않는다. 이미 학습 구간을 본 뒤에 나온 분해이므로, 이를 이용하면 사후 선택이다. 새로운 가설로 먼저 사전등록해야 한다. 규모와 업종은 현재 분류라는 한계도 적었다. 기준 문서에서 값은 바꾸지 않고 “오염된 구간” 규칙만 추가했다.

정리#

영역 내용
이력 주말 데몬 작업, 슬라이딩 창 때문에 예산을 둘로 분리
화면 시세 마크 표로 키 없이 평가손익 계산, 자동 갱신, 모바일 카드
리뷰 병렬 7 에이전트, High 15건 TDD, 재현으로 에이전트 보고 검증
연구 결과 열람 전에 폐기·재사전등록, 분해 결과로 유니버스를 정하지 않음

배운 점: 병렬 리뷰의 가치는 속도보다 독립된 눈이지만, 그 보고를 오케스트레이터가 직접 재현해야 신뢰할 수 있다. 연구 쪽에서는 사용자의 한 줄이 설계 결함을 잡았다. 중요한 것은 결과를 보기 전에 폐기했다는 점이다. 결과를 본 뒤에 설계를 바꾸면 그것은 수정이 아니라 선택이다.
