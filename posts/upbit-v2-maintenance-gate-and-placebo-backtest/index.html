자동매매 V2 개발 · Upbit (14) — 거래소 점검 때 주문을 다시 내지 않기, 그리고 무작위 진입과 비교하는 백테스트

새벽 거래소 점검 동안 쌓인 오류 83건에서 연결 서킷과 점검 게이트를 설계했고, 라이브 표본이 작은 캐너리의 신호가 정말 정보가 있는지를 같은 청산의 무작위 진입과 비교하는 백테스트로 확인했다. 전략 활성화 CLI, 코드 리뷰 후속, 연구 보조 도구 3종과 함께 11월 첫 주를 정리한다.

들어가며#

11월 9~10일의 기록이다. 서버 점검에서 시작해 거래소 점검 동안의 대응 설계, 캐너리의 신호 정보 검증, 운영 도구 정리로 이어졌다. 매매 금액과 손익은 공개하지 않으며, 인증과 접근 제어의 세부는 일반화한다.

1. 새벽 점검 동안 무슨 일이 있었나#

서버의 매매 기록을 읽기 전용으로 점검하다가 이상한 구간을 발견했다. 새벽 2시부터 5시 사이 거래소 점검(403 market_offline)과 연결 타임아웃 83건이 쌓여 있었다. 점검이 끝날 때까지 데몬은 같은 요청을 계속 반복했다.

이 구간에서 두 가지를 설계했다.

읽기 호출의 연결 서킷#

연결 실패가 연속으로 발생하면 일정 시간(쿨다운) 읽기 호출을 시도하지 않는 서킷이다. 처음에는 임계와 쿨다운을 코드에 두었다가 코드 리뷰 후속에서 연속 2회, 10초로 설정 파일에 외부화했다. 점검 응답을 별도 오류로 번역하고, 틱 루프가 이를 정상 대기 상태로 처리한다.

주문 점검 게이트#

더 중요한 쪽이다. 거래소가 market_offline을 응답하면, 쿨다운 동안 진입, 분할 익절, 시장가 청산 주문을 아예 제출하지 않는다. 제출 전에 막는 것이 핵심이다. 주문 행을 만든 뒤 거부되면 장부에 거부된 주문이 쌓이고 재제출 로직이 얽힌다. 그래서 주문 행 생성 이전에 건너뛴다. 쿨다운이 지나면 한 번만 탐침 주문으로 재개 여부를 확인한다.

모듈이 아직 없어서 수집 오류가 나는 것을 먼저 확인하고(TDD의 첫 실패) 구현했다. 쿨다운은 설정 파일의 초 단위 값이다.

청산 슬리피지도 채웠다#

같은 점검에서 청산 슬리피지 컬럼이 비어 있었다. 청산 체결가와 의도 가격의 차이를 채우도록 했다. 진입 슬리피지는 진입 의도 가격이 저장되지 않아 NULL로 두었고, 의도 가격 저장은 스키마 변경이 필요해 별도 백로그로 미뤘다. 이후 서버에서 연결 서킷과 점검 게이트의 실동작, 그리고 청산 슬리피지 채움은 해당 이벤트가 없어 미관측임을 기록하고 이벤트가 생길 때 확인할 점검 항목으로 올렸다. 배포했다고 해서 동작을 확인한 것은 아니다.

2. 코드 리뷰 후속#

전체 코드 리뷰(매매 핵심 경로 변경분 정밀, 저장소 표본 점검) 뒤 권고 처리 목록은 이랬다.

  • 서킷 임계를 설정화
  • 웹의 시세 클라이언트를 공유(요청마다 새로 만들던 것)
  • 장부 검증 강화
  • 매직 넘버를 상수로

이 중 일부는 구현 후에 테스트를 붙였고, 작업 로그에 **“RED 선행 없음”**이라고 솔직하게 적었다. TDD를 지키지 못한 부분을 숨기지 않는다. 보류 네 건은 백로그로 옮겼다.

테스트 하나가 복잡한 이유로 실패했다. 백업 스크립트 테스트 12건이 실패했는데, 테스트의 shim이 Git Bash의 /tmp(사용자 임시 폴더) 경로를 열지 못해서였다. shim을 고쳐 13건이 통과했다. 코드 문제가 아니라 환경 경로 문제였다.

3. 라이브 표본이 작을 때: 무작위 진입과 비교한다#

한 캐너리(여러 지표를 합산한 점수 기반)는 라이브에서 표본이 19건이었고 t값이 0.52로 아무것도 말해 주지 못했다. 소액 이익이 나고 있었지만 우연일 수 있다. 사용자는 “라이브 표본을 백테스트로 늘려 보자"고 요청했다.

백테스트 함수에 전략을 주입하는 인자를 추가했다(기본값은 기존 벤치마크 전략이라 동작 불변). 연구 폴더에 어댑터와 요약 스크립트, 결과 문서를 두었다. 학습 구간만 사용했고 파라미터는 건드리지 않았다.

핵심은 비교 대상이다. 같은 청산 규칙을 쓰는 무작위 진입(시드 3개)을 같이 돌렸다. 결과는 이랬다.

  • 캐너리 신호의 백테스트는 수익 팩터가 1.0을 크게 밑돌았고 건당 평균이 음수였으며 t값은 -11 정도로 유의하게 나빴다.
  • 무작위 진입도 수익 팩터와 건당 평균이 거의 같은 수준이었다.

결론: 진입 신호에 정보가 있다는 증거가 없고 라이브의 소액 이익은 우연으로 보인다. 청산 규칙 자체가 비용을 못 이기는 구조이고, 신호가 이를 바꾸지 못했다.

이 측정은 연구 회차가 아니다. 그래서 시도 횟수 K와 R은 변하지 않고, 이 결과로 파라미터를 고치지도 않는다. 참고 구간과 봉인 구간은 열지 않았다. 한계(플라시보 시드 3개뿐, 라이브와 백테스트의 노출 불일치, 학습 구간의 하락장 비중)를 결과 문서에 적었다.

캐너리 중지 여부는 사용자 결정으로 남겼다. 에이전트가 정하지 않는다.

4. 연구 보조 도구 세 가지#

다른 프로젝트(주식 쪽 V2)의 연구 체계와 비교한 뒤, 연구 도구 세 가지를 도입했다.

도구 역할
연구 가드 연구 폴더의 금지 행동(봉인 구간 접근 등)을 코드로 점검
연구 스냅샷 회차 시작 시점의 설정·데이터 지문을 고정
연구 원장(ledger) 시도 횟수와 봉인 해제 카운터의 기준값을 기록

테스트 15건을 추가했다. 원장 기준값을 처음 넣을 때 내 실수가 있었다. 봉인 해제 카운터 R에 회차 번호를 넣어 65라고 기록했는데 정확한 값은 36이었다. 후보 없음 회차까지 포함한 세션의 회차 번호를 R로 오인한 것이다. 회차 이력 재집계로 검증해 정정했고 그 사실을 작업 로그에 남겼다.

사전 등록 문서도 하나 작성했다(실행 0회). 앞서 기각된 주간 저변동 전략과 달라진 점은 월간 주기 하나뿐이다. 이후 사용자 판단으로 이 월간 실험은 중단되었다. 분류 체계에서 오늘의 두 회차를 연속 기각으로 셀지는 사용자 판정을 기다린다.

5. 운영 도구: 전략 활성화 CLI#

앞서 웹에 만든 전략 켜기/끄기를 명령행으로도 쓸 수 있게 했다. 목록, 켜기, 끄기 세 명령이 있고, 큐잉만 하며(적용은 다음 사이클의 기존 경로) 감사 로그를 남긴다. 알 수 없는 전략 ID가 하나라도 있으면 전체를 거부한다. 일부만 적용되는 상황을 막기 위해서다. 테스트 8건을 추가했고, 파일명이 다른 테스트 파일과 겹쳐서 pytest 수집 오류가 한 번 났다. 이름을 바꿔 해결했다. 같은 이름 충돌은 이 프로젝트에서 두 번째다.

6. 접근 제어 통합과 작업 절차#

11월 10일에는 다른 저장소에서 진행되는 앞단 접근 제어 시스템과 웹을 연동하는 요청을 받았다. 그 저장소 세션의 교차 메시지로 온 요청을 사용자가 이 세션에서 직접 확인하고 승인했고, 구현, 커밋, 배포, 활성화 각 단계마다 사용자 지시를 받았다. 활성화는 기본 꺼짐으로 먼저 배포하고 확인 후에 켰다. 비밀값은 출력 없이 서버에서 생성해 양쪽에 배치했다. 로그인 감사 기록에는 어느 경로로 인증됐는지가 남게 했다. 세부는 공개하지 않는다.

작업 중 하나는 반성할 일이다. 이 작업을 마치고 작업 종료 절차(문서 동기화)를 건너뛰었고, 사용자가 지적한 뒤에 항목을 추가했다. 절차는 기억이 아니라 습관으로 지켜져야 한다.

정리#

영역 내용
장애 대응 연결 서킷, 점검 게이트(주문 행 생성 전에 건너뜀)
관측 배포 ≠ 확인, 미관측은 점검 항목으로
신호 검증 같은 청산의 무작위 진입과 비교, 정보 증거 없음
도구 연구 가드·스냅샷·원장, 전략 활성화 CLI
정직한 기록 테스트 선행 불가, 자기 실수, 절차 누락을 모두 기록

배운 점: 표본이 작은 양의 결과는 “같은 규칙의 무작위 대조군"과 비교해 보기 전에는 아무것도 알려 주지 않는다. 신호가 정보를 가졌는지는 청산 규칙이 만드는 기본 결과를 빼고 봐야 한다. 그리고 장애 대응의 원칙은 단순하다. 주문을 내기 전에 막는다. 내고 나서 거부당한 주문은 장부에 흔적을 남기고, 장부의 흔적은 항상 나중에 비용으로 돌아온다.
