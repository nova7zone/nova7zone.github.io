무료 서버가 회수되지 않게 지키는 자원 현황 화면 만들기

무료 클라우드 서버는 사용량이 너무 낮으면 회수될 수 있다. 서버 두 대의 CPU, 네트워크, 저장공간을 모아 회수 기준과 비교해 보여 주는 화면과 수집기를 만든 과정. 누적 카운터를 증가분으로 계산해야 했던 버그, 배포 때 변경 감지가 빠져 옛 설정으로 돌던 사고, 코드 리뷰로 잡은 7건을 정리한다.

들어가며#

무료 클라우드 인스턴스에는 눈에 잘 띄지 않는 위험이 있다. 사용량이 일정 기준보다 오래 낮으면 서비스가 회수될 수 있다. 자동매매 서버 두 대를 이 방식으로 운영하다 보니, “지금 우리 서버가 회수 기준에서 얼마나 떨어져 있는가"를 한눈에 보는 화면이 필요해졌다. 접근 제어 게이트웨이를 운영하는 저장소에 자원 현황(/usage) 기능을 만든 하루의 기록이다. 서버 식별자와 내부 구성은 공개하지 않는다.

1. 무엇을 모으나#

항목 출처
CPU, 네트워크 클라우드 모니터링 API (읽기 전용)
저장공간 서버 안에서 직접 사용률 계산
회수 기준 대비 상태 위 값들을 기준과 비교

구성요소는 이렇다.

  • 통계 모듈: 수집한 샘플에서 백분위 같은 지표를 계산한다.
  • 모니터링 읽기 모듈: 클라우드 모니터링 SDK로 지표를 읽는다. 쓰기 권한은 없다.
  • 수집기: 정해진 주기로 돌며 결과를 파일에 남긴다. systemd 서비스와 타이머로 등록했다.
  • 화면과 메뉴: 포털에 새 메뉴를 추가했다. “회수 기준 대비 사용량을 올려야 함” 안내와 저장공간 패널을 넣었다.

수집기는 일회성(oneshot) 서비스와 타이머 조합이라, 배포 스크립트가 .timer와 oneshot 서비스를 다르게 다루도록 고쳐야 했다. 모니터링 SDK 의존성도 추가했다.

권한은 사람이 줬다. 클라우드 콘솔에서 동적 그룹과 읽기 전용 정책을 만드는 일은 에이전트가 하지 않고 사용자가 직접 했다. 에이전트는 읽기만 했다. 접근 정책을 바꾸는 일은 항상 사람의 몫이다.

2. 누적 카운터를 그대로 보여 주면 틀린다#

화면에 네트워크 값이 말이 안 되게 크게 나왔다. 원인은 단순했다. 네트워크 지표(NetworksBytesIn/Out)는 누적 카운터였다. 값 자체가 사용량이 아니라 “지금까지 쌓인 총량"이라서, 구간 사이의 증가분을 계산해야 한다. 증가분으로 바꿔 고쳤다.

지표의 종류(순간값, 누적값, 비율)를 먼저 확인하지 않으면 그래프는 그럴듯한데 의미가 없다.

3. 다른 서버의 저장공간은 누가 읽나#

두 번째 서버의 저장공간은 게이트웨이에서 직접 읽을 수 없었다. 그 서버를 운영하는 다른 프로젝트 세션이 저장공간을 알려 주는 읽기 전용 엔드포인트를 구현해 배포했고(사용자 지시), 수집기가 그것을 읽도록 했다. 다른 프로젝트의 코드를 이쪽에서 고치지 않고, 요청만 하고 인터페이스로 연결한다.

4. 코드 리뷰로 잡은 7건#

기능을 마친 뒤 코드 리뷰를 받았고 7건을 반영했다.

  1. 수집 시각 표시: 화면의 값이 언제 것인지 보이게 했다.
  2. 저장공간 사용률을 df 방식으로 계산해 파일시스템 표시와 맞췄다.
  3. 수집기가 읽는 주소의 리다이렉트를 차단했다. 응답이 다른 곳으로 보내도 따라가지 않는다.
  4. --check 모드가 전용 설정 파일을 적용하지 않던 것을 고쳤다.
  5. 저장공간을 못 읽은 경우 오류 배너를 보여 준다.
  6. 이전 결과 파일이 손상되어 있어도 수집기가 죽지 않게 방어했다.
  7. 서버 식별 값이 비어 있을 때 명확한 오류를 내게 했다.

테스트는 235건이 통과했고 1건이 건너뛰어졌다.

5. 배포 사고: “미리 pull한” 서버가 옛 설정으로 돈다#

배포 후 이상한 점이 있었다. 웹 서버(Caddy)가 옛 설정으로 계속 돌고 있었다. 원인은 배포 스크립트가 “저장소가 바뀌었는가"로 재시작 여부를 판단하는데, 누군가 서버에서 미리 git pull을 해 두어서 스크립트가 변경을 감지하지 못한 것이다. 설정 변경이 없다고 판단해 재시작을 건너뛰었다. 서비스를 직접 재시작해서 해결했다.

여기서 운영 규칙이 생겼다. 서버에서 git pull을 따로 하지 않고 배포 스크립트만 실행한다. 변경 감지가 스크립트 안에 있기 때문이다.

6. 확인한 것과 못 한 것#

확인한 것:

  • 통합 점검 12개 항목 모두 통과(마지막 배포 기준)
  • 수집기 점검에서 두 서버 모두 통과, 수집 결과 둘 다 “정상”
  • 사용자가 휴대폰 브라우저에서 화면이 표시됨을 확인

확인하지 못한 것:

  • 작은 화면 레이아웃 전체. 일부만 확인했다.

미완료로 남긴 작업(구성요소 권한 분리 같은 개선)은 이 글에서 다루지 않는다.

7. 작업 종료 절차도 스킬로#

이 저장소 전용으로 작업 종료 로그를 쓰는 스킬과 문서 최신화 스킬을 만들었다. 종료 시 문서 최신화 → 로그 순서로 한다. 문서 최신화 결과는 링크 깨짐 없음, 테스트 수 일치였다. 그동안 작업 종료 절차를 건너뛰는 실수가 있었는데, 절차를 스킬로 고정한 것이다.

정리#

항목 내용
목적 무료 서버가 회수 기준에 가까워지는지 한눈에 확인
구조 수집기(타이머) → 결과 파일 → 화면, 읽기 전용 권한
버그 누적 카운터를 증가분으로 계산
리뷰 7건 반영 (리다이렉트 차단, 손상 파일 방어 등)
사고 서버에서 미리 pull하면 배포 변경 감지가 실패

배운 점: 모니터링 지표는 이름이 비슷해도 의미가 다르다. 누적값과 순간값을 구분하지 않으면 화면이 거짓말을 한다. 그리고 배포 스크립트가 “변경 감지"를 책임지는 구조라면, 사람이 그 스크립트를 우회하는 순간 감지가 무너진다. 규칙을 문서로만 두지 않고 “배포는 스크립트로만"이라고 못박아 두었다.
