무료 서버의 유휴 회수 방지 — CPU 지표가 낮은 이유를 잘못 짚었다가 바로잡은 기록

2026-11-20

들어가며

무료로 쓰는 클라우드 서버에는 유휴 상태가 길면 회수될 수 있다는 정책이 있다. 지표(CPU, 메모리, 네트워크)의 최근 7일 95분위값이 기준 아래로 내려가면 위험하다는 식이다. 그래서 나는 서버 두 대에서 일부러 부하를 걸어 지표를 기준 위로 유지하는 유닛을 운영하고, 게이트웨이 저장소의 세션이 그 지표가 실제로 안전한지를 읽기 전용으로 검증한다. 이 글은 11월 20일 그 검증에서 위험을 발견하고, 원인을 한 번 잘못 짚었던 기록이다.

1. 점검 스킬을 만들다

먼저 반복하게 될 점검을 스킬(idle-check)로 만들었다. 두 서버의 회수 방지와 관리 상태를 읽기 전용으로 확인하고, 두 번째 서버는 직접 접속해서 읽기 명령만 쓰도록 방법을 적었다. 서비스와 타이머, 사용량 화면의 응답, 한도 점검, 주간 점검, 볼륨 사용량이 대상이다. 서버 변경은 하지 않는다.

점검 중에 실패한 유닛이 하나 보였다. 확인해 보니 열흘 전 일회성 재시작 작업이 취소되며 남은 기록이었고 에이전트 자체는 정상이었다. 실패 표시와 실제 장애는 다르다는 것을 확인한 사례다.

2. 위험 발견: CPU 7일 95분위가 기준 바로 아래

점검에서 두 번째 서버의 CPU 7일 95분위가 기준(20%) 바로 아래인 약 19%로 danger 판정이 나왔다. 부하 유닛은 CPU 코어 하나에 30%만 걸도록 설정되어 있었다. 코어가 둘이니 전체 CPU로는 15% 남짓이다. 여기까지는 맞았다.

내가 틀렸던 부분: 처음에 “이 서버는 CPU 일부(1/8)만 보장되는 형태라서 지표가 낮게 나온다"고 추정했다. 다른 세션(앱 세션)이 서버 안에서 직접 측정한 결과는 달랐다. 가상화 환경에서 steal 시간이 19~42% 였다. 즉 내가 건 부하의 일부를 하이퍼바이저가 가져가고 있었고, 보장 비율이 낮은 것이 아니었다. 추정을 확인 없이 문서에 쓰지 않은 것은 다행이었지만, 정정해서 기록했다.

3. 조치와 소유권

부하 유닛은 각 앱 저장소(국내 주식·코인)가 운영하는 구조였다. 게이트웨이 세션은 서버를 직접 바꾸지 않고 앱 세션에 상향 요청을 보냈다. 앱 세션이 부하 값을 30%에서 70%로 올리는 변경을 작성하고 검증해서 반영했다(해당 유닛만 재시작, 데몬과 웹은 그대로).

결과:

  • 반영 전 CPU 최근값 약 16% → 약 15분 뒤 약 37%
  • 7일 95분위는 평균에 오래 반영되므로 즉시 기준을 넘지는 않았고, 며칠 뒤 확인 항목으로 남겼다
  • 이틀 뒤(23일)에 판정이 ok로 회복된 것을 확인했다

그리고 기록해 둘 점: 앱 세션이 반영한 시점을 사용자가 지정했는지 이 세션에서는 확인하지 못했다. 서로 다른 세션이 같은 서버를 만질 때는 누가 언제 승인했는지가 흐려진다. 이것이 이후 서버 관리를 한 저장소로 모으는 이유 중 하나가 되었다.
