서버 관리를 앱 저장소에서 떼어 내고, Python 버전을 패치 단위로 고정하기

2026-11-24

들어가며

서버 두 대를 국내 주식 봇, 코인 봇, 게이트웨이 세 저장소가 각자 조금씩 관리하고 있었다. 부하 유닛은 앱 저장소 안에 있고, 로그 보관 정책은 배포 스크립트 안에 있고, 디스크 점검은 앱의 점검 스크립트 안에 있었다. 11월 23일 사용자가 서버 수준 관리를 전용 저장소와 세션으로 모으자고 결정했고, 24일까지 이관이 이어졌다. 이 글은 그 작업과 함께 진행한 Python 버전 고정의 기록이다. 서버 식별자와 네트워크 세부는 쓰지 않는다.

1. 무엇을 옮겼나

옮긴 기준은 “앱이 아니라 서버를 위한 것인가” 이다.

항목 이전 위치 옮긴 곳
유휴 회수 방지 부하 유닛 앱 저장소 둘 서버 관리 저장소의 공통 유닛(서버별 덮어쓰기 값만 분리)
로그 저널 보관 정책 앱 배포 스크립트 서버 관리 저장소(서버별 상한 값)
디스크·메모리 점검 앱 점검 스크립트 서버 상태 점검 타이머 5분 간격, 텔레그램 알림
게이트웨이용 디스크 조회 앱 웹 엔드포인트 상태 파일 방식으로 변경

순서는 새 곳을 먼저 켜고, 확인한 뒤에, 옛 곳을 지우는 것이다. 새 점검의 알림 발송을 확인하고서야 앱의 점검을 제거했고, 부하 유닛은 같은 유닛 이름으로 새 경로로 전환했다. 전환 중 유닛이 멈추는 공백은 약 2초였고, 전환한 뒤에야 옛 유닛 파일을 지웠다. 이중으로 부하가 걸리지 않도록 옛 커밋은 전환이 끝나기 전에는 배포하지 않기로 세션끼리 약속했다.

또한 서버 점검 알림은 전용 새 텔레그램 봇을 쓰기로 했다. 앱 알림과 섞이지 않게 하기 위해서다. 전송 실패 시에는 응답의 설명을 로그에 남기도록 했다(값이 아니라 원인).

서버에 대한 읽기 전용 통로

서버 사이를 사설망으로 점검할 수 있도록, 키로 접속하면 미리 정한 읽기 명령만 실행하도록 강제하는 방식을 도입했다. 키를 만들어 등록하는 일은 사용자가 했고, 양방향 확인을 마쳤다. (방법과 키 위치는 공개하지 않는다.)

2. 경계를 문서와 도구로 강제

사용자가 요청했다. “서버 관련 사항은 서버 관리 저장소에서 수행하고, 앱 저장소에서 서버 작업을 하려 하면 알려 달라.” 이 규칙을 앱 저장소의 결정 기록, 지침 문서, 규약 문서, 작업 시작 스킬의 정지점에 넣고 세션 메모리에도 저장했다. 사람의 약속만으로는 세션이 바뀌면 사라지기 때문이다.

3. Python 3.12.15로 패치 고정

모든 서버와 로컬 환경에서 Python이 같은 패치 버전이어야 한다는 결정이 있었다. 이유는 자동 업그레이드로 한쪽만 바뀌어 “서버에서만 실패"하는 상황을 막기 위해서다.

함정 1: venv가 마이너 링크를 가리킨다

패키지 관리자(uv)로 만든 venv는 3.12라는 마이너 링크 경로를 가리키고 있었다. 새 패치(3.12.16)를 설치하면 링크가 옮겨져 venv의 Python이 조용히 바뀐다. Windows에서는 실행 파일 자체에 그 경로가 박혀 있어 설정 파일만 고쳐서는 고정되지 않았다. 해결은 패치 번호가 들어간 폴더의 Python으로 표준 -m venv를 써서 새로 만드는 것이다. 설치된 패키지 목록(freeze)이 같은지 비교해 검증했고, 서버는 임시 위치에 예열한 뒤 서비스를 6~8초 정지해 교체했다. 이전 venv는 저장소 밖에 백업했다.

함정 2: 백업 폴더가 미추적 파일로 잡혀 배포를 막았다

서버의 옛 venv를 저장소 안에 .venv.bak-…으로 두었더니 .gitignore가 .venv/만 무시해 “git 로컬 변경"으로 배포가 거부되었다. 백업을 저장소 밖으로 옮기고 문서에 주의를 추가했다.

함정 3: CI가 30번 연속 실패하고 있었다

CI의 Python이 "3.12"라 최신 패치를 받고 있었다. 고정하려고 보니 최근 30회가 전부 실패였다. 두 가지가 겹쳐 있었다. 정적 타입 검사가 Windows 전용 호출 때문에 Linux에서 다르게 동작한 것, 그리고 서비스 관리자 명령이 없다고 가정한 테스트가 CI 실행기에는 그 명령이 있어서 실패한 것이다. 고정과 수정으로 CI가 처음 통과했다. 오래 실패하던 CI는 실패가 일상이 되면 새 실패가 보이지 않는다는 점에서 위험했다.

서버 시스템 Python

서버에는 앱이 쓰지 않는 시스템 python3도 있다. 한 서버에서 이것이 3.11로 바뀌어 있던 것을 배포판 기본(3.10)으로 되돌렸고, 이후 점검에 시스템 python3 기본 유지 여부를 추가했다.

4. 배포 스크립트에서 단계를 지울 때의 함정

저널 정책 배치를 앱 배포 스크립트에서 지우는 배포를 했는데, 스크립트가 자기 자신을 갱신하는 구조라 이번 실행은 옛 본문으로 돌았다. 옛 본문이 저널 설정 템플릿을 찾았지만 같은 커밋에서 이미 지워져 있어, 서버의 설정 파일이 빈 파일로 덮이고 저널 재시작과 정리가 한 번 더 실행되었다. 실제 값은 서버 관리 쪽 설정이 이미 유효해 영향은 없었고, 빈 파일은 관리 저장소가 지웠다.

교훈은 단순하다. 자기 갱신 스크립트에서 단계를 지우는 변경은 옛 본문이 한 번 더 돈다. 지운 단계가 참조하는 파일을 같은 커밋에서 함께 지우면 그 단계가 빈 입력으로 실행된다. 이런 배포는 두 번에 나눈다.

5. 쓰지 않는 옛 서비스를 지우다

관리 저장소가 앱 저장소에 물었다. 서버에 남은 옛 웹 서비스, 웹 서버, 인증서 도구의 용도는? 읽기 전용으로 확인하니 전부 현행 버전이 쓰지 않았다. 옛 웹 서비스는 중지 단계가 빠진 채 52일 동안 인터넷 쪽에 열려 있었다. 담당을 나눠 정리했다.

  • 옛 웹 서비스와 옛 버전 디렉터리: 앱 저장소 세션이 삭제 전에 저장소에 없는 것(서버에서만 고친 설정 파일, 로그, 데이터)을 확인해 사용자에게 보여 주고, 백업 없이 삭제하기로 한 결정을 받아 실행
  • 웹 서버와 인증서 도구: 관리 저장소가 패키지를 삭제
  • 방화벽 규칙: 사용자가 콘솔에서 삭제

자동 모드 분류기가 한 번 명령을 거부했다. 주석 정리와 압축 파일 삭제를 한 명령에 섞었기 때문이다. 우회하지 않고 남은 파일을 목록으로 남겨 사용자에게 넘겼다.

6. 서버 이전 준비 (진행 중)

서버 CPU가 공유 환경이라 steal이 큰 서버에서 국내 주식 봇을 더 여유로운 서버로 옮기는 계획을 세웠다. 일회성 이전 스크립트를 만들고, 서버 관리 쪽 검토에서 꼭 고칠 것 3건이 나와 반영했다.

  • 서버의 작업 예약이 어떤 줄은 절대 경로, 어떤 줄은 홈 경로라 3줄 중 1줄만 매칭되던 것 → 패턴을 고치고, 3줄이 아니면 변경 전에 실패
  • 큰 백업 폴더는 기본 동기화에서 빼고 별도 옵션으로, 이 옵션에서는 원본 서비스를 멈추지도 않고 낮은 우선순위로 돌린다
  • 웹이 내부 주소로만 바인딩되도록 설정하고, 옛 프록시 주소가 남아 있으면 경고

테스트에서도 문제가 나왔다. 새 서버에서 테스트 5건이 실패했는데 원인은 테스트가 실제 서비스 상태와 로컬 포트를 불러 서비스가 꺼진 서버에서 실패하는 격리 결함이었다. 두 함수를 픽스처로 고정해 고쳤다. 이전은 25일 새벽에 자동 실행되도록 예약했고, 결과는 다음 글에서 다룬다.
