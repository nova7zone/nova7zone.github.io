자동매매 V2 개발 · KIS (5) — 실전 주문을 직접 낼 수 없는 에이전트가 실전 점검 스크립트를 만든 방법

에이전트는 실전 주문을 낼 수 없고 이 프로젝트도 실전은 조회 전용이다. 사용자가 실전 주문 점검을 요청하자 거절하고 대안을 제시해, 절차 문서를 거쳐 가짜 브로커로 시험한 점검 스크립트를 만들고 실행은 사용자가 서버에서 했다. 같은 기간의 시세 조회 실전 전환, 일정이 겹치는 작업의 시각 분배, 파서가 거부한 형식 오류 한 줄, 레이트리밋 경고의 원인 세션 식별을 정리한다.

들어가며#

10월 30일부터 11월 3일까지의 기록이다. 모의 계좌로 운영하면서 실전 전환을 준비하는 시기였다. 계좌 정보와 주문 번호, 금액은 공개하지 않는다.

1. “실전 매매 테스트 해 줘"를 거절한다#

사용자가 “실전 매매 테스트"를 요청했다. 이 프로젝트에서 실전(live)은 조회 전용이다. 에이전트는 실전 주문을 직접 낼 수 없다. 이를 알리고 거절한 뒤 대안을 제시했다. 사용자는 절차 문서를 택했다.

작성한 런북(주문 없음)의 핵심 발견이 있었다.

  • 전략의 allowed_modes가 모의 전용이라, 정책만 열어도 데몬은 실전 주문을 내지 않는다.
  • 주문 실측 도구도 실전을 거부한다.
  • 모의 모드에서 전략 하나만 켜고 모드를 실전으로 바꿔도, 전략 로더가 기동 단계에서 거부한다.

이 안전장치들은 의도된 것이다. 실전 점검 방법은 둘로 갈렸다. (A) 실전 점검 전용 스크립트, (B) 전략 경유. 사용자가 A를 택했다. 이후 며칠 뒤 사용자가 “장중 실거래 테스트 스크립트를 만들고 확인할 수 있게 해 줘"라고 요청했다.

구현#

  • measure_live_orders.py와 설정 파일, 가짜 브로커로 시험 32건.
  • 전역 정책 파일은 그대로 두고 --execute일 때만 그 프로세스 안에서 실전 주문을 허용한다.
  • 코드 리뷰(high) 지적 반영 후 전체 검증을 통과했다.
  • 에이전트는 실전 주문을 실행하지 않았다.

실행은 사용자가 서버에서 했다. 대형주 1주로 계획 → 취소 → 체결 순서를 모두 정상 종료했다. 취소 왕복은 정상(취소 후 0.18초에 미체결이 사라짐)이었고, 체결 내역 지연은 0.140.20초, 잔고 반영은 0.191.77초였다. 왕복에 든 현금 손실은 모델이 추정한 비용에 가까웠다. 종료 후 보유는 0주였고, 기록과 별개로 잔고 조회로 확인했다.

에이전트의 경계가 어떻게 작동했는지가 이 이야기의 핵심이다. 에이전트는 스크립트를 만들고 시험하고, 사람은 실행 결정과 실행을 한다.

2. 시세 조회를 실전 키로 전환한다 (매매는 모의 유지)#

모의 서버의 호출 한도(초당 1건 안팎)가 시세 수집의 병목이었다. 일봉, 지수, 종목 마스터, 장중 현재가를 실전 키의 조회 전용 세션으로 옮기고, 매매는 모의로 유지하기로 했다(설정의 데이터 소스 구분, D-146). 수급 수집 창의 호출 상한도 늘렸다.

이어진 점검에서 두 가지를 확인했다. 전환 뒤에도 서버가 레이트리밋 응답을 주는 경고 수는 비슷했고(294건), 어느 세션에서 나오는지 알 수 없었다. 그래서 경고 문구에 session=<모드:앱키 sha256 앞 12자>와 조회 전용 표시를 추가했다. API 사용량 보고와 같은 식별자라서 키 값을 노출하지 않고도 세션을 구분할 수 있다.

원인은 모의 계좌의 잔고 조회였다. 심사와 집행이 같은 잔고를 반복 호출하고 있었다. 짧은 시간의 잔고 캐시(심사·집행기에만 래퍼)를 두고, 복구된 경고는 INFO로 낮췄다. 테스트 6건과 함께 모의 서버의 일일 상한이 거의 소진되던 문제가 해소되었다.

수급 데이터는 “달라진 부분만 갱신하면 되지 않나"를 검토했다. 호출 수는 종목당 1회로 줄지 않는다(날짜 범위 지정이 없고 한 호출이 약 30거래일). 달라진 줄 감지와 정정 기록은 이미 저장 단계가 한다. 달라진 줄만 쓰면 “오늘 받았는가"를 판단하는 fetched_at 기준이 깨져서 새 줄이 없는 날 재호출될 수 있어, 바꾸지 않았다.

3. 장 마감 후 작업이 겹치지 않게#

사용자가 이렇게 요청했다. “장 마감 후 작업이 겹치거나 밀릴 가능성이 있으면 시간 분배를 해 줘.” 데몬은 작업을 한 스레드로 차례로 실행한다. 서버 로그에서 각 작업의 실제 소요 시간을 조사했고, 수급 소급(과거 3개월 확보)을 별도 작업(18:50 시작, 20:15 시각 상한, 마감 20:20)으로 분리했다. 수집 마감은 23:00에서 20:20으로 당겼다. 이 시각 배분의 불변식(작업 간 겹치지 않음, 마감 순서)을 테스트로 고정했다.

그 결과를 서버에서 확인했을 때 문제 하나가 드러났다. 수급 수집 창의 호출 상한(30,000)에 도달해서 어느 저녁의 수급 수집이 0건이었다. 우리 쪽 안전판으로 둔 실전 일 상한(20만 건)은 증권사 공시 값이 아니라 가정이므로, 수집 창 상한을 올렸다. 해당일은 마감 뒤라 재수집할 수 없었고, 다음 날 실행이 최근 30거래일을 다시 받아 메운다.

수급의 잠정값과 확정값 차이도 측정하고 정정 감사 표를 만들었다(investor_flow_revisions).

4. 파서가 거부한 한 줄#

업종명 갱신이 며칠 계속 실패했다. 원인은 공개 업종 마스터 파일(490행)의 486번째 줄이었다. 이름이 없는 99999 자리 채움 줄 하나를 파서가 형식 오류로 거부했다. 수정은 정확히 99999인 줄만 건너뛰는 것이다. 다른 빈 이름은 계속 오류로 처리한다. 허용 범위를 최소로 좁힌다. 실제 파일로 490행 파싱을 확인했고 테스트 1건을 RED → GREEN으로 추가했다.

5. 연구 체계 개선#

사용자의 제안으로 연구 체계에 몇 가지를 도입했다.

  • 독립 검증 구간. 새로 쌓인 일봉 구간을 시도 장부에 opened_through로 기록해, 이후 연구가 열람한 적 없는 구간으로 독립 검증을 할 수 있게 했다.
  • 노출 맞춤 대조. 대조군을 원 전략과 같은 시장 노출로 맞추는 옵션.
  • 보고서에서 진입일 기준과 청산일 기준을 모두 보여 주고, 깔때기 표와 부트스트랩 신뢰구간을 추가했다.
  • 기준 문서의 재보정 로그에 관측을 쌓는다(값은 바꾸지 않는다).

사용자 설계의 연속 수정: 47 → 48 → 49회차#

사용자가 설계한 가설이 회차마다 조금씩 바뀌었다. 47회차(하락장에서 볼린저 밴드폭이 줄었다 늘 때 이동평균 돌파 매수)는 사전 진단에서 후보 수가 기준보다 적어 엔진을 돌리기 전에 기각되었다. 48회차는 매수 조건을 수정한 새 가설로 사전등록했지만 같은 이유로 기각되었다. 49회차는 48회차에서 거래량 조건을 빼고 다시 보았다. 후보가 늘어나 엔진을 돌렸고 순 수익 팩터가 낮았으며 대조군에 모두 졌다.

여기서 기록의 원칙이 드러났다. 48회차의 후보 수를 본 뒤에 조건을 뺀 사례라는 사실을 결정 문서와 이력 인덱스에 명시했다. 이후 연구에서 이 회차를 독립 시도로 계산할 수 있는지 판단할 때 필요한 정보다. 또 이 회차들에서 오케스트레이터가 확인한 사실도 적었다. 서브에이전트는 회차 폴더에만 썼고, 전략 파일과 설정과 결정 문서 변경은 오케스트레이터의 작업이어서 연구 가드가 허용 경로 밖 변경으로 보고한다. 이 보고는 정상이다.

도구 쪽 사소한 함정도 있었다. 인자가 불리언을 받지 못해 정수 0/1로 우회했다. 대조군 실행 시 데이터 캐시가 동시에 만들어지는 충돌은 40~45초 간격으로 시작하는 규칙으로 피했다.

6. 설정을 전략별 파일로 분리#

전략 설정이 하나의 큰 파일(27개 전략)에 모여 있었다. 사용자 요청으로 전략별 파일 폴더로 분리했다(공용 개정). 로더가 폴더를 읽어 파일 이름을 전략 ID로 쓰고, 예전 파일도 읽는다. 27개를 주석째 옮겼고 분리 전후의 엔트리가 같음을 확인한 뒤 옛 파일을 삭제했다. 테스트가 옛 형식을 직접 고치던 곳은 전략 파일 하나를 임시 폴더로 복사하는 방식으로 교체했다. 대시보드도 전략 설정을 켜기/끄기 표와 개별 상세 폼으로 나눴다.

작은 화면 변경도 있었다. 계좌 화면에서 계좌번호를 숨기고, 원금 옆에 올해 입금 총액을 표시했다. 올해 최초 등록 금액도 입금으로 센다는 점은 사용자와 확인했다.

정리#

영역 내용
경계 에이전트는 실전 주문을 내지 않고, 점검 스크립트를 만들고 사람이 실행
시세 조회는 실전 키(조회 전용), 매매는 모의
진단 경고에 세션 식별자, 원인은 잔고 반복 호출, 캐시로 해소
일정 작업 간 시각 불변식을 테스트로 고정
파서 정확한 한 줄만 허용
연구 독립 검증 구간, 후보 수를 본 뒤 조건을 뺀 사례를 기록

배운 점: 에이전트가 하면 안 되는 일을 요청받았을 때의 답은 “안 됩니다"에서 끝나지 않고 **“사람이 안전하게 하도록 만들어 드리겠습니다”**이다. 그리고 경고의 원인을 모를 때는 경고 문구를 바꾸는 것이 가장 싼 진단이다. 어느 세션인지 알려 주는 한 줄이 추측 몇 시간을 아낀다.
