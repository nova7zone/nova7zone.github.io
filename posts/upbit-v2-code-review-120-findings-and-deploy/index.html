자동매매 V2 개발 · Upbit (11) — 코드 리뷰 지적 120건을 우선순위로 풀고, 하루에 네 번 배포하다

정식 전략 승급을 앞두고 코어 전체를 12개 문서로 코드 리뷰해 지적 약 120건을 얻었다. 중요도와 연관성으로 Phase 0~3으로 나누어 모두 RED→GREEN으로 풀고, 정책 결정이 필요한 항목은 사용자에게 의미를 다시 설명해 결정받았다. 같은 날 배포 검증을 격리 작업 트리로 옮긴 일, 서비스 로그가 디스크를 먹던 원인과 정리를 정리한다.

들어가며#

10월 7일 하루에 서버 배포가 네 번 있었다. 그 중심은 아침에 시작된 코어 전체 코드 리뷰와 그 지적을 처리한 일이다. 정식 전략을 승급시키기 전에 코어의 가드가 충분한지 확인하려는 목적이었다.

1. 리뷰: 12개 문서, 약 120건#

리뷰 범위는 core/risk, core/execution, core/scheduler, core/api, core/registry, 메인 진입점, 전략 계층, 데몬, 호가 정렬과 상장폐지 처리, 데이터 계층, 설정 쓰기 경로, 수동 거래와 경계 처리였다. 영역별로 문서 12개를 만들었다. 지적은 약 120건이다.

120건을 그대로 늘어놓으면 처리할 수 없다. 체크리스트 문서(CHECKLIST)로 중요도와 연관성을 정리해 단계로 나누었다.

단계 성격
Phase 0 즉시 고칠 10항목
Phase 1 정책 결정이 필요한 항목
Phase 2 가드와 검증 보강
Phase 3 선별한 나머지

Phase 0 10항목은 TDD로 처리했다. 수정 전에 실패를 확인한 테스트 20건을 먼저 쓰고 구현했다.

2. 정책 결정은 사용자의 몫#

Phase 1에는 코드를 고치는 문제가 아니라 정책을 정해야 하는 항목 12개가 있었다. 접근 원칙은 두 가지였다.

  • 결정이 필요한 것은 사용자에게 의미를 설명하고 묻는다. “라이브 진입 경합"은 사용자에게 의미를 다시 설명한 뒤 결정을 받았다.
  • 기본값이 분명한 것은 바로 구현한다. 체결 기록 원자화, 5xx와 해석 오류 조회 분기, 418 정지 자동 해제, 전략 1회 로드, 기동 시 자격 증명 확인이 이쪽이다.

사용자가 직접 결정한 세 건은 이랬다. 상장폐지 종목은 격리하고 알림을 보낸다. 경계 캔들은 확인한 뒤 재시도한다. 킬스위치는 명시 값을 가진다. 다른 정책은 사용자가 위임했다. 예를 들어 “시장 필터가 켜졌는데 국면이 불명이면?“에는 이렇게 정했다. 사이징은 횡보 국면으로 처리하고 진입은 막지 않으며, 스냅샷 신선도는 6시간으로 하고 now를 주입해 테스트 가능하게 만든다. 기준선 기반 손절이 현재 가격 위에 있으면 진입을 막지 않고 WARNING을 남긴다.

또 하나의 결정은 진입 우선순위다. 후보들이 한 사이클에 몰릴 때 어떤 순서로 처리하는가. 캐너리는 거래대금 순서를 유지하고, 점수는 전체 전략 글로벌이 아니라 전략별로 전략 안에서만 적용하기로 했다. 코드 변경 없이 “라이브는 한 전략의 후보를 낸 순서대로 처리한다"는 사실을 테스트로 고정했다.

3. Phase 2·3: 가드와 입력 검증#

Phase 2는 영역별 가드 보강이다.

  • 리스크: 입력 검증
  • 실행: 종결 상태에서 거꾸로 가는 상태 전이 거부, 존재하지 않는 주문 조회 제한, 알 수 없는 키 무시
  • API: 십진 직렬화, 빈 응답, 토큰 버킷
  • 설정: 범위 검증, 호가표, 캐너리 6종의 Field 검증
  • 레지스트리: 손절 갱신의 상태 보존, 모드별 조회, 스키마 버전 게이트
  • 데몬: 종료 코드, 단조 시계, 최상위 가드, 잔고 조회의 인증 오류 시 종료
  • 상장폐지 오판 방지와 복구

Phase 3은 선별했다. 모두 RED → GREEN으로 풀었다. 테스트는 1,700건을 넘었다.

보류한 것은 세 건(수동 거래 정합, 꼬리 봉 보간, 일일 처리 따라잡기)이고 이유를 결정 문서에 적었다. 나중에 제안이 승인되어 구현했다.

  • 수동 거래 정합: 정합이 끝난 시각 컬럼을 추가하고(스키마 v10, 기존 행은 백필) 정합 대상을 “정합 시각이 비어 있는 행"으로 바꿨다. 실패한 행이 재시도되고 부분 매도 경고가 1회로 줄었다.
  • 꼬리 봉 보간: 마지막 봉이 비었을 때 최대 12봉까지만 보간한다. 실제 봉이 오면 보간을 덮어쓰는 테스트를 고정했다. 시작한 사이클에서 BTC 신선도가 확인된 경우에만 목표를 넘기고, 폴백 사이클과 틱 중 수집에서는 보간하지 않는다.

4. 배포 검증을 격리한다#

배포 스크립트의 검증 단계를 **별도 작업 트리(worktree)**에서 돌리도록 바꿨다(D-190). 이전에는 pull을 먼저 하고 검증했다. 검증이 실패해도 운영 디렉터리의 코드는 이미 바뀐 뒤다. 격리 검증은 별도 사본에서 테스트한 뒤 통과해야 반영한다. 첫 격리 검증 배포에서 테스트 1,640건이 약 160초에 통과했고, 유닛 파일이 자동 재배치되었다.

배포 때마다 같은 확인을 했다. 경계 시각 앞뒤 10분을 피한다. 열린 포지션이 있으면 --force 여부를 확인한다. 재시작 후 phase_failed, 자격 증명 오류, 트레이스백이 0건인지, 포지션이 유지되는지 본다. 헬스체크 전 항목이 통과해야 한다. 정지 시간 제한(TimeoutStopSec)은 서버 실측(사이클 소요 약 1분)을 근거로 30초에서 120초로 늘렸다.

5. 로그가 디스크를 먹고 있었다#

배포 중 서버의 서비스 로그(systemd 저널)가 상한인 4.0GB에 도달한 것을 발견했다. 원인 분석 결과 줄 수의 75%가 HTTP 클라이언트 라이브러리의 INFO 로그였다(체결 틱 조회 67%, 계좌 25%, 시세 8%). 반복되는 진입 건너뜀 로그가 약 8%였다.

두 단계로 처리했다.

  1. 코드: HTTP 클라이언트 로거를 WARNING으로 고정하고, 반복되는 건너뜀 로그를 DEBUG로 낮췄다(테스트 6건). 코드 변경만으로는 이미 쌓인 저널 파일이 줄지 않는다.
  2. 서버: 저널을 1GB로 정리(vacuum)하고 저널 설정 드롭인을 적용했다. 4.0GB가 1.0GB로 줄었고 서비스에는 영향이 없었다. 드롭인 절차는 운영 문서에 추가했고, 점검 스킬에도 로그 볼륨 확인 절을 신설했다.

배포 후 30분간 26줄, HTTP 클라이언트 로그 0줄로 효과가 유지되었다.

정리#

영역 결과
리뷰 12개 문서, 약 120건, 중요도 기준 4단계
처리 Phase 0~3 전부 RED → GREEN, 테스트 1,700건 이상
정책 사용자 결정과 위임을 구분, 설명 후 결정
배포 검증을 격리 작업 트리로, 하루 네 번
운영 로그 볼륨 4.0GB → 1.0GB

배운 점: 리뷰 결과를 수정 작업 목록으로 바꾸는 단계가 리뷰만큼 중요하다. 120건을 중요도와 연관성으로 분류했기에 사흘이 아니라 하루에 처리할 수 있었다. 그리고 정책 항목은 코드로 풀 수 없다. 의미를 설명하고 결정을 받는 절차를 분리하면 에이전트가 결정을 가로채는 일이 없다. 마지막으로, 로그도 운영 비용이다. 반복 로그의 대부분이 라이브러리 기본 설정에서 나오는 경우가 많다.
