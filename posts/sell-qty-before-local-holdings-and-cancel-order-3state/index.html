AI를 이용한 자동매매 프로그램 작성 (36) — 매도 qty_before 로컬 전환, 29시간 좀비주문 사고

매도 주문 하나가 29시간 동안 40회나 취소 시도만 반복하던 좀비 주문 사고를 추적해, qty_before 캡처를 API 재조회 대신 로컬 holdings 기반으로 바꾸고 cancel_order 응답을 3-state로 구분해 재시도해도 해소되지 않는 케이스를 걸러낸 과정을 정리한다.

들어가며#

이전 글에서 VWAP 목표가 손실 매도 버그를 고쳤다. 같은 날 사용자가 OCI에서 복사해온 로그를 분석하다가 더 오래 방치돼 있던 문제를 하나 더 발견했다.

결론부터 말하면, 매도 주문 하나가 취소 시도만 29시간·40회 반복하며 ERROR 로그를 쌓고 있었다. 원인은 두 가지였다 — 어제(6/24) 고쳤던 qty_before 순서 버그와 유사하지만 다른 원인의 재발, 그리고 KIS API의 취소 실패 응답이 “재시도 가능"과 “재시도 불가능"을 구분하지 못하던 문제였다.

발견 경위: 29시간 40회 취소 시도#

사용자가 OCI에서 복사해온 logs/, data/를 분석 요청해 살펴보던 중 data/pending_orders.json에 특정 종목 매도 주문(<주문번호>)이 2026-06-24 09:15부터 06-25 14:00까지 29시간·40회 연속으로 취소 시도 후 매번 실패하며 ERROR 로그만 쌓이는 것을 발견했다.

다행히 실제로는 utils.reconcile.sync_broker_holdings()가 06-24 09:30에 이미 holdings.json에서 정상 제거해 실거래 영향은 없었다. 하지만 근본 원인 2건이 미해결로 남아 있었다.

원인 1: qty_before 오염 재발#

PR #69(6/24)에서 get_balance() 호출을 send_sell_order() 앞으로 옮겨 “주문 후 즉시체결로 잔고 0” 문제를 고쳤었다. 그런데 이번엔 그 시점의 get_balance() 자체가 모의투자 서버의 지연반영/플레이키 동작으로 여전히 0을 반환하는 경우가 재현됐다. 순서를 바꿔도 API 응답 자체가 신뢰할 수 없으면 같은 문제가 재발한다는 것을 확인한 셈이다.

이 경우 holdings-diff 체결판단의 기준점(qty_before=0)이 영구히 오염돼 체결을 영원히 인식 못 하게 된다.

수정: 매도 직전 get_balance() 재호출 자체를 없애고, 이미 직전 cron의 매수체결 확인을 거쳐 검증된 로컬 holdings.json의 보유수량을 qty_before로 사용하도록 바꿨다. 같은 패턴이 3곳에 있어 모두 수정했다.

  • strategy_v2/trading/sell.py
  • strategy_v1/trading/sell.py
  • trading/order_manager.py::sell_worst_performer_for_cash()

API를 매번 다시 불러서 최신값을 얻으려는 시도가 오히려 신뢰성을 떨어뜨렸고, 이미 검증된 로컬 상태를 믿는 쪽이 더 안정적이었다는 게 이번 교훈이다.

원인 2: 재시도 무한 루프#

KISApiClient.cancel_order()가 모든 실패를 bool(False)로만 반환하고 있었다. 문제는 “이미 체결되어 취소할 수량 없음”(40330000)이나 “원주문번호 존재하지 않음”(40320000) 같은, 재시도해도 영원히 해소되지 않는 케이스를 일시적 오류와 구분하지 못한다는 점이었다.

수정: cancel_order() 반환값을 3-state로 바꿨다.

반환값 의미
True 취소 성공
False 일시적 실패, 재시도
None 취소 대상 이미 없음, 재시도 불필요

api/api_constants.py에 ORDER_ALREADY_RESOLVED_CODES 상수를 추가했고, order_manager.check_pending_orders()는 None이면 재시도 없이 pending에서 즉시 제거하고 텔레그램으로 “보유현황을 확인하세요” 알림을 보내도록 했다.

fix: 매도 qty_before를 로컬 holdings 보유수량으로 전환, cancel_order 응답을
3-state로 구분해 좀비 주문 제거

TDD로 RED 확인 후 수정했다. tests/test_kis_api_cancel_order.py를 신규 생성(5건)하고, tests/test_trading.py/tests/test_v2_trading.py에 회귀 테스트 4건을 추가했다. data/pending_orders.json의 좀비 항목(<주문번호>)은 수동으로 제거했다 — 코드 수정 후로는 다음 cron부터 자동으로도 정리됐을 것이다.

pytest tests/ 759개 전체 통과를 확인했다.
