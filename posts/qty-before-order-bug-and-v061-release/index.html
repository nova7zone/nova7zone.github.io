AI를 이용한 자동매매 프로그램 작성 (34) — 매도 체결인식 실패 버그 수정, v0.6.1 릴리즈

일간 리포트의 "매수 1건 | 매도 0건"과 "보유 종목 없음"이라는 모순된 값을 추적하다 발견한 qty_before 캡처 순서 버그를 수정하고, PR #68을 머지해 v0.6.1을 릴리즈한 과정을 정리한다.

들어가며#

이전 글에서 종목당 매수금액 동적화와 현금 하한선 강제매도 기능을 구현했다. 이 브랜치를 PR #68로 머지하기 전, 일간 리포트에서 이상한 값을 발견해 먼저 조사부터 했다.

결론부터 말하면, 매도 주문의 qty_before(체결 전 보유수량)를 캡처하는 순서가 뒤바뀌어 있어 체결 인식이 영원히 실패하던 버그를 찾아 고쳤다. 이후 PR #68을 머지하고 v0.6.1을 릴리즈했다.

발견 경위: 리포트의 모순#

사용자가 받은 오늘 일간 리포트가 “매수 1건 | 매도 0건"인데, 동시에 “보유 종목 없음"이라고 표시하고 있었다. 매도가 0건이면 매수한 종목이 보유 목록에 남아있어야 하는데 그렇지 않았던 것이다.

data/trading.db와 pending_orders.json을 직접 조회해 추적한 결과: 특정 종목이 09:15:11에 손절(stop_loss)로 실제 체결됐는데, pending_orders.json엔 그 주문이 qty_before=0으로 남아 14:45~15:45 cron마다 “취소할 수량이 없습니다"만 반복하고 있었다. systematic-debugging skill로 근본 원인을 추적했다.

근본 원인: get_balance() 호출 순서#

설계 문서(docs/superpowers/specs/2026-06-22-order-fill-detection-holdings-diff-design.md)의 전제는 “주문 접수 시점에 주문 전 보유수량을 캡처"하는 것이었다. 그런데 strategy_v2/trading/sell.py와 order_manager.py::sell_worst_performer_for_cash, 이 두 곳만 send_sell_order() 호출 후에 get_balance()를 불러 순서가 뒤집혀 있었다.

모의투자처럼 매도가 즉시 체결되면, 이미 줄어든 잔고를 qty_before로 기록해버리는 셈이다. 그러면 check_pending_orders()의 holdings-diff 체결판단이 영원히 0으로 고정돼 체결을 인식하지 못하고, 매 cron마다 취소 시도만 반복하게 된다.

반면 strategy_v1/trading/sell.py와 strategy_v2/trading/buy.py는 처음부터 올바른 순서였다. 즉 이번 버그는 두 파일에서만 발생한 국소적인 문제였다.

fix: 매도 주문 qty_before 캡처 순서 버그 수정 (holdings-diff 체결판단 영구 실패)

strategy_v2/trading/sell.py, trading/order_manager.py::sell_worst_performer_for_cash가
send_sell_order() 호출 후에 get_balance()로 qty_before를 캡처하고 있어, 모의투자처럼
매도가 즉시 체결되면 이미 줄어든 잔고를 qty_before로 기록 → check_pending_orders()의
holdings-diff 체결판단이 영원히 0으로 고정돼 체결을 인식 못하고 매 cron마다 취소
시도만 반복하는 버그였음. get_balance() 호출을 send_sell_order() 앞으로 이동.

test-driven-development/systematic-debugging 절차대로, send_sell_order에 즉시체결 시뮬레이션(side_effect)을 걸어 get_balance 응답을 미리 줄여놓는 방식으로 재현 테스트 2건을 먼저 추가해 Red를 확인한 뒤, get_balance() 호출 위치만 이동해 Green으로 전환했다. pytest tests/ 736개 전체 통과를 확인했다.

범위 밖으로 남긴 발견#

조사 중 하나 더 발견했지만 이번 작업 범위가 아니라 사용자 결정으로 수정을 보류한 항목이 있다. utils/reconcile.py::sync_broker_holdings()가 holdings.json을 실제 KIS 잔고로 보정할 때 trade_log.json/daily_stats에는 아무것도 기록하지 않아서, 위 케이스의 실제 손실이 일간 리포트 실현손익에서 누락되는 문제다. next-tasks.md에 후속 확인 항목으로 기록만 하고 넘어갔다.

web/templates/backtest.html은 이번 작업과 무관한 별개 진행 중인 변경이라 커밋에서 제외했다.

PR #68 머지 + v0.6.1 릴리즈#

사용자 지시로 PR #69(qty_before 버그)를 먼저 생성해 CI(pytest 736개) 통과를 확인한 뒤 --squash로 master에 머지(527adf8)했다. git fetch origin master && git merge origin/master로 feature/build를 동기화(08e6b15, 충돌 없음)했다.

이어서 지난 글에서 다룬 종목당 매수금액 동적화 + 현금 하한선 강제매도 작업을 PR #68로 생성하고 CI 통과를 확인한 뒤, 사용자 지시로 master에 squash-merge(95902c0)했다. 머지 전에는 별도로 strategy_v2/DEVELOPMENT_SPEC.md 점검 요청도 받았다 — 사용자가 “DEVELOPMENT_SPEC.md를 참고해 strategy_v2/specs/를 작성했다"는 전제로 신규 수정 명시를 요청해서, §9/§10-5의 sector_max_count가 같은 세션에서 바뀐 실제 값(3→12)을 반영하지 못한 stale 상태였던 것을 발견해 정정했다.

release-notes skill(disable-model-invocation이라 Skill 도구 대신 Read로 수동 실행) 절차대로 v0.6.0 이후 머지된 PR을 조사했다. #68 1건뿐이라 버전 번호로 처음엔 v0.7.0(minor)을 제안했지만, 사용자가 v0.6.1(patch)로 확정했다.

build-docs/release-notes-draft-v0.6.1.md를 v0.6.0 draft 형식 그대로 작성한 뒤, 사용자 확인 후 git tag v0.6.1 95902c0 → push → gh release create로 GitHub Release를 발행했다. v0.6.0 때 겪었던 “본문 제목에 (draft) 잔존” 실수를 이번엔 미리 방지했다 — release 본문 작성 시 첫 줄을 # v0.6.1 (draft)가 아니라 # v0.6.1로 치환한 사본을 --notes-file에 전달했다(로컬 draft 파일 자체는 작업 기록이라 “(draft)” 제목 그대로 유지).
