자동매매 V2 개발 · Upbit (15) — 시장 신호를 모으며 규칙으로 바로 매매하고, 코드 리뷰로 이상치 버그를 잡다

2026-11-14

들어가며

11월 중순의 Upbit 쪽 작업은 두 갈래였다. 하나는 백테스트로 검증할 과거 자료가 없는 신호(파생상품 펀딩비, 미결제약정, 해외 거래소와의 가격 차이, 호가 불균형)를 일단 쌓기 시작하는 일이고, 다른 하나는 쌓는 동안 알려진 단순 규칙으로 소액 실매매를 하며 패턴을 보는 일이다. 금액과 손익은 공개하지 않는다.

1. 연구 선행 정리 (11월 11~12일)

  • 오픈소스 봇 코드 탐색: 공개된 봇 코드를 전략 근거로 인용할 수 있는지 탐색했다. 웹 검색 7회, 배제 15건, 자격 4관문 통과 0건으로 NO-CANDIDATE. 코드와 서버 변경은 없다.
  • 연구 감사: 80회차 중 기준 구간까지 도달한 것이 0건이고 80%는 엔진을 돌려 보기도 전에 문헌·봉인 절차에서 탈락했다. 탈락 사유가 신호가 아니라 절차의 문턱이었다는 뜻이다. 사용자가 통계 문턱은 그대로 두되 가족 단위 사전등록과 최대 t 통계량(다중 검정 보정) 으로 보는 별도 트랙(Track B)을 신설했다. 첫 가족(일봉 60칸)은 통과 0건으로 종결했고, 가족 검정에서 유의했던 1칸도 월 표본이 너무 작아 판정 불가라 구제하지 않았다.
  • 진입 방식 측정: 지금의 지정가 즉시체결 방식이 시장가나 봉 전체 지정가보다 낫다는 것을 서버 읽기 전용 자료 394건으로 확인했다. 방식 유지를 권고했다.
  • 캐너리 라이브 분석: 완결된 거래 전부가 합산 손실이었고 주원인은 약세장의 롱이었다. 파라미터 튜닝은 권고하지 않았다. 우위가 없는 신호를 조정하면 스누핑이 되기 때문이다. 사용자가 두 전략 중 하나를 끄고 하나를 유지하기로 했다.

2. 시장 신호 수집과 캐너리 3종 (D-260, D-261)

사용자 요청은 “자료를 쌓으면서, 백테스트 없이 알려진 규칙으로 실매매하고, 웹에서 패턴을 보자"였다.

수집(core): 시세 DB에 신호 테이블 3개(스키마 v5)를 만들고, 매 틱에서 호출되는 수집기가 내부 간격(60초·300초·3600초)으로 상위 20개 종목의 펀딩, 미결제약정, 김프, 호가를 받는다. 오래된 행은 하루 한 번 지운다. 수집 오류는 틱을 멈추지 않도록 격리했다.

전략(캐너리 3종): 펀딩이 음수일 때, 김프가 음의 구간일 때(반대로 양의 구간이면 청산), 호가 불균형이 크고 종가가 이동평균 위일 때 진입한다. 손절·익절·보유 시간 상한은 같은 값으로 맞추고 동시 보유를 3개로 제한했다. 이 전략들은 연구로 검증된 것이 아니라 신호를 관측하기 위한 도구이므로 “캐너리"라 부른다.

웹 화면: 최신 신호 표, 기준선과 매수·매도 지점이 표시된 시계열, 진입 당시 신호값이 붙은 매매 내역, 성과 요약. 웹은 시세 DB를 읽기 전용으로만 연다. 웹 계층이 전략 모듈을 직접 불러오지 못하는 구조 계약 때문에 임계값은 설정 파일에서 필요한 키만 읽는다.

배포에서 만난 것

1차 배포는 서버의 격리 검증에서 실패했다. 한 테스트가 앞 모듈과 같은 30초 구간의 일회용 인증 코드를 재사용해 401이 났다. 테스트 사이에 상태를 초기화하는 픽스처를 불러오지 않아 순서에 의존하는 테스트였다. 운영에는 영향이 없었고, 수정해 다시 배포했다. 첫 수집 배치에서 세 신호 테이블에 행이 들어오는 것과 세 전략의 진입 활성화를 확인했다.

3. 코드 리뷰 10건과 이상치

배포 직후 코드 리뷰(high)에서 10건이 나왔고 전부 고쳤다(D-262). 성격별로 보면:

유형 내용
시간 상한 미결제약정 배치에 시간 상한을 두고 실패하면 중단하며 경고를 남긴다
연결 해외 거래소 연결을 재사용하고 제한 시간을 5초로 둔다
장애 전파 시장 신호용 호출이 주문용 서킷 브레이커를 열지 않도록 분리했다
웹 표시 신선도 밖 신호에는 매수 표시를 하지 않는다. 전체 집계는 SQL에서 한다
점검 신호 테이블이 15분 이상 갱신되지 않으면 주기 점검이 알린다
전략 진입 판단에서 신호를 먼저 확인한다

배포한 뒤 실제 값을 보니 특정 종목의 김프가 +47~72%로 나오고, 호가가 흔들리는 종목은 ±2%로 튀었다. 상장 직후나 거래가 얇은 종목의 값이다. 수집기가 절대값이 임계(0.2)를 넘으면 기록에서 제외하고 경고를 한 번만 남기도록 하고, 전략에도 한 틱의 변화 상한을 두었다(D-263).

그리고 14일 리뷰에서는 결함 두 개가 더 나왔다. 김프가 이상치로 제외되는 동안 직전의 정상값이 계속 노출되던 것, 그리고 한 캐너리의 구간 경계에서 호가 단위를 과소평가하던 것이다. 전부 고쳤다(D-267).

4. 메모리 방어선 보강

게이트웨이 쪽에서 서버 메모리 사용이 낮아 유휴 회수 방지가 CPU 부하 하나에만 의존한다는 요청이 왔다. 유휴 방지 유닛에 메모리 점유 옵션(2GB 점유, 가용 메모리가 1GB 아래이면 해제)을 추가하고, 유닛에 메모리 상한과 스왑 금지를 걸었다(D-264). 이 구성은 이후 서버 관리 저장소로 이관되었다(다른 글에서 다룬다).

5. 사고: 백업 스크립트가 운영 틱을 28초 지연시켰다

로컬 재현용 시세 DB를 받으려고 .backup 기반 스크립트를 돌렸다. 데몬이 계속 쓰는 DB라 백업이 계속 재시작했고, SSH가 끊긴 뒤에도 서버의 백업 프로세스가 37분 남아 있었다. 그 동안 틱 지연이 185건, 최대 28.5초였다. 보유 포지션 4건의 감시가 늦어졌지만 손익 영향은 없었다.

15일에 스크립트를 고쳤다(D-268). 읽기 일관 스냅샷인 VACUUM INTO로 바꾸고, 연결이 끊겨도 정리되도록 새 세션과 프로세스 그룹으로 실행하며 종료 시 정리한다. 서버 실측 1분 28초, 중단해도 잔존물 0이다. 이 사고의 교훈은 운영 DB를 읽는 도구도 운영 틱의 경쟁자라는 점이다.

6. 라이브 구간을 로컬에서 재현하다 (진단)

사용자가 “모의투자로 전환하는 의미가 있는가"를 물었다. 모의 모드는 체결을 낙관적으로 가정해서 정보가 적다고 답했고, 대신 라이브 구간을 로컬 엔진으로 재현하기로 했다.

서버에서 읽기 전용으로 거래·후보·유니버스 기록을 뽑고, 시세 DB는 필요한 테이블만 한 읽기 트랜잭션으로 추출해 로컬에서 재구성했다. 결과는 다음과 같다.

  • 10개 전략의 신호 일치율 100% (활성 변경이 적용 시각 다음 경계부터 반영된다는 것을 실측으로 확인)
  • 재현한 수익 팩터는 9개 전략에서 1.0 미만이었고, 같은 거래는 라이브가 0.6~6.9%p 더 나았다
  • 엔진의 손절 체결 가정(봉 저가)은 라이브 실측보다 크게 비관적이다. 기록만 하고 core 개정 제안으로 남겼다

그리고 이 과정에서 백테스트 체결률이 10%로 나오던 것이 already_holding 중복 신호를 체결 실패로 읽은 것이었음을 정정했다. 숫자가 이상하면 정의부터 의심하라는 사례다.

배운 점: 자료가 없는 신호는 일단 쌓으면서 소액 실매매로 보되, 그 전략의 이름이 “캐너리"라는 것을 잊지 않아야 한다. 검증된 전략이 아니라 센서다. 그리고 센서의 값이 이상하면(김프 +70%) 전략을 의심하기 전에 수집 단계의 이상치부터 막는다. 마지막으로 운영 DB를 읽는 일회성 도구도 운영과 같은 수준으로 설계해야 한다.
