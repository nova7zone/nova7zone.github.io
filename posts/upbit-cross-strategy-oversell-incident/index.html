자동매매 Bot 전환 및 개발 · Upbit (8) — 한 전략이 다른 전략의 물량까지 팔아 버린 사고

청산이 확인되지 않는 이상 징후를 조사했더니, 두 전략이 같은 코인을 들고 있을 때 먼저 청산하는 쪽이 상대 물량까지 통째로 팔고 있었다. 계좌 잔고를 공유하는 거래소 구조에서 '내 수량'을 장부에 기록하지 않았던 설계 결함을 찾고, 마이그레이션·복구 도구·중복 매수 정리까지 마무리한 과정.

들어가며#

7월 16일, 실운영 중 이상 징후가 하나 올라왔다. 특정 코인의 청산이 장부에서 확인되지 않았다. 처음에는 제3자가 개입한 건지, 외부 요인인지 알 수 없었다. 조회 도구부터 만들어 서버에서 실행해 보니 그 코인의 완료 주문 3건은 전부 우리 봇의 식별자 접두사(두 전략 각각)를 달고 있었다. 외부 개입은 아니었다.

1. 숫자가 맞아떨어졌다#

타임라인을 맞춰 보니 이랬다.

  1. 같은 사이클에서 전략 A와 전략 B가 같은 코인에 각자 독립적으로 진입했다.
  2. 몇 시간 뒤 전략 B의 청산 주문이 나갔다.
  3. 청산 주문의 수량이 A의 수량과 B의 수량의 합과 정확히 일치했다.

두 전략이 사 둔 물량을 B가 한꺼번에 팔아 버린 것이다. A의 장부에는 여전히 포지션이 열려 있는데 실제 보유량은 0이었다. 이후 A의 청산 주문은 가진 수량이 없으니 실패한다.

2. 근본 원인: “내가 산 수량"을 어디에도 기록하지 않았다#

장부(trades 테이블)에 이 전략이 몇 개를 샀는지 컬럼이 아예 없었다. 진입 처리 코드는 체결 수량을 계산은 하고 있었지만 장부에 넘기지 않아 그대로 버려졌다. 그래서 청산 시점의 보유 수량을 구하는 함수는 어쩔 수 없이 거래소 계좌의 해당 코인 잔고 전체를 읽었다.

문제는 업비트에 전략별 서브계좌가 없다는 점이다. 그 잔고는 같은 코인을 가진 모든 전략이 공유한다. 두 전략이 동시에 같은 코인을 들고 있으면, 먼저 청산하는 쪽이 상대 몫까지 매도한다. 전략 간 격리를 설계에서 전제하고 있었는데, 가장 중요한 경계인 수량이 격리되어 있지 않았다.

3. 수정: 수량을 장부에 두고, 거래소 잔고는 상한으로만 쓴다#

사용자 승인 뒤 즉시 고쳤다.

  • 장부에 quantity(진입 체결 수량)와 remaining_quantity(남은 수량) 컬럼을 추가했다.
  • 청산 시에는 remaining_quantity에서 판매 수량을 차감하되 0 아래로 내려가지 않게 했다.
  • 수량 조회는 장부의 남은 수량을 우선하고, 값이 없는 옛 거래는 계좌 잔고로 폴백한다. 어느 쪽이든 실제 계좌 잔고를 상한으로 캡해서, 장부가 어긋나도 존재하지 않는 수량은 팔지 못한다.

이미 만들어진 DB를 어떻게 바꾸나#

CREATE TABLE IF NOT EXISTS는 이미 있는 테이블에 컬럼을 추가해 주지 않는다. 그래서 PRAGMA table_info로 컬럼 유무를 확인하고 없으면 ALTER TABLE ADD COLUMN을 하는 별도 마이그레이션 함수를 만들었다. 서버의 운영 DB도 다음 초기화 시점에 자동으로 적용되고, 옛 행은 NULL로 채워진다. 새 인자는 모두 기본값이 None이라 옛 호출부와 테스트는 한 줄도 바꾸지 않고 통과했다.

테스트는 교차 전략 재현을 포함해 12건을 추가했다. 두 전략이 같은 코인을 들고 있을 때 한쪽 청산이 다른 쪽 물량을 건드리지 않는지, 폴백이 동작하는지, 계좌 잔고 상한이 걸리는지다.

4. 이미 생긴 장부 불일치를 정리하는 도구#

수정은 앞으로의 일이다. 이미 어긋난 장부를 사람이 안전하게 정리할 수단도 필요했다.

교차 전략 스윕 백필: 기존 진단 도구는 같은 전략·같은 코인의 로그만 훑기 때문에, 자기 시도 없이 다른 전략의 청산에 휩쓸린 이 사례는 구조적으로 찾지 못한다. 그래서 닫을 장부 거래의 식별자와, 실제로 체결된 주문의 ID(다른 전략 명의일 수 있다)를 사람이 직접 대조해 지정하면 그 주문의 실체결가로 손익을 계산해 백필하는 도구를 만들었다. 수량이 NULL인 옛 거래는 직접 수량을 지정할 수 있다. 실제 서버에서 실행하고 나니 사용자가 처음 확인한 진입가·청산가와 정확히 일치하는 값으로 장부가 마감되었다.

중복 매수 정리: 같은 조사에서 다른 코인 두 건이 의심 대상으로 올라왔다. 대조 결과 중복 기록이 아니라 실제로 같은 코인을 두 사이클 연속 두 번 매수한 것이었다(두 주문의 수량 합이 실잔고와 정확히 일치했다). 진입 파이프라인에 “이미 보유 중” 가드가 없어서 생긴 노출 2배 상태였고, 이 가드 부재는 이미 할 일 목록에 있었지만 이 확인으로 우선순위가 올라갔다. 조회 함수가 시장당 한 행만 가정해서 방치하면 오래된 행이 같은 방식으로 고아가 될 위험이 있었다. 그래서 두 행을 하나로 병합하는 도구를 만들었다. 살아남는 행에 수량을 합산하고 진입가는 가중평균으로 계산하며, 감사용 기록(merged_from)을 남긴다. 병합된 쪽은 실제 거래 없이 손익 0으로 행정 종결한다.

두 도구 모두 기본은 dry-run이고 --apply를 줘야 반영한다. 서버에서 dry-run으로 확인한 뒤 적용했고, 마지막으로 진단 도구를 다시 돌려 열린 거래 전부 정상, 중복 경고 없음, 사고 포지션은 목록에서 정상 소멸을 확인했다.

5. 이날 정리된 다른 오탐들#

같은 날 같은 흐름에서 두 가지가 더 나왔다.

  • 대조(reconcile) 오탐: 구조적으로 항상 불일치로 판정되는 경우가 있었다. 조건을 고쳤다.
  • 락 충돌: 일일 리포트와 가드가 같은 락 파일을 두고 부딪혀 한쪽이 건너뛰어졌다. 리포트 파일명 충돌 버그와 함께 고쳤다.

둘 다 실운영 로그와 장부를 맞대어 보다가 드러난 문제다.

배운 점: 공유 자원 위에서 여러 주체가 일할 때는 “내 몫"을 반드시 자기 장부에 적어 둬야 한다. 거래소 잔고 같은 외부 상태를 내 수량으로 믿으면, 격리되어 있다고 생각한 두 전략이 서로의 몫을 건드린다. 그리고 사고 대응은 수정과 복구를 분리해서 생각해야 한다. 코드를 고치는 일과, 이미 어긋난 데이터를 사람이 검증하고 되돌릴 도구를 만드는 일은 별개의 작업이다.
