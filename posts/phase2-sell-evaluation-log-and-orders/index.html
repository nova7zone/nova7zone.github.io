AI를 이용한 자동매매 프로그램 작성 (45) — Phase 2 데이터 수집 1부: sell_evaluation_log, orders

들어가며#

이전 글에서 VKOSPI 오조회 버그와 리스크 버그 5건을 고쳤다. 7월 3일 작업 지시서의 Phase 2는 “데이터 수집 계층"이라 불리는 신규 테이블 4종을 만드는 작업이다 — 지금까지는 매매 결과만 남기고 있었는데, 왜 그렇게 판단했는지의 과정을 데이터베이스에 남기기 시작하는 단계다.

결론부터 말하면, 매도 판단 근거 전체를 남기는 sell_evaluation_log와 주문의 생애주기를 이벤트로 기록하는 orders, 두 테이블을 신설했다. 둘 다 brainstorming → writing-plans → subagent-driven-development 전체 절차로 진행했고, 매 Task마다 subagent 구현 + 리뷰를 거쳤다.

sell_evaluation_log — 매도 판단 근거 기록 (T2-1)#

지금까지는 매도가 발생했을 때 “무엇을” 팔았는지는 남았지만, “왜” 그 판단이 내려졌는지 — 예를 들어 손절 기준에는 안 걸렸지만 다른 조건도 함께 확인했는지 — 는 로그에만 흩어져 있었다. sell_evaluation_log는 매도 사이클마다 모든 체크 결과를 데이터베이스 행 하나로 남긴다.

Task 1 (commit e5b6a80): db/schema.py에 sell_evaluation_log 테이블 DDL을 추가했다(15개 컬럼 + idx_sell_eval_mode_code_ts 인덱스). work order 원안에 없던 managed_by 컬럼은 position_registry의 discriminator 컬럼명 관례를 재사용해 추가했다 — v2/v3가 한 테이블을 공유하기 위함이다.

Task 2 (commit 84c216f): db/repository.py에 insert_sell_evaluation_log()/get_sell_evaluation_logs()를 추가하고 TABLE_LABELS에 등록했다(DB 뷰어 조회 가능).

Task 3/4 (commit d2ec517/8ec613e): v3/v2 strategy_sell.py::evaluate() 반환 구조를 확장했다. 기존 {should_sell, reason, priority, details} 계약은 그대로 유지(하위호환)하면서, 우선순위 2/4/5/6 체크 전체의 {should_sell, reason, details}를 담는 all_checks 키를 추가했다. v2의 기존 테스트 하나가 _NO_SELL과의 정확한 dict 일치를 검증하던 테스트라, 개별 필드 검증으로 함께 수정했다.

Task 5/6 (commit 1dd17f9/d056eea): v3/v2 sell.py::run_sell()을 수정했다. 손절(stop_price) 발동 여부와 무관하게 항상 candles를 조회하고 evaluate()를 호출해 전체 체크 결과를 로그에 남기도록 바꿨다 — design 문서에서 사용자가 확정한 트레이드오프였다(손절 사이클마다 API 콜 1건 추가 발생을 감수). candles 부족 시에도 skipped_reason="insufficient_candles"로 1행을 기록한다.

구현 중 테스트 픽스처 결함 두 가지를 발견해 수정했다(둘 다 production 로직이 아닌 테스트 입력값 문제로 리뷰에서 독립 검증했다).

  • v3 테스트: 신규 테스트 4개 중 3개에 import 누락 + fear_filter: {}가 _classify_level()을 매번 extreme_fear로 폴백시켜 “미발동” 테스트를 오염시키던 문제 → 클래스 로컬 설정으로 수정
  • v2 테스트: 위 fear_filter 문제에 더해, 공유 _config() 헬퍼의 condition_weights: {}가 balanced 전략 점수를 항상 0으로 만들어 score_drop을 오발동시키는 두 번째 오염 원인을 추가로 발견 → 공유 _config()는 건드리지 않고 신규 테스트 클래스 전용 override 상수로 해결(다른 기존 테스트에 영향 없음)

Task 7 (commit 1d1bc57): db/repository.py::delete_old_sell_evaluation_logs()를 신규 추가하고 utils/reconcile.py::run()에 90일 경과분 주 1회(월요일) 삭제 훅을 추가했다. run()의 기존 반환 dict 형태는 변경 없이 유지했다(정확 일치 테스트가 있었다) — 삭제 건수는 로그로만 기록한다.

pytest tests/ 946개(시작 전) → 966개(Task 7 종료 시점) 전체 통과했다.

배포 후 확인이 필요한 항목은 매도 사이클마다 sell_evaluation_log에 1행씩 정상 기록되는지, 손절 사이클의 API 콜 추가가 예산(max_calls_per_run)에 미치는 영향, 월요일 reconcile 실행 시 실제로 90일 경과 로그가 삭제되는지였다.

범위 밖 발견도 하나 기록해뒀다 — tests/test_v2_trading.py의 공유 _config() 헬퍼가 애초에 두 가지 픽스처 결함(fear_filter 폴백, condition_weights 미설정)을 갖고 있다는 점인데, 이번엔 신규 테스트 클래스에서 로컬 override로 우회했지만 다른 기존 테스트에 미치는 영향 분석이 필요해 이번 범위에서는 손대지 않았다.

orders — 주문 이벤트 append-only 로그 (T2-2)#

orders 테이블은 주문 하나의 생애주기(placed→partial×N→filled, 또는 placed→cancelled/lost)를 “행 갱신"이 아니라 **“이벤트 1건 = 행 1개 삽입”**으로 기록하는 append-only 로그로 설계했다. 최종 체결 수량은 분석 시점에 SUM(filled_qty) WHERE order_no=...로 계산한다. 현금 하한선 확보 강제매도(sell_worst_performer_for_cash)도 슬리피지 분석 대상에 포함하기로 했다.

Task 1 (commit 5127d22): db/schema.py에 orders 테이블 DDL 추가(16개 컬럼 + 인덱스 2개).

Task 2 (commit 8ee4fbe): db/repository.py에 insert_order_event()/get_orders()를 추가하고 TABLE_LABELS에 등록했다.

Task 3 (commit 634d790): trading/order_manager.py에 순수 헬퍼 3종을 추가했다 — _calc_slippage_pct()(매도는 부호 반전해 “양수=불리한 체결"로 방향 통일, 시장가 주문은 None), _order_event_reason()(매수는 buy_context 전략명, 매도는 sell_reason_code), _resolved_order_event()(취소/소실 이벤트 dict 빌더).

Task 4 (commit 6f96db8): add_pending_order()에 order_type/mode/db_path 옵션 파라미터 3개를 추가(기본값 있음, 기존 호출부 무변경)해 status='placed' 이벤트를 기록한다.

Task 5 (commit bfc5f5e): check_pending_orders()의 체결/부분체결/취소성공/소실 4개 분기 각각에 이벤트 삽입을 추가했다(순수 추가, 기존 체결판단·재등록·취소 로직은 무변경 — zero-deletion diff로 리뷰에서 직접 확인했다). 첫 시도는 백그라운드 테스트 실행 대기 중 멈춰(커밋 없음) 재파견으로 완료했다.

Task 6 (commit ebc8268): sell_worst_performer_for_cash()에도 mode/db_path 옵션 파라미터를 추가해 강제매도도 orders에 기록되게 했다.

Task 7/8/9 (commit c658409/90b05e1/9913f59): v1/v2/v3 buy.py/sell.py의 호출부에 order_type/mode/db_path 전달을 연결했다. v1은 스크리닝 픽스처가 실제 매수를 발생시키지 않아 브리프가 승인한 대로 신규 통합 테스트를 드롭하고 기존 Task 4/5/6 단위 테스트로 배선 커버리지를 대체했다. v2/v3는 기존 buy/sell 성공 테스트를 확장하거나 신규 테스트 3건을 추가해 get_orders() 실제 DB round-trip으로 검증했다. Task 9는 구현 subagent가 세션 한도 오류로 커밋 전에 중단됐지만(작업 자체는 완료돼 있었다), 컨트롤러가 diff를 직접 검증하고 테스트를 재실행한 뒤 커밋했다.

pytest tests/ 968개(Task 1 시작 전 967 + 1) → 990개(Task 9 종료 시점) 전체 통과했다.

배포 후 확인이 필요한 항목은 매수/매도 사이클마다 orders에 이벤트가 정상 기록되는지, 슬리피지 값이 실측과 부합하는지, 부분체결 시나리오가 실제로 발생하면 append-only 다중 행이 의도대로 남는지였다.

정리#

테이블 목적 Task 수 테스트
sell_evaluation_log 매도 판단 전체 체크 결과 기록 7 946→966
orders 주문 생애주기 append-only 이벤트 9 968→990

두 테이블 모두 기존 매매 로직 자체는 건드리지 않고, “판단은 그대로 하되 그 과정을 데이터로 남긴다"는 원칙으로 설계했다. 특히 orders는 zero-deletion diff로 리뷰했다는 점이 인상적인데, 기존 로직을 전혀 바꾸지 않고 로그 삽입만 추가했다는 걸 리뷰에서 직접 확인할 수 있었기 때문이다. 다음 글에서는 이어서 시장 상황 자체를 기록하는 market_context_log와, 매수되지 않은 후보까지 포함해 스크리닝 품질을 검증하는 candidate_outcome 테이블을 다룬다.
