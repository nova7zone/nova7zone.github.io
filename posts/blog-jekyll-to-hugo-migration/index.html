블로그를 Jekyll에서 Hugo로 옮기며 정한 것들: 호스팅, 저장소 구조, 변환 스크립트

자동매매 서버에 블로그를 같이 둘까 하는 고민에서 시작해, GitHub Pages와 Hugo로 이전하기로 결정한 과정. 원본은 비공개 저장소에 두고 빌드 결과만 공개 저장소에 올리는 두 저장소 구조, Chirpy 글 51편을 일괄 변환한 스크립트, 이전 전 백업 절차를 정리한다.

들어가며#

이 블로그는 원래 Jekyll(Chirpy 테마)로 운영하던 글 50여 편짜리 사이트였다. 그것을 Hugo로 옮기고, 앞으로는 AI(Claude Code)로 개발하는 과정의 작업 로그에서 글을 만들어 올리기로 했다. 이 글은 이전 결정과 구조, 변환 작업을 정리한다. 서버 내부 구성과 계정 정보는 공개하지 않는다.

1. 어디에 둘 것인가: 서버에 두지 않는다#

처음에는 이미 돌고 있는 접근 제어 게이트웨이 서버에 블로그를 같이 올리는 방안을 검토했다. 결론은 비권장이었다.

이유 설명
공격면 공개 사이트를 로그인 게이트웨이 서버에 두면 노출 면적이 늘어난다
주소 충돌 서버의 기본 주소는 로그인 화면이 쓰고 있다
평판 같은 도메인에서 브라우저 보안 경고 이력이 있다
쿠키 게이트웨이 쿠키가 도메인 전체 범위라 공개 사이트로도 전송된다

정적 파일만 서빙하는 안도 따져 봤지만 호스트 이름 이전과 쿠키·보안 정책 수정이 필요해서 변경 범위가 컸다. 그래서 GitHub Pages로 정했다. 서버는 건드리지 않고, 서버 평판과도 분리된다. 단 무료 플랜의 Pages는 공개 저장소에서만 동작한다. 이미 nova7zone.github.io라는 공개 저장소가 있었다.

Hugo인가 Jekyll 유지인가#

방문자가 느끼는 속도와 디자인은 둘 다 정적 HTML이므로 차이가 거의 없다. 테마가 결정한다. Hugo의 장점은 로컬에서 쉽게 실행된다는 것이다. 단일 실행 파일이면 되고 Ruby 환경이 필요 없다. 그래서 Hugo(Extended 버전)로 이전하기로 했다.

2. 두 개의 저장소#

가장 중요한 설계 결정이다.

위치 내용 공개
작업 저장소 (비공개) Hugo 설정과 테마, 글 원본(Markdown), 기존 자료, 이미지, 스킬, 검사 스크립트 비공개
public/ (공개 저장소 작업 사본) hugo로 만든 빌드 결과만 공개
  • public/은 공개 저장소의 별도 git 작업 사본이다. 비공개 저장소의 .gitignore에 public/을 넣어, 두 저장소가 서로의 파일을 추적하지 않는다.
  • 작업 로그 같은 원본 자료는 이 저장소에 복사하거나 커밋하지 않는다. 원래 위치에서 읽기만 한다.
  • 초안과 게시를 구분한다. 모든 새 글은 draft: true로 시작하고, 승인된 글만 draft: false로 바꾼다. 빌드는 -D 없이 실행해 초안이 결과물에 들어가지 않는다.
  • 사용자 지시어를 정했다. **“게시해”**는 공개 저장소에 올린다(모든 점검 통과 후). **“푸시해”**는 비공개 저장소에만 올리고 공개되지 않는다. 헷갈릴 수 없게 용어를 못박았다.

기존 글의 주소는 유지하지 않기로 했다. 대신 이미지는 static/assets/img/<슬러그>/ 같은 경로에 그대로 복사해 글 안의 참조를 바꾸지 않았다.

3. 이전 전에: 백업과 되돌릴 수 없는 일#

공개 저장소의 과거 이력을 정리하기로 했기 때문에 순서가 중요했다.

  1. 기존 사이트 작업 사본 전체를 비공개 저장소로 복사한다. 커밋되지 않은 파일(원본 Markdown 한 개)도 포함한다.
  2. jekyll-final 태그를 만든다. 파일 수와 마지막 커밋을 사용자에게 보여 드리고 백업이 완전함을 확인받는다.
  3. 사용자가 공개 저장소를 삭제하고 같은 이름으로 다시 만든다. 에이전트는 삭제하지 않는다.
  4. 삭제 직전에 빌드 결과를 미리 준비해 두었다가 바로 푸시한다. 삭제 시점부터 블로그가 내려가기 때문이다.

사소한 사고도 있었다. 기존 작업 사본 안에 중첩된 .git 폴더가 있어서 비공개 저장소에 올리면 서브모듈 비슷한 링크(gitlink)가 되어 버릴 상황이었다. 폴더 이름을 바꿔(.git_jekyll_history) 해결했다. 이력 정리의 한계도 사용자에게 알렸다. 이미 퍼진 복사본, 포크, 캐시는 지울 수 없다.

되돌릴 수 없는 작업(저장소 삭제와 재생성, 강제 푸시, 이력 정리, 공개 범위 변경)은 에이전트가 하지 않는다. 값을 안내하고 사람이 직접 한다.

4. 테마 선택#

후보를 로컬 hugo server로 미리 보고 사용자가 골랐다. PaperMod로 정했다. 기존 Chirpy와 모양이 달라진다는 점을 먼저 알렸다. 외부 스크립트와 통계, 댓글은 넣지 않았다. 테마는 저장소에 포함(vendored)해서 빌드가 외부 의존 없이 재현되게 했다.

한국어 사이트이고 baseURL = https://nova7zone.github.io/다. 카테고리는 프로젝트별(KIS 자동매매, Upbit 자동매매, OCI 인프라, AI 에이전트), 태그는 종류별(버그수정, 설계, 배포, 릴리스, 프롬프트, 설정, 리뷰, 연구)로 정했다.

5. 글 51편을 스크립트로 변환#

Chirpy의 front matter(categories, tags, img_path, toc, mermaid)와 콜아웃 문법을 Hugo 형식으로 바꿔야 했다. 글마다 손으로 고치지 않고 변환 스크립트와 테스트로 처리했다.

  • 규칙과 예외는 스크립트 안에 둔다. 글마다 따로 기록하지 않는다.
  • 변환 후 샘플을 사용자에게 보여 주고, 로컬 서버로 기존 사이트와 나란히 비교한다(이미지, 링크, 다이어그램, 표).
  • 스크립트는 멱등하게 만들었다. 여러 번 돌려도 같은 결과가 나온다.

작은 스크립트들을 모아 반복 작업을 자동화하고, 각 스크립트에 테스트를 붙이는 방식이 이후 보안 검사와 게시 점검으로 이어졌다.

정리#

결정 이유
서버가 아니라 GitHub Pages 공격면, 주소, 평판, 쿠키 문제 회피
Hugo 로컬 실행이 쉽다
비공개 원본 + 공개 빌드 결과 원본 자료가 공개되지 않게
용어 “게시해”/“푸시해” 공개와 비공개 푸시 혼동 방지
변환은 스크립트 51편을 일관되게, 멱등으로

배운 점: 이전 작업에서 가장 중요한 것은 새 도구가 아니라 되돌릴 수 없는 단계의 순서다. 백업의 완전성을 확인받고, 삭제는 사람이 하고, 빌드 결과를 미리 준비한다. 그리고 “공개한다"는 한 단어에 여러 의미가 섞이지 않도록 용어부터 정한다. 다음 글에서는 게시 전에 돌리는 보안 점검과 게시 절차를 다룬다.
