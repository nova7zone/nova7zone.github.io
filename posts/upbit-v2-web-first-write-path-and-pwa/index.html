자동매매 V2 개발 · Upbit (8) — 웹의 첫 쓰기 경로, 이미 있던 장치를 찾아 쓰다 (그리고 PWA)

단순한 첫 캐너리가 검증하지 못한 실행 경로를 채우는 두 번째 캐너리를 만들고, 웹에서 전략을 켜고 끄는 첫 쓰기 기능을 붙였다. 설계 탐색 중 '자리만 있고 배선이 안 된 줄 알았던' 설정 변경 장치가 이미 구현되어 있음을 발견해 설계를 바꾼 일, 서버에서 설정 파일을 직접 고쳐 생긴 드리프트, 홈 화면 설치용 PWA까지 정리한다.

들어가며#

첫 캐너리의 첫 완결 거래로 실주문 경로의 큰 줄기는 확인됐다. 그러나 사용자의 지적이 정확했다. “첫 캐너리는 매매 조건이 너무 단순하다.” 고정된 시장 하나, 지정가 IOC 매수, 손절과 시간 청산만 검증했다. 지표 기반 진입, 익절 청산(앞서 가격 버그를 고친 바로 그 경로), 동시에 여러 포지션 처리는 라이브로 실행된 적이 없었다. 9월 24일부터 26일까지의 기록이다.

1. 두 번째 캐너리: 실행 인프라의 빈칸을 채운다#

연구 분류 체계 전체가 봉인되어 있었으므로 이번에도 목적은 통계적 우위 검증이 아니라 실행 인프라 검증이다. 이 전제 때문에 백테스트 전후 대조 대상이 아니다. 기획(brainstorming)으로 순차 합의했다.

  • 별도 신규 캐너리로 만든다.
  • 진입은 이동평균 골든크로스.
  • 청산은 고정 가격 익절 + 손절.
  • 유니버스는 고정 후보군(약 20종) 중 상위 10종. 전체 시장 열거는 데이터 제공자 계약 변경이 필요해서 범위 밖으로 뺐다.
  • 최대 3개를 동시에 보유한다.

후보군은 서버에서 실측한 24시간 거래대금 순위에서 스테이블코인과 밈코인을 제외해 골랐다. 캐너리 진입 승인 로직이 단일 전략 하드코딩이었던 것은 전략별 최대 동시 보유 수 테이블로 일반화했다.

테스트 파일 이름이 흥미로운 교훈을 남겼다. 같은 이름의 test_strategy.py가 두 군데 있었는데 tests/ 전체에 __init__.py가 없어서 pytest 모듈 이름이 충돌했다. 고유한 이름으로 바꿨다. 사소한 규약이지만 캐너리가 늘수록 반복될 문제다.

2. 웹의 첫 쓰기 경로#

사용자의 요청은 이랬다. 새 전략을 배포하면 웹에서 전략을 골라 켜고 끌 수 있게 하고, 끄면 이미 보유한 포지션은 원래 진입했던 전략의 규칙대로 계속 청산되게 해 달라. 지금 배포하면 첫 캐너리를 두 번째 캐너리로 교체해 달라.

V2의 원칙은 “웹은 설정과 배분만 쓰고 주문은 하지 않는다“이다. 이 기능은 웹이 처음으로 상태를 바꾸는 쓰기 경로다.

설계를 바꾸게 한 발견#

탐색을 시작했을 때는 새 테이블 두 개(설정 버전, 감사 로그)가 필요하다고 판단했다. 그런데 코드를 열어 보니 이미 설정 버전 테이블과 감사 로그 테이블, 변경 대기열과 적용·롤백 함수가 구현되고 테스트까지 되어 있었고, 4시간 사이클의 8번째 단계가 매 사이클 변경 적용 함수를 실제로 호출하고 있었다. 로드맵 초기에 “자리만 있고 미배선"으로 기록됐던 것이 어느새 완성되어 있었다.

이 발견을 사용자에게 알리고, 새 테이블 두 개를 만들겠다던 앞선 선택 대신 기존 장치 재사용으로 방향을 바꿔 다시 승인받았다. 새로 만든 것은 얇았다.

  • 범위 이름 규칙(strategy_activation:<id>)과 기본값(켜짐)을 정한 작은 모듈
  • 사이클 함수에 entry_enabled 파라미터 추가. 5단계(포지션 유지)는 항상 실행하고, 6~7단계(후보 생성)만 조건부로 건너뛴다.
  • 메인이 사이클마다 활성 여부 맵을 새로 읽어 전달
  • 웹에 전략별 활성화 POST 엔드포인트(로그인 재사용, 대기열에 넣고 감사 기록)와 체크박스·저장 버튼

“끄면 신규 진입만 막고 보유 포지션은 계속 관리한다"는 요구가 그대로 단계 구조에 맞았다. 포지션 유지 단계가 후보 생성 단계와 분리되어 있었기 때문이다. 테스트는 모듈 단위 7건, 사이클 게이팅 2건, 웹 엔드포인트 6건을 추가했다.

에이전트는 로그인할 수 없다#

배포 후 첫 캐너리를 비활성화해야 했는데, 웹 로그인 자격증명은 에이전트가 읽을 수 없게 설계되어 있다. 그래서 체크박스를 직접 클릭할 수 없었다. 대신 서버에서 웹 엔드포인트와 동일한 코드 경로를 1회 호출해 비활성화를 대기열에 넣었다. 감사 로그의 행위자 필드에 “ssh 수동(웹 로그인 자격증명 없음)“을 기록해 구분했고, 다음 로그인 때 사용자가 화면에서 직접 확인하고 조작할 수 있게 했다. 에이전트가 사람의 인증을 우회하지 않는다는 설계 원칙이 구현에 그대로 반영되었다.

타이밍이 우연히 만든 정상 동작#

배포 재시작이 09:00 경계를 막 넘긴 시점이라 데몬이 놓친 09:00 사이클을 즉시 따라잡았다. 이 캐치업 사이클에서 첫 캐너리 포지션이 정상 청산되고, 같은 사이클 안에서 새 포지션이 열렸다. 비활성화 적용(8단계)이 후보 생성(6~7단계)보다 뒤에 오기 때문이다. 토글과 무관한 원래 예정된 동작이며, 이 포지션이 그 캐너리의 마지막이 된다는 것을 정확히 예측하고 확인했다. 두 번째 캐너리도 같은 사이클에서 처음 라이브로 실행되었다(유니버스 10, 후보 0 — 골든크로스가 아직 없었으므로 정상).

3. PWA: 안드로이드 홈 화면에 추가#

사용자가 “대시보드를 안드로이드 앱으로 편하게 보고 싶다"고 했다. 이미 폰 브라우저로 접속 가능하다는 것을 설명하고, 네이티브 앱과 PWA 매니페스트의 작업량 차이를 안내했다. 사용자는 PWA로 충분하다고 확인했고 “일단 추가만 하고 배포는 필요할 때 한꺼번에” 하라고 지시했다.

  • 매니페스트(이름, 시작 URL, display=standalone, 기존 CSS 색상 재사용)
  • 아이콘 두 장은 별도 디자인 없이 라이브러리로 생성했다(사이트 강조색 원 + 텍스트)
  • 헤드에 매니페스트 링크, 테마 색상, 파비콘 3줄 추가

서버 로직은 건드리지 않았다. 정적 파일과 템플릿뿐이다. 응답의 content-type과 상태 코드를 테스트 클라이언트로 직접 확인했다.

4. 서버에서 직접 고친 설정#

캐너리 실행 경로가 검증되고 익절 실측까지 끝나자 사용자가 포지션당 사이징을 올리라고 지시했다. 그런데 사용자가 서버에서 위험 설정 파일을 직접 먼저 고친 상태였다. 프로젝트 규칙은 “서버 직접 수정 금지"다. 로컬 값을 맞춰 커밋해 git 드리프트를 해소했다. 근거 문서와 결정(D-138)도 갱신했다. 이 배포에 앞서 로컬 커밋만 되어 있던 PWA도 함께 서버에 반영되었다.

그런데 배포 직후 상태 문서, 할 일 문서, 작업 로그가 갱신되지 않아 이틀간 “PWA 미배포"로 낡은 채 남아 있었다. 9월 28일 세션에서야 뒤늦게 반영됐다. 배포 직후의 문서 갱신이 빠지면 다음 세션이 틀린 상태를 믿고 시작한다.

정리#

항목 결과
두 번째 캐너리 지표 진입, 익절 청산, 동시 다중 포지션을 라이브 검증
웹 쓰기 경로 기존 설정 변경 장치를 재사용, 신규 테이블 없음
인증 경계 에이전트는 로그인하지 않고 동일 코드 경로로 큐잉, 감사 로그에 구분
PWA 정적 파일 3종, 서버 로직 무변경
드리프트 서버 직접 수정분을 로컬에 맞춰 커밋

배운 점: 새 기능을 설계하기 전에 코드를 읽는 비용은 작고, 이미 있는 것을 다시 만드는 비용은 크다. “자리만 있고 미배선"이라는 문서의 서술은 몇 주 사이에 사실이 아니게 될 수 있다. 그리고 쓰기 기능을 붙일 때는 기능 자체보다 누가 그 쓰기를 했는지가 감사 기록에 구분되어 남는가가 더 중요하다.
