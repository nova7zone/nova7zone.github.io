자동매매 Bot 전환 및 개발 · Upbit (1) — 착수, 그리고 실측이 설계를 뒤집은 순간

국내주식 봇 kis-auto-trading의 core/strategies 분리 아키텍처를 그대로 승계해, Upbit 코인 자동매매 봇을 새로 시작했다. 그런데 착수 직전 실측한 Upbit API 응답 하나가 애초에 정해둔 기준봉 시각을 뒤집었다. 코드를 짜기 전에 가정을 검증하는 게 왜 중요한지, 그리고 그 검증 과정에서 base.py 이식이 어떻게 달라졌는지를 정리한다.

들어가며#

이전 시리즈에서 국내주식 봇 kis-auto-trading을 core(전략 무관 인프라)와 strategies(전략 로직)로 분리해 다시 세운 이야기를 썼다. 이번 시리즈는 그 아키텍처를 들고 새 시장으로 건너간 이야기다 — Upbit 원화(KRW) 마켓 코인 자동매매 봇 upbit-auto-trading.

같은 설계를 다른 시장에 그대로 옮기면 간단할 줄 알았다. 실제로는 착수 첫날부터 “당연히 이렇겠지"라고 적어둔 가정 하나가 실측 한 번에 뒤집혔다. 그 이야기부터 해야 할 것 같다.

1. 왜 새 저장소인가#

기존 kis-auto-trading-bot(국내주식)과 그걸 다시 설계한 kis-auto-trading은 주식 시장을 전제로 한다 — 장 시작·마감이 있고, 휴장일이 있고, 하루 봉의 기준이 명확하다(장 마감 시각). 코인은 이 전제가 전부 깨진다. 24시간 무휴장이고, “하루"라는 개념도 거래소가 임의로 정한 기준일 뿐이다.

그래도 core/strategies 분리, 파이프라인 6단계 인터페이스(build_universe → build_pools → screen, reevaluate, evaluate_entry → evaluate_exit), import-linter로 강제하는 계층 경계 — 이 골격 자체는 시장이 달라져도 그대로 쓸 수 있는 부분이었다. 그래서 kis-auto-trading에서 확정한 ARCHITECTURE.md를 read-only 참조로 두고, 그 위에 Upbit 특유의 것만 새로 얹는 방식으로 착수했다.

2. 실측이 설계를 뒤집었다 — 기준봉 시각#

착수요청서 초안에는 기준봉을 06:00 KST로 적어뒀다. 국내주식 장 시작(09:00)에 맞춰 하루를 나누던 습관을 코인에도 그대로 옮긴, 별생각 없는 선택이었다.

그런데 코드를 짜기 전에 실제로 Upbit 240분봉 API를 호출해봤다.

GET /v1/candles/minutes/240?market=KRW-BTC

반환된 candle_date_time_kst 값을 늘어놓으니 09:00 / 05:00 / 01:00 / 21:00 … 이었다. 즉 Upbit의 4시간봉은 UTC 00:00 기준으로 정렬되어 있고, 그걸 KST로 환산하면 네이티브 경계가 01·05·09·13·17·21시다. 06:00은 이 경계 어디에도 없다.

06:00을 고집했다면 60분봉을 모아서 4시간 단위로 다시 집계하는 계층을 따로 만들어야 했다. 그러면 결측 처리·경계 검증·타임존 버그가 그 집계기 안에서 또 하나씩 생긴다. 대신 기준봉을 05:00 KST로 바꾸면 이 경계와 정확히 일치한다 — 그러면 GET /v1/candles/minutes/240을 가공 없이 그대로 쓸 수 있다. 집계기 자체가 통째로 사라지는 것이다.

그 자리에서 기준봉을 05:00으로 확정했다. 사이클도 05:05·09:05·13:05·17:05· 21:05·01:05(‘:05’는 API 반영 지연을 흡수하는 여유)로 다시 짰다. 코드를 한 줄도 쓰기 전에 API 응답 하나를 확인한 덕분에, 나중에 지표 계산이 다 끝난 뒤에야 “어? 봉 경계가 안 맞네"를 발견하는 상황을 피했다. 가정은 코드를 짜기 전에 실측으로 깨는 게 제일 싸게 먹힌다 — 이번 프로젝트에서 가장 먼저 얻은 교훈이다.

3. 승계 이식에서 마주친 편차 4건#

파이프라인 인터페이스 정본 strategies/base.py는 kis-auto-trading의 ARCHITECTURE.md §3를 그대로 옮겨 적는 작업이라 쉬울 거라 생각했다. 실제로 초안을 원문과 한 줄씩 대조하니 편차가 네 군데 나왔다.

  1. reevaluate의 반환 타입 — 초안은 별도 타입을 썼는데, 원문은 ExitDecision을 그대로 반환하고 기본값은 “유지(hold)“였다.
  2. 진입 판단 반환 타입이 EntrySignal이어야 하는데 초안에서 누락돼 있었다.
  3. build_pools의 기본 구현 — 그룹 풀이 필요 없는 단순 전략은 전체 유니버스를 단일 그룹으로 묶는 기본 동작이 있어야 하는데, 초안엔 추상 메서드로만 있었다.
  4. 데이터 접근 경로 — 전략이 ctx.data(DataProvider)를 통해서만 캔들에 접근해야 하는 부분이 초안에서 흐릿했다.

넷 다 “일단 만들어보고 나중에 맞추면 되지"로 넘길 수 있는 것들이었다. 그런데 이 인터페이스는 앞으로 v1·v2 전략과 core 양쪽이 계속 의존할 계약이라, 여기서 어긋난 채로 굳으면 나중에 고치는 비용이 훨씬 커진다. 그래서 원문 대조를 0단계의 완료 조건에 넣고, 네 건을 전부 고친 뒤에야 0단계를 닫았다.

참고로 kis-auto-trading-bot(v3 실운영 원본)은 base.py 같은 계약 없이 전략이 서로 얽혀 있는 레거시 구조라, 이번 대조에는 쓸 수 없었다. ARCHITECTURE.md §3 쪽이 유일한 정본이었다.

4. 하드런이 남긴 사소하지만 성가신 교훈들#

설계·이식과 별개로, 이번 착수에서 환경 쪽으로 세 가지를 새로 배웠다. 전부 당장 큰 문제는 아니었지만, 방치하면 나중에 CI가 갑자기 빨갛게 변하는 종류의 것들이다.

  • requirements-dev.txt는 ASCII 전용으로. 한글 주석을 넣었더니 Windows 로케일(cp949)에서 pip가 그 파일을 디코딩하다 UnicodeDecodeError를 냈다. 주석은 영문으로만 쓴다.
  • enum은 StrEnum이 아니라 (str, enum.Enum). StrEnum은 Python 3.11+ 전용인데, 검증 샌드박스가 3.10이라 호환이 안 됐다. 대신 ruff의 UP042 규칙을 ignore 처리했다.
  • PowerShell에서 venv 삭제는 Remove-Item -Recurse -Force. cmd의 rmdir /s /q 감각으로 접근하면 안 된다.

이런 것들은 아키텍처 문서에는 절대 안 남는데, 실제로 손을 움직이면 꼭 한 번씩 걸린다. 그래서 이번엔 세션 기록(work-log.md)에 “하드런 교훈"이라는 항목을 따로 만들어 남겨두기로 했다.

정리#

항목 결정
아키텍처 kis-auto-trading의 core/strategies 분리를 read-only 참조로 승계
기준봉 06:00(초안) → 05:00 KST로 변경 — 240분봉 네이티브 경계(01·05·09·13·17·21시)와 일치 확인 후 확정
집계기 불필요 — GET /v1/candles/minutes/240을 가공 없이 그대로 사용
base.py ARCHITECTURE.md §3 원문 대조 완료, 편차 4건 수정(reevaluate/EntrySignal/build_pools 기본구현/ctx.data)
강제 수단 import-linter 3계약 + pre-commit + CI(3.11/3.12 매트릭스)
환경 교훈 requirements-dev ASCII화, enum 3.10 호환, PowerShell venv 삭제 명령 차이

이번 편의 교훈은 하나로 요약된다. “당연히 이렇겠지"로 적어둔 숫자는, 코드를 짜기 전에 실제 API 응답으로 한 번 확인하는 게 제일 싸게 먹힌다. 06:00이라는 숫자 하나를 그대로 밀어붙였다면, 존재할 필요가 없었던 집계 계층 하나를 만들고 검증하고 유지보수했을 것이다.

0단계(repo 골격 + base.py + import-linter + CI)는 검증을 전부 통과하고 닫았다. 다음 글은 1단계 — core/api(JWT 서명·rate limiter·주문 API 래퍼)와 core/data(240분봉 수집·경계 검증·결측 보간)를 다루게 될 것 같다. 특히 Upbit의 rate limit이 그룹별로 다르게 걸려 있어서(order는 초당 8회로 유독 낮다) 그 토큰버킷을 어떻게 짰는지가 재미있는 대목이 될 것 같다.
