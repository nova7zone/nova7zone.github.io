자동매매 Bot 전환 및 개발 · Upbit (3) — 서버에 올리며 겪은 두 번의 삽질

로컬에서 테스트 61개가 전부 통과한 코드를, 이번엔 실제 OCI A1 서버에 올리고 진짜 Upbit 계좌에 연결했다. 코드는 문제가 없었다. 대신 GitHub 인증과 Upbit의 낯선 "포켓" 개념이 발목을 잡았다 — 둘 다 코드 리뷰만으로는 절대 안 보이는 지점이었다.

들어가며#

지난 글에서 core/api·core/data를 TDD로 완성하고 로컬 테스트 61개를 전부 통과시켰다. 이번엔 실제 운영 환경(OCI A1, ARM64 서버)에 그 코드를 올리고, 실제 Upbit API 키로 계좌를 연결해볼 차례였다. 코드 자체는 문제가 하나도 없었다. 대신 “서버 환경"과 “플랫폼의 계정 모델"이라는, 코드 리뷰만으로는 절대 안 보이는 지점에서 두 번 발목을 잡혔다.

1. 첫 번째 삽질 — “Repository not found"가 사실은 인증 실패였다#

private 저장소를 서버에서 clone하려는데 Repository not found 에러가 났다. 저장소 경로를 몇 번이나 다시 확인했는데 이상이 없었다. 알고 보니 GitHub은 private 저장소에 대해 인증되지 않은 요청에는 “권한 없음"이 아니라 일부러 “존재하지 않음"을 돌려준다 — 저장소의 존재 여부 자체를 숨기기 위한 설계다. 즉 이 에러 메시지는 사실 토큰 인증 실패였다.

fine-grained personal access token을 다시 발급하고 credential.helper store로 저장한 뒤 재시도하니 해결됐다. 이때 “정상적으로 저장됐는지"를 확인하는 방법도 유용했다 — 같은 명령(git fetch)을 한 번 더 실행했을 때 아무것도 묻지 않고 조용히 끝나면 토큰이 저장되어 재사용되고 있다는 뜻이다. 반대로 또 Username/Password를 물어보면 저장이 안 된 것이다. “에러 메시지 없음"이 항상 “성공"을 뜻하진 않지만, 이 경우엔 침묵이 곧 정상 동작의 증거였다.

2. 두 번째 삽질 — API는 정상인데 잔고가 계속 빈 리스트였다#

§9 검증(정적 검사·테스트)과 API 인증 스모크(시세 조회·계좌 조회 실호출)까지 전부 서버에서 통과시켰다. 그런데 계좌 조회(accounts()) 결과가 계속 빈 리스트였다 — 실제로는 코인을 보유 중인데도. 코드도, 인증도, 접근 설정도 전부 맞았다. 문제는 Upbit의 포켓(Pocket) 구조였다.

Upbit는 계좌가 메인포켓과 서브포켓(최대 5개)으로 나뉘고, 입출금은 메인포켓에서만 일어난다. API 키를 처음 발급할 때 별생각 없이 “A1서버"라는 이름의 서브포켓으로 만들었는데, 이 서브포켓엔 애초에 아무 자산도 없었던 것이다 — 실제 보유 자산은 전부 메인포켓에 있었다. API·서버·코드는 전부 정상 동작했고, 그냥 빈 포켓을 보고 있었을 뿐이었다.

착수요청서를 다시 열어보니 애초에 “v1 운영은 메인포켓 단일 구성으로 시작한다"고 이미 적어뒀었다. 서브포켓을 만든 것부터가 그 결정에서 벗어난 선택이었던 셈이다. 메인포켓 기준으로 키를 다시 발급받고(필요한 최소 권한만 부여) 키 설정을 교체하니 실제 보유 자산이 정상 조회됐다.

돌아보면 이 문제는 API 문서만 읽어서는 절대 안 보였을 종류다. 인증·엔드포인트 스펙은 코드로 다 검증했는데, 정작 걸린 건 “이 플랫폼이 계좌를 어떤 단위로 나누는가"라는, 코드 바깥의 개념 모델이었다. 거래소마다 이런 계정 모델이 다르다는 걸 다시 새겼다.

정리#

항목 내용
배포 환경 OCI A1(ARM64), Python 3.12, venv
GitHub 인증 fine-grained PAT + credential.helper store — “Repository not found"는 인증 실패의 위장
§9 검증 lint-imports · pytest 61 passed · 레지스트리 스모크, 서버에서도 전부 통과
API 인증 스모크 시세·계좌 조회 통과, 주문 파라미터 검증(order-test)은 최소 주문금액 미달로 보류
운영 포켓 서브포켓 시행착오 후 메인포켓 단일 구성으로 확정(착수요청서 원안 재확인)

이번 편의 교훈은 하나로 요약된다. 코드가 전부 정상이어도, 플랫폼 고유의 계정/권한 모델을 모르면 삽질한다. API 명세서만 파고들다 보면 “이 거래소는 계좌를 어떻게 나누는가” 같은, 훨씬 기본적인 질문을 건너뛰기 쉽다.

실제 계좌 연결까지 끝났으니, 다음은 착수요청서 2단계 — BTC 국면 판정 (core/market), 사이징과 손절(core/risk), identifier 기반 주문 추적 (core/execution)이다. 국내주식용으로 짜여 있던 국면 분류기를 BTC 시세로 어떻게 갈아끼우는지가 다음 글의 중심이 될 것 같다.
