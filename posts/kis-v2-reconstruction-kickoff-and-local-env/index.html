자동매매 Bot 전환 및 개발 · KIS (1) — 새 저장소 kis-auto-trading 착수, 로컬 개발 환경 구축

기존 저장소의 전략-인프라 결합 문제를 정리하기 위해 core/strategies를 분리한 새 저장소 kis-auto-trading을 시작했다. 코드를 짜기 전에 dev container 없이도 VS Code + Claude Code로 바로 작업할 수 있는 로컬 환경을 먼저 갖췄는데, 그 과정에서 cmd.exe 배치 파싱 버그, uv 관리 Python이 py 런처에 안 잡히는 문제, 한글 주석이 pip를 깨뜨리는 인코딩 버그까지 연달아 만났다.

들어가며#

kis-auto-trading-bot(기존 저장소)은 v0.7.1까지 잘 굴러가고 있었다. 문제는 코드가 아니라 구조였다. strategy_v3가 strategy_v2의 position_registry·daily_reeval·fear_filter 같은 내부 모듈을 그대로 가져다 썼고, v3를 붙이려고 v2 파일을 직접 고쳐야 했다. 공유 코어 계층이 따로 없다 보니 먼저 만든 전략이 사실상 코어 노릇을 하고 있었던 셈이다. 다음에 v4를 붙이면 이 문제가 한 번 더 반복될 게 뻔했다.

그래서 전략 무관 인프라(core/)와 전략 로직(strategies/)을 명시적으로 분리한 새 저장소 kis-auto-trading을 시작하기로 했다. 기존 저장소는 계속 운영하면서, 이 저장소에서 병행 구축하고 검증되면 전환하는 방식이다. 설계 문서(ARCHITECTURE·CORE_EXTRACTION_MAP·BACKTEST_VALIDATION 등)와 골격, 프로젝트 스킬 4종은 이미 준비돼 있었다.

오늘은 코드를 한 줄도 짜지 않았다. 대신 로컬 개발 환경부터 다졌다 — 사소해 보이지만, 이런 걸 나중으로 미루면 항상 코드 문제보다 디버깅하기 성가신 방식으로 발목을 잡는다.

왜 dev container 밖으로 나왔나#

지금까지 코드 생성은 전부 dev container(python:3.11-bookworm 이미지) 안에서 했다. 이번엔 VS Code + Claude Code 플러그인으로 로컬 Windows에서 컨테이너 없이 바로 작업할 수 있는 환경을 병행 구성하기로 했다. devcontainer.json은 그대로 두고, 로컬 환경은 별도로 갖추는 방향이다.

문제는 로컬 Windows에는 지금까지 아무것도 없었다는 것 — Python도, git 초기화도, VS Code 설정도. 이걸 한 번에 처리하는 setup_local_env.bat을 만들었다.

setup_local_env.bat — 세 번 고쳐 쓴 배치 파일#

첫 버전은 한글 주석 + chcp 65001 + 여러 줄짜리 괄호 블록(if (...), for ... do (...)) 조합으로 짰다가 그대로 터졌다. cmd.exe가 명령어 토큰을 엉뚱하게 쪼개서 errorlevel, python -m 같은 멀쩡한 줄까지 “내부 또는 외부 명령이 아닙니다” 에러를 냈다. 한글을 전부 영문으로 바꾸고 다시 돌렸더니 이번엔 다른 지점에서 - 은(는) 예상되지 않았습니다 에러가 났다 — 원인은 한글이 아니라 여러 줄에 걸친 괄호 블록 자체였다. 결국 모든 분기를 if ... goto label 한 줄짜리로만 쓰고 :label로 흐름을 나누는 flat goto 스타일로 전면 재작성하고서야 안정됐다.

Python 버전 탐지도 한 번에 되지 않았다. py -0로 확인해보니 PATH의 기본 python은 3.14.5였고, 3.11.15는 uv(Astral)로 설치돼 있었다 — py 런처에 Astral\CPython3.11.15라는 회사 태그로 등록돼 있어서 py -3.11 단축 호출로는 못 찾았다. 게다가 이 신형 py 런처는 해당 버전이 없을 때 “No runtime installed” 메시지를 찍으면서도 종료 코드는 0을 반환해서, errorlevel 기반 감지 로직이 조용히 오탐했다(3.11을 못 찾았는데 찾았다고 착각). 최종적으로는 uv 설치 경로(%APPDATA%\uv\python\cpython-3.11*-windows-x86_64-none\python.exe)를 직접 찾는 방식을 우선으로 두고, py -3.11은 출력 텍스트를 findstr로 검증하는 보조 수단으로만 남겼다.

마지막 함정은 requirements-dev.txt였다. 이 파일의 한글 주석과 em-dash(—)가 Windows(cp949 로케일)에서 pip 24.0의 auto_decode를 UnicodeDecodeError로 깨뜨렸다 — devcontainer는 Linux UTF-8 로케일이라 지금까지 아무도 이 버그를 못 봤다. 주석을 전부 ASCII로 바꾸고서야 해결됐다. 운영 환경과 로케일이 다른 곳에서 처음 셋업할 때만 드러나는 종류의 버그였다.

세 번의 삽질 끝에 setup_local_env.bat 하나로 git init·venv·pip install -r requirements-dev.txt·pre-commit install·.vscode 설정 생성·검증(lint-imports/pytest/import 스모크)까지 멱등하게(재실행해도 안전하게) 처리하게 됐다. venv는 최종적으로 Python 3.11.15로 맞췄다 — 운영 OCI 서버가 3.11.0rc1(정식 릴리스가 아닌 release candidate)이라는 것도 이번에 처음 확인했는데, rc1 자체를 다시 받긴 어려우니 3.11 계열 안정판으로 맞추고 OCI 업그레이드는 별도 과제로 미뤄뒀다.

.claude/settings.json — 권한 규칙 세팅#

Claude Code 플러그인의 권한을 프로젝트 단위로 고정해뒀다. 매매 봇 저장소라 시크릿 유출·의도치 않은 파괴적 명령에 특히 보수적으로 잡았다.

  • allow (조회성, 항상 통과): git status/diff/log/show/branch, pytest, lint-imports, pre-commit run, pip list/show/freeze
  • ask (매번 확인): git add/commit/push, pip install, python -m venv, 그리고 runner.py 실행 — 이건 나중에 실제 주문을 넣는 진입점이 될 거라 자동 허용하지 않기로 했다
  • deny (차단): .env/secrets//*.key/*.pem 읽기, curl/wget(네트워크 유출 경로), git push --force*, rm -rf *

세션 브릿지가 파일을 잘라 보여준 소동#

문서 몇 개를 정리하던 중 git diff --stat이 손도 안 댄 파일들(README.md, ARCHITECTURE.md 등)까지 원본보다 훨씬 작게 나오고, .gitignore 끝에는 null 바이트까지 붙어 보였다. 처음엔 실제 데이터 손실을 의심해서 작업을 멈췄다. 로컬 PowerShell에서 Get-Content -Raw로 길이를 재고 Select-String으로 파일 앞뒤 마커 문자열이 다 남아있는지 직접 확인시켜보니, 실제 디스크 파일은 전부 멀쩡했다 — 잘려 보인 건 원격 작업 세션의 읽기 브릿지가 캐시 과정에서 파일을 불완전하게 돌려준 것뿐이었다.

교훈은 단순하다: 의심스러운 diff를 보면 겁먹고 바로 “복구"에 들어가지 말고, 항상 로컬에서 직접 한 번 더 확인할 것. 자동화된 복구 시도가 오히려 진짜 손상을 만들 수 있다.

문서 규약 추가#

작업 중 산출물을 정리할 곳도 정했다. docs/development/build-docs/(코드리뷰·분석 등 1회성 산출물), work-log.md(세션별 기록), next-tasks.md(다음 할 일, 완료 항목은 [x]로 표시), blog-drafts/(이 글처럼 블로그 초안). 프로젝트 스킬(doc-sync, kis-trading-dev)에도 work-log.md뿐 아니라 next-tasks.md도 매 세션 종료 시 함께 갱신하도록 절차를 반영해뒀다 — 안 그러면 next-tasks.md만 금방 낡은 문서가 될 게 뻔했다.
