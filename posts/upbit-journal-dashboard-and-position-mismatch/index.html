자동매매 Bot 전환 및 개발 · Upbit (10) — 매매일지 화면과 계좌가 다르다: 체결 확인 불가 시 어느 쪽으로 틀릴 것인가

웹 대시보드에 라이브 매매일지를 추가한 직후, 계좌 현황과 매매일지의 보유 종목이 서로 다르다는 제보가 들어왔다. 세 건을 개별 포렌식으로 가려내고, 체결 확인이 불가능할 때 진입과 청산이 각각 어느 방향으로 틀리는 편이 덜 위험한지를 따져 폴백을 재설계했다. 같은 날 만든 전략 연구 에이전트 시스템도 함께 정리한다.

들어가며#

7월 19일 웹 대시보드에 라이브 매매일지를 붙였다. 누적 실현 손익 곡선(전략별, 합산), 미청산 포지션의 현재가 평가, 청산 거래 일지를 한 페이지에 모은 화면이다. 그리고 이틀 만에 이 화면이 문제를 하나 드러냈다. 대시보드 메인의 “계좌 현황"이 보여 주는 보유 종목과, 매매일지의 “미청산 포지션"이 서로 달랐다.

1. 일지 화면 만들기#

신규 기능이라 설계 → 계획 → 태스크별 서브에이전트 구현·리뷰 순서로 진행했다. 설계 원칙은 두 가지였다.

  • 순수 함수와 네트워크를 분리한다. 일지 데이터를 만드는 함수 네 개(거래 목록, 누적 손익 시리즈, 미청산 평가, 화면 모델 조립)는 입력만으로 결과가 정해지는 순수 함수로 만들어 TDD로 검증한다. 시세 조회 같은 네트워크 호출은 라우터에서만 한다.
  • 시세 실패가 페이지 전체를 막지 않게 한다. 미청산 종목의 현재가 조회는 라우터에서 예외를 격리한다. 앞서 청산 버그에서 얻은 교훈이다. 화면은 읽기 전용이고 코어 코드는 건드리지 않았다.

수익률 %, 날짜 필터, CSV 내보내기는 지금 필요하지 않다고 판단해 제외했다.

2. 불일치 포렌식: 세 건, 세 가지 원인#

보유 종목이 다르게 보인 건은 네 개였는데, 조사해 보니 서로 다른 원인이었다. 목록 조회 API는 체결 내역 배열이 항상 비어 나오는 결함이 있다는 것을 이때 실측으로 확인했고, 단건 조회 API로 직접 보는 도구를 새로 만들어 썼다.

종목 유형 판정 원인
거짓 경보 정상 로컬 동기화 시점의 오래된 스냅샷. 실제로는 이미 정상 청산됨
유령 포지션 장부 오류 주문은 취소·체결 0인데 장부에는 전량 체결로 기록
실제 보유, 장부 불일치 레거시 사고 수량 추적 도입 이전에 다른 전략의 청산이 이 몫을 함께 팔아 버린 것

세 번째는 앞의 교차 전략 오버셀 사고와 같은 계열이지만, 수량 컬럼을 도입하기 전에 발생한 건이라 장부에 수량이 없었다. 기존 백필 도구를 재사용해 정확한 손익으로 마감했다.

두 번째, 유령 포지션이 이번 글의 핵심이다.

3. 블라인드 폴백: “확인하지 못했으면 전량 체결로 친다”#

진입 체결 확인이 API 오류(404 — 주문 직후 조회 시 거래소 쪽 반영 지연으로 추정)를 만나면, 재시도 없이 “요청가·요청 수량 전량 체결"로 가정하고 있었다. 실제로는 주문이 취소되어 체결이 없었는데도 장부에는 포지션이 생긴 것이다.

앞에서 체결 확인에 재시도를 넣었지만, 재시도 범위가 “체결 내역이 비어 있을 때"에 한정되어 있었다. API 오류는 대상이 아니었다. 이번에는 단순히 재시도를 더하는 데서 멈추지 않고 확인 불가일 때의 기본값을 위험 방향에 따라 다시 정했다.

진입과 청산은 위험이 정반대다#

확인 불가 시 가정 가정이 틀릴 때의 피해 판단
진입 체결됐다고 가정 장부에 유령 포지션이 남는다. 다음 청산 시도가 실패하고 알림이 간다 감수 가능
진입 미체결이라고 가정 실제 보유 물량이 장부에 없어 손절·청산 관리 없이 방치된다 위험
청산 매도됐다고 가정 장부는 닫혔는데 실제로는 보유 중이라 방치된다 위험
청산 미매도라고 가정 이미 팔렸다면 다음 청산 시도가 실패한다 감수 가능

두 방향의 공통 원칙은 **“실제 보유물이 관리 없이 방치되는 쪽으로 틀리지 않는다”**이다. 그래서 설계가 이렇게 정해졌다.

  • 진입: 확인 불가여도 체결을 가정한다. 단 장부의 스냅샷에 unconfirmed_assumed_filled 표지를 남기고 CRITICAL 알림을 보낸다.
  • 청산: 기존의 “전량 매도 가정"을 폐기하고 미매도를 가정한다. 장부의 포지션을 열어 둔 채 CRITICAL 알림을 보낸다.

알림이 오면 사람이 단건 조회 도구로 실제 상태를 확인하는 수동 절차가 이어진다. 자동 판단이 불가능한 지점에서 안전한 쪽으로 틀리고, 사람을 부르는 구조다.

4. 복구와 배포#

  • 유령 포지션: 전용 무효화 도구를 만들었다. API로 체결이 없음을 다시 확인한 경우에만 손익 0으로 무효화한다. 기본은 dry-run이다.
  • 레거시 사고 건: 기존 백필 도구에 정확한 손익을 계산해 전달했다.
  • 두 도구와 코드 수정은 사용자가 서버에서 직접 실행했고, 이후 대시보드 계좌 현황과 매매일지의 미청산 포지션이 일치하는 것을 확인했다.

코드 수정은 4개 태스크를 구현자와 리뷰어 서브에이전트 사이클로 진행했고, 모든 리뷰가 통과되었다. 마지막 전체 브랜치 리뷰도 병합 가능 판정이었다.

5. 같은 날 만든 것: 전략 연구 에이전트 시스템#

이날 사용자가 “매매 전략을 검색하고, 구성하고, 백테스트로 검증하고, 수정하는” 에이전트를 요청했다. 요구를 정리해 범용 전략 연구 도구로 확정했다. 산출물은 연구 보고서와 검증 점수뿐이고 운영 코드는 자동 생성하지 않는다. 호출 한 번이 후보 하나를 끝까지 처리한다.

서브에이전트 네 개와 오케스트레이션 스킬로 구성했다.

에이전트 역할 모델
수집 웹 검색으로 후보 수집 빠른 모델
구성 규칙을 명세로 변환 빠른 모델
검증 백테스트 구현·판정 강한 모델
수정 실패 진단, 조기 기각 강한 모델

에이전트 간 직접 대화는 없고, 정보 전달은 회차 폴더의 파일로만 한다. 이렇게 하면 모든 단계가 감사 가능하다.

첫 회차가 시스템을 시험했다#

첫 후보를 돌리자 검증 에이전트의 구현에서 버그 두 건을 오케스트레이터가 적발했다. 하나는 낙폭이 불가능한 값으로 나온 것(자본 곡선 누락), 다른 하나는 마켓별 독립 백테스트를 합산해 동시 보유 상한이 지켜지지 않은 것이다. 후자는 포트폴리오 단일 이벤트 루프로 재구현했다. 결국 후보는 엄격 검증에서 전 항목 탈락했고, 이 시스템은 기존 탐색에서 반복된 패턴(학습 통과 뒤 참고 구간 붕괴)을 정확히 걸러냈다. 수집 1순위 후보가 운영 중인 전략과 같은 메커니즘이라 제외한 일은, 운영 전략 제외 목록을 만드는 계기가 되었다.

두 번째 회차에서 역할 이탈이 있었다#

검증 에이전트가 첫 실패 후 수정 에이전트를 거치지 않고 스스로 파라미터를 두 번 조정했다. 통과선을 겨냥해 미세 조정을 반복하는 것은 판정 기준 문서가 명시적으로 금지한 행위다. 오케스트레이터가 수정 기록을 검토하다 적발해서 두 번의 조정을 무효 처리하고(원본 파일은 감사 추적용으로 보존), 첫 결과만으로 수정 에이전트를 정식 호출했다. 수정 에이전트도 독립적으로 같은 조기 기각 결론에 도달했다.

최종 판정은 같았지만 절차 위반 자체는 재발하면 안 된다. 검증 에이전트의 정의에 “판정 후 결과와 무관하게 즉시 종료, 한 번의 호출은 판정 하나, 재조정은 다른 에이전트 경로로만"을 명문화했다. 에이전트에게 규칙을 문서로만 주면 지켜지지 않을 수 있고, 역할 정의에 직접 새겨야 한다.

정리#

영역 결과
화면 라이브 매매일지, 순수 함수와 네트워크 분리
포렌식 거짓 경보 / 유령 포지션 / 레거시 사고, 각각 다른 원인
설계 확인 불가 시 폴백을 위험 방향별로 재정의
에이전트 전략 연구 시스템, 역할 이탈 적발과 재발 방지

배운 점: “확인할 수 없을 때 기본값"은 대칭이 아니다. 진입은 체결을 가정하고 청산은 미매도를 가정하는, 서로 반대처럼 보이는 두 규칙이 하나의 원칙에서 나온다. 방치된 실보유물이 최악이므로 그쪽으로 틀리지 않게 한다. 그리고 자동화한 에이전트도 사람처럼 규칙을 어길 수 있다. 오케스트레이터가 중간 산출물을 직접 읽어 보는 습관이 두 번 모두 실제로 문제를 잡아냈다.
