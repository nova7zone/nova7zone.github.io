자동매매 코드 개발 (49) — 종목명이 비어 있던 진짜 원인, 그리고 사전 캐시 시각을 옮긴 뒤의 검증

특정 그룹의 매수 알림에서 종목명이 비던 문제는 '모의투자 서버가 빈 값을 준다'는 기존 진단이 틀려 있었다. API 응답을 직접 확인해 진짜 원인을 찾았다. 같은 주에 사전 캐시 실행 시각을 18시에서 6시로 옮긴 변경을 로그로 검증하고 문서의 낡은 서술까지 정리한 기록.

들어가며#

7월 7~8일에는 서로 다른 두 가지를 마무리했다. 하나는 일부 전략 그룹에서 종목명이 알림과 대시보드에 비어 보이던 문제, 다른 하나는 사전 캐시를 만드는 스케줄을 저녁에서 새벽으로 옮긴 변경의 검증이다. 둘 다 “기존에 내린 결론이 정말 맞았는지 다시 확인한다"는 점에서 닮아 있다.

1. 종목명이 비던 문제 — 기존 진단이 틀렸다#

제보는 간단했다. 그룹 A(거래량 기반)와 D(RSI 기반)로 매수할 때 텔레그램과 대시보드에 종목명이 나오지 않았다. 그룹 C(업종 상위)는 늘 정상이었다.

처음에는 이전에 남긴 두 가지 추정이 있었다.

  • “그룹별 함수가 이름을 채우지 않는다”
  • 7월 3일의 진단: “모의투자 서버가 이름 필드를 빈 문자열로 준다”

조사해 보니 둘 다 불완전하거나 틀려 있었다. 실제 증권사 API를 직접 호출해 응답을 열어 봤다. 현재가 조회(inquire-price) 응답에는 종목명 필드가 처음부터 없었다. 업종명과 시장명만 있을 뿐이다. “모의투자 서버가 빈 값을 준다"가 아니라 “그 엔드포인트가 애초에 이름을 주지 않는다"였다. 그래서 같은 엔드포인트를 실전 서버로 다시 호출해 이름을 보강하는 코드도 똑같이 실패하고 있었다.

반면 사전 캐시를 만들 때 쓰는 종목 목록 조회(get_stock_list)에는 이름이 들어 있었다. 이 이름은 이미 계산해 두고도 업종 캐시에만 저장하고 나머지 그룹용 캐시에는 버리고 있었다. 그룹 C와 일부 폴백 경로만 이 이름을 써서 정상이었던 이유가 설명됐다.

수정#

  • 캐시에 {코드: 이름} 사전을 추가했다. 이미 조회한 값을 재사용하므로 추가 API 호출은 없다.
  • 그룹 A·D와 B의 일부 경로가 이 사전을 먼저 보고, 캐시에 없을 때만 기존 폴백을 타도록 했다.
  • 캐시 적중 시에는 오히려 API 호출이 줄어든다(이전에는 이름 조회에 실패한 뒤 추가 호출까지 했다).
  • 테스트는 사전 채움·빈 이름 제외 회귀 2건, 각 전략의 “사전 있으면 사용, 없으면 기존 폴백” 4건을 RED 확인 후 GREEN으로 만들었다.

교훈: “서버가 빈 값을 준다” 같은 결론은 응답 원문을 직접 확인하기 전에는 가설일 뿐이다. 이번에도 API를 직접 호출한 한 번이 진단을 바꿨다.

2. 사전 캐시를 새벽 6시로 옮긴 변경 검증#

사전 캐시(--next-pre-market)는 원래 전 거래일 18시에 실행했는데, 운영 스케줄을 당일 06시로 바꿨다. 사용자가 서버 로그와 데이터 폴더를 복사해 와서 검증을 요청했다.

확인 항목 결과
06시 실행 로그 약 1분 안에 정상 종료, 그룹별 60종목·업종 40종목 모두 생성
이전 18시 실행과의 품질 동등, 저하 없음
오전 매수 사이클 캐시 기반으로 1차 선정 정상 산출, “캐시 없음/만료” 경고 없음

왜 결과가 같은지는 논리로도 설명된다. 새벽 6시에는 아직 당일 봉이 없으므로 일봉 조회는 항상 직전 완결 영업일 종가를 돌려준다. 이는 18시(장 마감 직후)에 실행했을 때 캐싱되는 데이터와 같다. 오히려 주말·연휴 사이의 캐시 공백이 최대 약 63시간에서 약 3시간으로 줄어 캐시 만료 위험은 낮아졌다.

문서의 낡은 서술 정리#

코드는 바꾸지 않았지만 문서가 문제였다. 스케줄이 바뀐 뒤에도 설치 안내, 개발 명세, 캐시 설정 파일의 주석, 전략 흐름도 문서가 “18시, 장 마감 후” 기준으로 서술되어 있었다. 이를 “06시, 장 시작 전, 7월 7일부터(이전에는 전날 18시)“로 정정했다. 정리 중에 원래 목록에 없던 흐름도 문서에서도 같은 낡은 서술을 찾았고, 설정 예시의 값이 실제 파일과 어긋난 것도 발견해 함께 고쳤다. 로직은 건드리지 않았기 때문에 캐시 관리 테스트 28건으로 회귀만 확인했다.

정리#

항목 내용
종목명 미표시 원인 현재가 조회 응답에 이름 필드가 없음 + 이미 조회한 이름을 일부 캐시에만 저장
해결 캐시에 이름 사전 추가, 추가 API 호출 없음
스케줄 변경 로그로 동등성 검증, 주말 공백 63시간에서 3시간으로 단축
문서 낡은 시각 서술을 코드·설정·흐름도 전반에서 정정

배운 점: 스케줄이나 구조를 바꾸면 코드보다 문서가 먼저 낡는다. 변경 직후 “그 변경이 언급된 모든 곳"을 한 번 훑는 과정을 작업 절차에 넣어 두는 편이 낫다.
