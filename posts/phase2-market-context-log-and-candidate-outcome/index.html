자동매매 코드 개발 (46) — Phase 2 데이터 수집 2부: market_context_log, candidate_outcome

매수 사이클마다 시장 상황 전체를 스냅샷으로 남기는 market_context_log와, 매수되지 않은 후보까지 포함한 스크리닝 전체 결과의 사후 수익률을 추적하는 candidate_outcome 테이블을 신설했다. SQLite UNIQUE 제약의 NULL 처리 방식이 만든 재실행 중복 버그도 함께 정리한다.

들어가며#

이전 글에서 sell_evaluation_log와 orders 테이블을 신설했다. Phase 2 데이터 수집 계층의 나머지 두 테이블은 각각 “그때 시장이 어떤 상태였는가"와 “사지 않은 종목은 어떻게 됐는가"를 남기는 작업이다.

결론부터 말하면, 매수 사이클 시작 시점의 시장 컨텍스트(VKOSPI, 공포 국면, 포지션 배율 등)를 기록하는 market_context_log를 만들었다. 이어서 매수되지 않은 후보를 포함한 스크리닝 전체 결과의 사후 성과(D+1/D+5 수익률)를 추적하는 candidate_outcome을 구현했는데, 이 과정에서 SQLite UNIQUE 제약의 NULL 처리 방식이 만든 재실행 중복 버그도 발견해 고쳤다.

market_context_log — 매수 사이클 시장 스냅샷 (T2-3)#

매 매수 사이클(run_buy()) 시작 시점의 시장 컨텍스트(VKOSPI, 공포 국면, 시장 국면, 시장 위치 필터 레벨/KOSPI가, 최종 합산 포지션 배율/최소점수 보정치)를 1행씩 기록한다. hard_block(공포 필터 매수 차단) 체크보다 반드시 앞에서 기록해서, 이상 사이클(하드블록 포함)도 빠짐없이 남기기로 했다.

market_filter.classify_market_position()이 이미 계산하고 버리던 KOSPI 현재가를 반환값에 추가로 재사용했다(API 호출 추가 없음, 폴백 경로는 None 유지). position_scale/min_score_delta는 실제 스크리닝에 쓰이는 “합산된” 값(combine_position_scale/combine_min_score_delta)을 run_buy()에서 한 번 더 순수 호출해서 기록한다.

Task 1 (commit 02dca55): db/schema.py에 market_context_log 테이블 DDL 추가(11개 컬럼 + 인덱스).

Task 2 (commit 2bbba8e): db/repository.py에 insert_market_context_log()/get_market_context_logs() 추가, TABLE_LABELS 등록.

Task 3 (commit 215b2f6): strategy_v2/screening/market_filter.py::classify_market_position()의 _level_result()에 kospi_price 반환값 추가 — 정상 판정 경로는 실측값, 폴백 경로(비활성화/조회실패/파싱실패/이상값/데이터부족)는 전부 기본값 None을 유지했다(폴백 자체가 이상 신호이므로 억지로 채우지 않는다).

Task 4 (commit d6b7331): strategy_v2/trading/buy.py::run_buy()의 hard_block 체크 직전에 combine_min_score_delta/combine_position_scale 계산 + market_context_log 기록을 연결했다. 구현 subagent의 마지막 턴이 보고서 작성 전에 잘렸는데(이전 T2-2 세션이 같은 스크래치 파일명을 남겨둔 상태였던 것으로 추정), 컨트롤러가 uncommitted diff를 직접 검증(브리프와 정확히 일치 확인)하고 테스트를 재실행한 뒤 보고서를 작성·커밋했다.

Task 5 (commit 3bdd2dc): strategy_v3/trading/buy.py::run_buy()에도 동일 배선(v3 전용 first_stage_groups.combine_* 함수 사용)을 추가했다.

pytest tests/ 991개 → 1002개(Task 5 종료 시점) 전체 통과했다. 최종 리뷰에서 Minor 4건이 나왔는데 전부 non-blocking이었다 — min_score_delta 컬럼명이 실제로는 “합산된 최종 임계치"를 저장한다는 네이밍 이슈, relax 루프의 추가 완화가 기록되지 않는다는 설계상 이미 알려진 한계, 기간 필터 표현이 다소 과장됐던 문서 표현, min_position_scale=0.1 리터럴이 4곳에 중복돼 있다는 점(private 상수 import 회피를 위한 의도적 선택)이었다.

candidate_outcome — 스크리닝 전체의 사후 성과 추적 (T2-4)#

next-tasks.md 표현으로 “가장 복잡한 항목"이었다. T2-1(sell_evaluation_log)·T2-2(orders)·T2-3(market_context_log)이 실제 매수/매도된 종목의 판단 과정을 남긴다면, T2-4는 매수되지 않은 후보를 포함한 스크리닝 전체 결과의 사후 성과(D+1/D+5 수익률)를 남겨 스크리닝 품질 자체를 검증 가능하게 한다.

핵심 설계 결정: v2(하루 1개 파일, pool_hour=NULL) + v3(시간대별 스냅샷, pool_hour=9~14) 후보 풀 모두 대상으로 한다. ret_d1/ret_d5는 price_at_selection 대비 D+1/D+5 종가 수익률로 정의했다. was_bought는 orders 테이블(T2-2) 기준으로 판정한다. D+1/D+5 backfill은 별도 영업일 계산 유틸을 만들지 않고, get_daily_candles_until()이 반환하는 실제 거래일만 담긴 캔들 리스트의 인덱스 오프셋(i-1/i-5)으로 처리했다 — 공휴일 캘린더가 전혀 불필요해진다. 기존 07:00 --pre-market cron에 통합해서 crontab 변경도 불필요했다.

Task 1 (commit 2de8fd4): db/schema.py에 candidate_outcome 테이블 DDL 추가(12개 컬럼 + 인덱스 + UNIQUE(pool_date, pool_hour, code)).

Task 2 (commit a4ba5cb): db/repository.py에 insert_candidate_outcome()(bool 반환)/get_pending_candidate_outcomes()/update_candidate_outcome_returns()/get_candidate_outcomes() 추가.

Task 3 (commit e4212be): strategy_v3/screening/first_stage_groups.py에 load_candidate_pool_snapshot() 공개 헬퍼를 추가했다.

Task 4 중 발견한 SQLite UNIQUE 제약 버그#

Task 4 구현 중 작성한 재실행(rerun) 테스트가 실제 버그를 잡아냈다. SQLite의 UNIQUE 제약은 NULL 값끼리 서로 다르다고 취급한다(NULL != NULL). pool_hour가 항상 NULL인 v2 후보는 같은 (pool_date, code)로 재실행해도 INSERT OR IGNORE가 중복을 걸러내지 못하는 문제였다.

수정 (commit cf99f4a): 테이블 제약을 COALESCE(pool_hour, -1) 표현식 유니크 인덱스로 교체했다(v3처럼 pool_hour가 non-null인 경우는 영향 없음). 회귀 테스트 2건(raw SQL 레벨 + insert_candidate_outcome() 레벨)을 추가했다.

Task 4 (commit f972884): utils/candidate_outcome.py를 신설하고 ingest_candidate_pools()를 구현했다 — 전일 v2/v3 후보 풀을 읽어 was_bought(orders 테이블 기준, 코드별 캐싱)와 함께 candidate_outcome에 삽입한다. 소스별 개별 try/except로 격리해서 v2 파일 없음/v3 특정 시간대 파일 없음이 서로 영향을 주지 않도록 했다. 구현 subagent가 세션 한도로 마지막 검증/커밋 직전에 중단돼서, 컨트롤러가 uncommitted diff를 직접 검증하고 버그 수정을 포함해 최종 커밋을 진행했다.

Task 5 (commit 4f0ebcd): backfill_returns()를 구현했다 — ret_d1/ret_d5가 NULL인 행을 코드별로 dedupe해 get_daily_candles_until()을 1회씩만 호출하고, 반환된 캔들 리스트에서 pool_date의 인덱스를 찾아 i-1/i-5로 D+1/D+5 종가를 조회한다. 아직 거래일이 안 지났거나 캔들에 pool_date가 없으면(거래정지 등) NULL을 유지해 다음 실행에서 자동 재시도한다. 종목 1개 API 실패가 나머지를 막지 않는다.

Task 6 (commit e592611): runner.py의 기존 --pre-market(07:00 cron) 분기에 ingest_candidate_pools()/backfill_returns() 호출을 daily_reeval과 별도의 독립적인 try/except로 추가했다.

최종 리뷰에서 Minor 5건이 나왔는데 전부 non-blocking이었다. --pre-market 실행 자체가 통째로 누락되면(서버 다운 등) 그날 후보 풀은 영구히 수집 못 한다는 것(설계 단계에 이미 정한 사양), previous_business_day()가 한국 공휴일 캘린더는 없다는 것, backfill의 count=30 캔들 윈도우가 이론상 6주 이상 지연되면 오래된 행을 영구히 놓칠 수 있다는 것, _pct()가 stck_clpr 누락 시 0으로 폴백해 가짜 -100% 수익률을 만들 수 있다는 것(기존 패턴과 동일, 새 결함 아님), get_orders(limit=500) 매직 넘버였다.

pytest tests/ 1002개(Task 1 시작 전) → 1029개(Task 6 종료 시점) 전체 통과했다. 배포 후 확인이 필요한 항목은 매 거래일 07:00 --pre-market에서 후보 풀이 정상 삽입되는지, 며칠 누적 후 ret_d1/ret_d5가 실제로 채워지는지(D+5는 6영업일 후 첫 backfill에서 확인 가능), was_bought=1 행이 실제 매수 체결 종목과 일치하는지였다.
