자동매매 V2 개발 · Upbit (12) — 점검 스킬도 낡는다: 정합성 리뷰와 읽기 전용 정기 점검 스크립트

에이전트가 따르는 스킬과 지침 문서가 코드·설정·다른 문서와 어긋나기 시작했다. 스킬을 실물과 대조하는 정합성 리뷰로 지적 약 25건을 찾고, 정의가 네 곳에서 다른 판정 기준을 정본 하나로 맞췄다. 점검에 쓰는 AI 사용량을 줄이려고 읽기 전용 점검 스크립트를 만든 과정과, 외부 AI의 개선 제안서를 실물과 대조해 대부분 불채택한 판단을 정리한다.

들어가며#

운영이 안정되면서 문제의 위치가 코드에서 에이전트가 읽는 문서로 옮겨 갔다. 점검 스킬, 연구 에이전트 지침, 세션 시작·종료 절차 같은 문서다. 이 문서들은 코드와 달리 테스트가 없어서 설정값이 바뀌어도, 로그 이벤트 이름이 바뀌어도 조용히 낡는다. 10월 12일부터 18일까지, 그 낡음을 찾는 작업과 점검 자동화를 다룬다.

1. 스킬을 실물과 대조한다#

사용자가 정합성 리뷰를 요청했다. 대상은 세 묶음이었다.

대상 대조 기준 결과
전략 연구 스킬·에이전트 4종·판정 기준 문서 백테스트 하니스 코드 지적 10건 (사실 7, 잠복 1, 설계 판단 1, 마이너 1)
세션 시작·종료·문서 동기화 스킬 검증 스크립트, CI, 규약 문서 지적 6건
서버 점검·캐너리 점검 스킬 설정값, 로그 이벤트, 코드 지적 9건

방법은 기계적이다. 스킬이 언급하는 로그 이벤트 40여 개를 코드에서 전수 검색했고(전부 존재), 링크와 앵커의 깨짐을 확인했다(0건). 서버는 읽기 전용으로 한 번만 조회했다. 모든 리뷰의 원칙은 먼저 보고만 하고 고치지 않는다였다. 사용자가 지시한 뒤에 고쳤다.

대표적인 지적들은 이랬다.

  • 타입 검사 범위가 둘로 갈렸다. 검증 스크립트는 scripts 폴더를 포함하는데 CI와 규약 문서는 제외했다. 로컬에서는 통과하고 CI에서는 다르게 동작할 수 있다. 하나로 통일했다.
  • 서버 점검 스킬의 낡은 수치. 배치 크기, 보관 기간, 틱 예산 같은 설정값을 문서에 숫자로 박아 두었다. 설정이 바뀌면 틀린다. 설정 파일을 가리키게 바꿨다.
  • 항상 0인 grep. 요청 제한(429) 횟수를 로그에서 찾는 명령이 있었는데, 그것은 로그 이벤트가 아니라 카운터였다. 영원히 0이 나오는 점검은 안심을 주는 가짜 점검이다. 삭제했다.
  • 작업 로그 양식이 정본과 실제가 달랐다. 정본을 문서 맨 위에 두고 이전 양식은 소급 변환하지 않는다고 명시했다.
  • 변경 → 문서 매핑이 없었다. 문서 동기화 단계에 “어떤 코드 변경이 어떤 문서를 바꿔야 하는가” 표를 추가했다.

정의가 네 곳에서 달랐다#

가장 무거운 지적은 연구 판정 기준 중 하나(R2)의 정의가 네 군데에서 서로 달랐다는 점이다. 어떤 문서는 “전 구간 신뢰구간 하한이 1.0 초과"라 하고, 어떤 문서는 “전반과 후반 각각의 점추정 수익 팩터가 1.0 초과"라 했다. 실제 운용은 후자였다.

정본을 기준 문서의 해당 절 하나로 정하고 나머지 세 문서가 그 절을 가리키도록 고쳤다. 다만 여기서 중요한 단서가 있다. 문서의 한 문구가 바뀌는 것이므로 판정 기준 변경이 아니라 실제 운용 정의에 정렬하는 것임을 사용자에게 확인받아야 했다. 판정 기준을 조용히 바꾸는 일은 이 프로젝트에서 가장 피해야 할 일이다.

같은 방식으로 후속 코드 수정도 했다. 고원 탐색 함수에 선택 인자(최고점 하한, 격자 끝 최고점 배제)를 추가했다. 기본값은 기존 동작이라 기존 호출에 영향이 없고 기준 문서가 새 값으로 호출하도록 명시했다(판정 강화, 소급 재판정 없음). 또 위험 설정과 공포 게이트 설정이 라이브는 한쪽을, 백테스트는 다른 쪽을 읽는 이중 출처 문제를 일치 테스트로 막았고, 백테스트 리포트에 설정 지문 줄을 추가했다.

2. 날짜 표기 통일#

사용자가 모바일 화면 캡처를 주면서 “모든 날짜·시간 표기를 2026-10-12T19:27:26 형식으로, 시간이 필요 없는 것은 2026-10-12로” 요청했다. 마이크로초가 붙은 것, 오프셋이 붙은 것, KST 접미사, MM-DD HH:MM 형식이 화면마다 섞여 있었다.

표기 함수를 한 파일에 모으고(날짜·시간·셀 세 종류) 템플릿 11곳에 필터로 적용했다. 파이썬 쪽에서 문자열을 만드는 곳도 같은 형식으로 맞췄다. 배포 후에는 로그인된 브라우저로 화면 두 곳을 읽기 전용으로 확인해 잔존 형식 0건을 확인했다. 나머지 화면은 테스트로만 확인했다고 정직하게 적었다.

3. 점검에 쓰는 AI 사용량을 줄이는 법#

4시간마다 에이전트가 서버를 점검하는 데 비용이 들었다. 사용자는 이렇게 요청했다. 서버의 점검 스크립트 결과만 보고, 세부는 필요할 때만 확인하고, 이상이 있으면 수정 권고안을 검토하는 방향으로.

이미 서버에는 상태 점검 cron이 있었다. 하지만 틱 초과, 로그 반복, 상태 불변식, 체결 흐름 신선도는 보지 않았다. 겹치지 않도록 별도의 읽기 전용 스크립트를 만들었다.

  • 규칙 F1~F15와 INFO 요약
  • 설정 파일로 임계값 분리
  • 테스트 24건
  • 이 스크립트의 출력을 읽는 점검 스킬 + 모니터링 문서
  • 시험은 서버의 임시 디렉터리에서 실데이터로 실행했고(결과 STATUS: OK), 서버 파일은 삭제했다

배포하자마자 오탐이 나왔다. F15(로그의 마지막 줄이 92분 전)가 발동했는데 cron은 정상이었다. 상태 점검 로그가 4시간 경계에만 쌓여서 90분 임계값과 맞지 않았다. 하트비트 파일을 도입했다. 점검 스크립트가 매 실행마다 파일을 갱신하고, 새 스크립트는 하트비트를 우선, 로그를 대체로 본다.

4. 틱 초과와 반복 로그#

점검이 잡은 문제가 두 개 있었다.

  • 틱 초과. 30분에 449건. 틱당 약 4초로 3초 예산을 넘었다. 직전 구간은 0건이었다. 같은 시각부터 대기 후보가 6건 생겼다. 원인은 미확인이었고 추정은 이랬다. 리스크 체크의 거래소 호출이 최소 손익비 검사보다 앞서 있어서 대기 후보마다 매 틱 반복된다. 우선 사용자 지시로 틱 간격을 3초에서 5초로 늘렸다. 원인 추정을 확정으로 쓰지 않고 “미확인"이라고 적었다.
  • 반복 로그. 최소 손익비 미달로 대기 중인 후보 하나가 매 틱 INFO를 남겨 30분에 1,200줄이 쌓였다(저널이 거의 1GB). 앞서 만든 반복 강등이 리스크 거부 경로에만 있고 이 분기에는 없었다. 새 사유일 때만 INFO, 반복은 DEBUG로 낮추는 회귀 테스트를 수정 전 실패 확인 후 추가했다. DB에는 중복 제거가 있어서 한 줄뿐이었고 노이즈는 저널에만 있었다.

5. 외부 AI의 제안서를 실물과 대조한다#

사용자가 다른 AI 도구가 쓴 “전략 연구 에이전트 개선 제안서"를 가져왔다. 같은 방식으로 저장소 실물과 대조했다. 결과는 이랬다.

  • 제안의 대부분(실현 가능성 산술, 미측정 게이트, 플라시보 매칭, 기각 원인 분류, 관찰 기반 탐색)은 이미 판정 기준 문서와 사전 등록 문서에 있었다. 불채택.
  • 제안서에 사실 오류도 있었다. 보고서 44건 중 스모크 실패가 1건뿐이라는 점, 회차 폴더가 75개라는 점이다.
  • 채택은 세 건이다. 후보 수 계약 통일(1개 이상이면 진행, 3~7개는 목표치), 수정 유형 분류 양식(구현 정정 / 가설 변경 / 변경 없이 기각), 보고서 양식에 기각 원인 코드·결정 단계·측정/미측정 게이트·재개방 조건 필드(최종 판정을 대체하지 않는 보조 표기).

판정 문턱과 봉인 구간 보호는 건드리지 않았다. 새 양식은 다음 회차부터 적용하고 기존 보고서는 소급 변환하지 않는다. 외부 제안을 받았을 때는 “좋은 제안인가"보다 “우리가 이미 하고 있는가"를 먼저 묻는다.

정리#

영역 결과
정합성 리뷰 스킬·지침 약 25건 지적, 고치기 전에 보고
판정 정의 네 곳에서 달랐던 R2를 정본 하나로, 기준 변경 아님을 확인
정기 점검 읽기 전용 스크립트(F1~F15)로 AI 사용량 감소
오탐 하트비트로 해소
외부 제안 실물 대조 후 대부분 불채택, 3건 채택

배운 점: 스킬과 지침은 코드와 같은 방식으로 낡지만 테스트가 없다. 그래서 주기적으로 실물과 대조해야 한다. 문서가 설정값을 숫자로 박아 두면 낡고, 설정 파일을 가리키면 낡지 않는다. 그리고 점검이 항상 통과하는 것은 안심이 아니라 점검이 죽었다는 신호일 수 있다. 항상 0이 나오는 grep은 지워야 한다.
