들어가며#

이전 글에서 v0.7.0을 릴리즈하며 v3를 메인 전략으로 전환했다. 7월 3일은 v3가 실제로 돌아가기 시작한 지 이틀째 되는 날로, 운영 로그 검증과 외부에서 준비된 작업 지시서 기반의 긴급 수정이 함께 진행됐다.

결론부터 말하면, KIS Open API가 애초에 제공하지 않는 V-KOSPI200 지수를 잘못된 코드로 조회하고 있어서 fear_filter가 매 사이클 극단적 공포로 오판하던 버그를 찾아 고쳤다. 이어서 리스크 버그 5건을 추가로 수정했다. 같은 날 v0.7.0 배포 후 이틀치 v3 운영 로그를 분석해, 종목명 대량 누락·재선정 날짜 미전달·v2가 v3 포지션까지 매도하는 Critical 버그 3건도 발견해 고쳤다.

v3 운영 로그 검증: Critical 버그 3건#

먼저 v0.7.0 배포 후 OCI(모의투자)에서 v3가 처음 운영된 이틀치(07-02~07-03) logs/, data/, data/cache를 사용자가 복사해 전달해서 V3_HANDOFF.md §9 절차대로 분석했다.

검증 완료 항목: position_registry에 managed_by='v3', entry_profile(fear_driven/momentum/trend_following), entry_group_scores(G1G5 정상값) 6건이 전부 정상 기록됐다 — 7월 1일 buy.py Critical 버그(2b189e1) 수정이 실거래에서 해소됐음을 최초로 직접 확인했다. 매시간 재선정 0914시도 정상 실행됐고, 1차 퍼널 로그도 정상(그룹 A~D 전부 매 사이클 1건 이상 1차선정, 과거 “그룹 D 항상 0건” 문제 재발 없음)이었다.

Critical 버그 3건 발견·수정 (전부 TDD, pytest tests/ 897/897 통과):

  1. 종목명 대량 누락 — 모의투자(VTS) get_price_info()가 호출 성공(rt_cd=0)해도 hts_kor_isnm을 빈 문자열로 반환하는 경우가 잦았다. 같은 재선정 사이클에서 캐시 기반 그룹 C는 이름이 채워지고 실시간 조회 기반 그룹 A/B/D만 비어 있는 패턴으로 근본 원인을 특정했는데, 실제 매수 체결 종목의 holdings.json name까지 빈 값으로 저장되고 있었다. 이전에 고친 버그(bd10663)는 코드는 맞았지만 API가 애초에 이름을 안 주는 케이스를 못 막았던 것이었다 — get_stock_sector()와 동일 패턴으로 get_stock_name()(항상 live 앱키 조회)을 신규 추가해 _current_price_and_name()에 fallback을 적용했다(v2/v3 공통, 동일 버그 패턴이라 양쪽 다 수정).
  2. 매시간 재선정 date_str 미전달 — strategy_v3/trading/buy.py의 mark_candidates_selected(now.hour) 등 재선정 관련 호출이 date_str을 넘기지 않아 first_stage_groups.py가 자체적으로 “오늘"을 재계산하는 구조였다. now_kst()를 모킹해도 두 모듈의 “오늘"이 어긋날 수 있어 기존 테스트 2건이 실패 중이었다(제3자 검증 중 재발견 — pytest 훅이 이 실패를 잡아냈다). now에서 date_str을 한 번만 계산해 관련 호출 전체에 명시적으로 전달하도록 수정했다.
  3. v2 병행 매도가 v3 포지션까지 매도 — runner.py::_has_legacy_v2_holdings()가 True(v2 잔존 포지션 존재)일 때 strategy_v2/trading/sell.py::run_sell()이 managed_by 구분 없이 holdings.json 전체를 순회하고 있었다 — v3로 갓 매수한 포지션까지 v2의 구식(그룹 정규화 없는) 스코어링으로 매도해버린 것이다. 특정 종목이 09:15 v3 매수 후 10:15 v2 target_reached로 오매도된 실제 사례로 확인됐다. managed_by='v3' 종목은 v2 매도 평가에서 스킵하도록 수정했다.

미해결로 남긴 확인 항목도 있다 — strategy_sell.yaml hold_days/score_exit_ratio/MFE 트레일링 반영은 운영 2일차라 아직 트리거 조건 미도달(지금까지 매도는 전부 stop_loss)이었고, API 예산 잔여는 애초에 로그로 안 남기고 있어 계측 코드 추가가 선행되어야 했다.

커밋: 706f719. release-notes-draft-v0.7.0.md의 “다음 단계” 체크리스트도 함께 갱신했다(9개 중 6개 [x]).

VKOSPI 오조회 긴급 수정(Phase 0)#

사용자가 외부에서 준비한 작업 지시서 3종(docs/development/20260703_review/: work-order, code-review, strategy-return-analysis) 기반 다단계 작업(Phase 04)에 착수했다. 오늘은 Phase 0(T0-1)과 Phase 1(T1-1T1-5)만 완료하고 Phase 2부터는 다음 세션으로 넘겼다.

T0-1 (commit 29a4629): KIS Open API는 V-KOSPI200을 제공하지 않는다. 그런데 잘못된 지수 코드(VKOSPI_INDEX_CODE="2030")로 조회하고 있어서 464~586의 엉뚱한 값을 반환했고, fear_filter가 매 사이클 extreme_fear로 오판해 포지션 사이징·프로파일·청산 로직을 상시 왜곡시키고 있었다.

수정: api/krx_api.py를 신규 작성(KRX Open API로 실제 V-KOSPI200 EOD 종가 조회, 공휴일 영업일 재시도) + market_data_helpers.py(KRX 1순위 + KOSPI 일봉 기반 realized volatility 폴백, sanity guard, 이상값 텔레그램 1일 1회 경고, 일별 파일 캐싱) + fear_filter.classify()(vkospi=None → “unknown” 레벨 신설). /code-review(8각도 finder + 검증)로 diff를 재검토해 확인된 이슈 9건을 추가 수정했다(공휴일 데이터소스 혼합, sanity guard의 정상 0.0 오탐, candle count 비대칭, 캐싱 부재로 인한 중복 외부 호출 등).

리스크 버그 5건 수정(Phase 1)#

  • T1-1(H-1, commit 7c0ff14): 매도 registry close 시점을 주문 접수에서 체결 확인으로 이동. 미체결 취소 시 registry만 ‘sold’로 남아 다음 사이클 손절 재평가가 스킵되던 orphan 포지션 버그를 수정했다. _on_sell_filled의 v1용 close_position_registry(이미 닫힌 행이라 no-op) 대신 close_position_registry_v2로 통일하고, 전량 체결 시에만 close(부분체결 시 미close 버그도 함께 수정)하도록 했다.
  • T1-2(H-2, commit 142a27f): 주문·취소 API POST 재시도 금지. _request/_request_full에 retryable 파라미터를 추가해 타임아웃이 중복 주문으로 이어질 위험을 차단했다(401 토큰 재발급 재시도는 그대로 유지).
  • T1-3(H-3, commit 1ffcccf): 서버 타임존 의존 코드 제거. v3 buy.py 목표가 valid_until 판정, token_manager.py 차단 플래그 날짜를 now_kst()/today_kst()로 통일했다.
  • T1-4(M-3, commit 58ba391): 체결가를 주문가 대신 실측값으로 기록. get_holding_avg_price()(매수, pchs_avg_pric)·_approx_sell_fill_price()(매도, 현재가 근사)를 신규 추가했다(orders 테이블 연계는 Phase 2로 이월).
  • T1-5(M-1/M-4, commit ab9d24d): 보유 한도가 pending 매수를 못 세던 버그를 수정(get_pending_buy_count())하고, KIS API 콜 스로틀을 추가했다(min_call_interval_seconds, 기본 0.3초, VTS 초당 2건 제한 대응).

pytest tests/ 913개(Phase 0 시작 전) → 946개(Phase 1 종료 시점) 전체 통과했다. Phase마다 개별 커밋으로 나눴다.

정리#

항목 내용
VKOSPI 버그 존재하지 않는 지수를 잘못된 코드로 조회 → fear_filter 상시 오판
Phase 0 수정 KRX Open API로 실제 지수 조회 + realized volatility 폴백
Phase 1 리스크 버그 5건 orphan 포지션, 주문 재시도, 타임존, 체결가, pending 카운트/스로틀
v3 운영 검증 Critical 3건 종목명 누락, 재선정 날짜 미전달, v2가 v3 포지션 오매도
실제 사고 특정 종목 v3 매수 후 v2에 의해 오매도

가장 근본적인 지수 오조회 버그가 시리즈 내내 fear_filter의 판단을 왜곡시키고 있었다는 것과, v3 전환 직후 v2/v3 병행 운영 중 서로 다른 전략이 같은 포지션을 건드리는 경계 문제가 실거래로 드러났다는 것, 두 가지가 이 날의 핵심이었다. Phase 2(데이터 수집 계층 — 신규 테이블 4개 + holdings_snapshot 연결)는 다음 세션으로 이월됐다. 다음 글에서는 7월 4일, 매도 판단 근거를 데이터베이스에 남기는 sell_evaluation_log와 주문 이벤트를 append-only로 기록하는 orders 테이블을 신설하는 과정을 다룬다.
