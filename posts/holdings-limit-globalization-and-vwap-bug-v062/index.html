AI를 이용한 자동매매 프로그램 작성 (35) — 보유한도·가격범위 전역화, VWAP 손실매도 버그, v0.6.2 릴리즈

보유종목 한도와 매매 가격범위를 메인 설정 탭으로 전역화하면서 최종 리뷰가 잡아낸 config_loader 화이트리스트 누락 버그, 그리고 실거래 손실 매도 사고(금호건설)로 발견한 VWAP 목표가 버그를 수정하고 PR #70을 머지해 v0.6.2를 릴리즈한 과정을 정리한다.

들어가며#

이전 글에서 매도 체결인식 실패 버그를 고치고 v0.6.1을 릴리즈했다. 6월 25일은 설정 화면 구조를 정리하는 작업으로 시작해서, 실거래 손실 매도 사고를 조사하는 것으로 이어졌다.

결론부터 말하면, 보유종목 한도와 매매 가격범위를 v1 매매설정 탭에서 메인 설정 탭으로 통합했는데 최종 리뷰에서 이 필터를 항상 무력화시키는 config_loader 화이트리스트 누락을 발견했다. 이어서 사용자가 보고한 실거래 손실 매도(금호건설, -0.96%)를 추적해 VWAP 목표가 로직의 비대칭 버그를 찾아 고쳤다. 두 작업 모두 PR #70으로 머지하고 v0.6.2를 릴리즈했다.

보유종목 한도·가격범위 전역화#

기존에는 매매 가격범위(1주당 최소/최대 가격) 필터가 v1 전략에만 있었고, 웹 설정 화면에서도 v1 매매설정 탭에만 입력칸이 있었다. brainstorming으로 통합 방향을 정했다 — v1 매매설정 탭의 기존 가격범위 입력을 없애고, 메인설정 탭으로 단일화하는 것.

설계 후 subagent-driven-development로 3-Task 구현을 진행했다.

  1. v2 스크리닝에 1주당 가격범위 필터 추가
  2. 보유종목수 최대값/매매 가격범위 전역 API 4종 추가, 기존 v1 전용 가격 필드 제거
  3. 메인 설정 탭에 보유종목 한도/매매 가격범위 카드 추가, 매매 설정 탭 기존 v1 가격 입력 제거

Task별 리뷰는 모두 Approved였다.

최종 리뷰에서 발견된 Critical: 화이트리스트 누락#

전체 브랜치를 한 번에 보는 최종 리뷰에서 Critical 1건이 나왔다. utils/config_loader.py의 _load_screening_configs_v2()가 first_stage_groups.yaml의 키를 런타임 config로 전달할 때 쓰는 화이트리스트에 min_price/max_price가 빠져 있어서, 방금 만든 v2 가격범위 필터가 항상 비활성 상태(하드코딩 기본값만 사용)였다.

3개 Task 모두 이 파일을 건드리지 않았기 때문에 개별 리뷰에서는 보이지 않던 cross-task 결함이었다. 화이트리스트에 두 키를 추가하고, 로더 함수를 직접 거치는 회귀 테스트를 추가해 수정했다. 재리뷰는 Approved였다.

작업 중 부수적인 사고도 있었다 — 수정 커밋 1차 시도가 git add 범위를 잘못 잡아 무관한 파일 약 20개(KIS 토큰 캐시 등 민감 데이터, 별도 진행 중이던 backtest.html WIP, 플랜 문서)를 같이 커밋해버렸다. 즉시 발견해 git reset --soft + 선택적 재스테이징으로 정정하고, 재리뷰로 최종 커밋 범위가 의도한 2개 파일뿐임을 확인했다.

VWAP 목표가 손실 매도 버그#

사용자가 실거래 사고를 보고했다. 특정 종목을 매수한 직후 “목표가 도달"로 판단돼 매도되면서 오히려 소폭 손실이 났다는 것이다. systematic-debugging으로 추적했다.

원인은 cond_vwap.calculate()가 종목 자신의 20일 VWAP 대비 위치만 보는 지표라서, 매수가와 무관하게 발동할 수 있었던 것이었다. 같은 파일의 vkospi_exit/trailing_stop은 이미 profit_pct > 0 가드가 있었는데, reversal/fear_driven 두 전략의 target_reached 분기에는 이 가드가 빠져 있었다 — 즉 다른 매도 조건에는 이미 적용된 안전장치가 이 조건에만 비대칭적으로 누락돼 있던 것이다.

TDD로 수정했다. 손실 시 미발동 + 수익 시 정상발동(대조군) 테스트 4건을 먼저 추가해 Red를 확인한 뒤, _check_reversal_exit()에 registry_entry 파라미터를 추가하고 두 함수(reversal/fear_driven)의 target_reached 분기에 profit_pct > 0 가드를 추가해 Green으로 전환했다.

사용자 요청으로 docs/STRATEGY_V2_trading_flow.md에 18:00/07:00/09:00 단계별 실제 동작과, 백테스트가 이 시간흐름을 반영하지 않는다는 점도 함께 정리했다(매도 시각 표기 오류 10:00→09:00도 같이 정정했다).

pytest tests/ 753개 전체 통과를 확인했다.

PR #70 머지 + v0.6.2 릴리즈#

두 작업을 묶어 PR #70을 생성하고 CI(pytest) 통과를 확인한 뒤 --squash로 master에 머지(332d3d3)했다. git fetch origin master && git merge origin/master로 feature/build를 동기화(0040dfe, 충돌 없음 — 별개 WIP였던 backtest.html도 그대로 보존됐다)했다.

release-notes skill 절차대로 v0.6.1 이후 머지된 PR을 조사(#69, #70 2건)했다. 직전 패턴(feat+fix 묶음을 patch로 처리)에 맞춰 v0.6.2(patch)를 사용자가 확인했다. build-docs/release-notes-draft-v0.6.2.md를 v0.6.1 draft 형식을 따라 작성하면서, #69의 보류 항목(reconcile 손실 미기록)도 “다음 단계"에 함께 포함했다.

여기서 반복 실수가 하나 있었다. v0.6.1 work-log에 “draft 파일을 그대로 --notes-file에 넘기면 본문 제목에 (draft)가 남는다"는 주의사항을 이미 기록해뒀는데도, 똑같이 release-notes-draft-v0.6.2.md를 그대로 전달해 같은 실수를 반복했다. 발행 직후 gh release view로 자체 점검하다 발견해서, 첫 줄만 # v0.6.2로 치환한 임시 사본을 gh release edit --notes-file로 재전달해 정정했다. 다음부터는 release 생성 직후 항상 gh release view로 본문 첫 줄을 직접 확인하기로 했다.
