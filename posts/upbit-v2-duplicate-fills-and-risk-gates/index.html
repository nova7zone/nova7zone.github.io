자동매매 V2 개발 · Upbit (9) — 중복 체결 조사: 내가 쓴 '체결 없음' 기록이 틀렸다

재시작 직후 같은 4시간 경계를 다시 처리해 중복 후보가 생긴 사고를 고쳤지만, 사용자의 의문 한 줄 덕분에 '중복 후보는 체결까지 가지 않았다'는 내 기록이 틀렸음이 드러났다. 거래소 체결 내역과 실제 잔고를 대조해 주문이 먼저 나가고 중복 확인이 나중이던 순서 결함을 찾고, 리스크 게이트 두 개가 같은 사유 이름으로 섞여 있던 문제와 함께 정리한다.

들어가며#

9월 28~29일에는 캐너리 전략이 늘어나면서(총 다섯 종) 지금까지 숨어 있던 문제가 연달아 나왔다. 이 글은 가장 교훈이 컸던 중복 체결 조사를 중심으로 한다. 금액과 종목은 공개하지 않는다.

1. 재시작이 이미 끝난 경계를 다시 처리했다#

서버 모니터링을 점검하는 장치가 데몬 자체의 루프 말고는 없다는 것을 확인한 사용자가 “이 세션을 /loop로 주기 재확인"을 선택했다. 첫 점검에서 이상한 패턴이 잡혔다.

한 캐너리가 4시간 경계에서 진입했다가 손절되고 2초 뒤 재진입, 2초 뒤 또 손절했다.

후보 테이블을 대조해 원인을 추적했다. 새 캐너리 배포로 인한 재시작이 이미 처리가 끝난 4시간 경계를 다시 스크리닝했고, 기존 체결분과 완전히 같은 값의 중복 후보를 만들었다. 이 후보가 동시 보유 한도 때문에 대기하다가, 원래 포지션이 손절로 자리를 비운 순간 3시간 지난 낡은 가격으로 체결되었다.

근본 원인#

틱 루프의 “마지막으로 처리한 사이클 시각"이 메모리에만 있었다. 재시작마다 빈 상태로 시작하므로 같은 4시간 구간 안에서 재시작하면 이미 처리한 경계를 다시 처리한다. 해결은 DB 영속화였다.

  • 하트비트 테이블에 마지막 사이클 시각과 마지막 일일 처리 날짜 컬럼을 추가했다(스키마 증분 변경, 삭제 없는 ALTER TABLE).
  • 재기동 시 기존 값을 보존하고(킬스위치 값과 같은 방식), 사이클과 일일 처리가 성공할 때 갱신한다.
  • 시작 직후 읽어 루프에 초기 상태로 넘긴다.

테스트 5건을 먼저 쓰고 구현했다. 린터가 가변 기본 인자 함수 호출 한 건을 잡아서 고쳤다.

그때 기록한 내용은 이랬다. “다른 마켓의 중복 후보 두 건도 같은 경쟁을 시도했으나 잔고 부족으로 매 틱 실패하다 만료로 소멸했다. 체결은 없었다.” 이 문장이 틀렸다.

2. 사용자의 의문 한 줄#

며칠 뒤 사용자가 물었다. “캐너리 외 보유 자산이 이렇게 큰데, 이게 수동 매매가 아니라 예전 중복 자동매매 때문 아닌가? 기록이 없으면 매도할 때 어떻게 되나?”

기억이 아니라 거래소 기록으로 확인했다. 서버에서 읽기 전용으로 거래소의 종료된 주문 내역을 전체 기간 조회해 실제 잔고와 대조했다. 그리고 서비스 로그의 해당 시각(16:53~17:13)을 직접 다시 읽었다.

로그 패턴 의미
order_submitted → HTTP 200 (실제 체결) 주문이 거래소에서 실제로 체결됨
직후 positions INSERT → UNIQUE constraint failed 이미 보유 중이라 장부 기록이 실패
위 순서가 8회씩 반복 중복 주문이 반복 체결됨

주문이 먼저 나가고, 이미 보유 중인지 확인하는 것은 그다음이라는 순서 결함이었다. 체결은 실제로 있었다. 앞서의 “체결 없음” 기록은 틀렸다. 심지어 같은 시각에 다른 전략이 이미 다른 전략이 보유 중인 마켓에 같은 패턴으로 체결시킨 것도 발견했다. 같은 전략 내 중복만이 아니라, 전략 간 충돌이라는 더 일반적인 결함이었다. 마켓당 열린 포지션은 하나라는 스키마 제약이 있어서 초과 체결분은 장부 밖에 남았다.

이 결과를 사용자에게 보고하고 처리 방식을 물었다. 사용자는 두 가지를 모두 선택했다. 재발 방지 코드 수정과 초과 보유분의 장부 편입이다.

3. 재발 방지: 주문 전에 확인한다#

테스트를 먼저 썼다. 다른 전략이 이미 보유한 마켓에 진입 후보가 들어오면 거부해야 한다. 실제 충돌 시나리오로 쓰자 승인되어 버리는 것이 재현됐다. 이후 진입 리스크 체크의 맨 앞에 “이미 보유 중인 마켓이면 거부(already_holding)” 검사를 추가했다.

기존 테스트 두 개가 의도와 다르게 통과하고 있었다. 후보 마켓이 우연히 이미 보유 중인 마켓과 같아 새 검사가 먼저 걸리게 된 것이다. 원래 검증하려던 대상(전략별·글로벌 개수 상한)에 닿도록 후보 마켓을 다르게 수정했다. 테스트가 통과한다고 같은 것을 검증하는 건 아니다.

4. 장부 보정: 사람이 값을 확인한 뒤에#

초과 보유분을 장부에 편입하는 일은 되돌리기 어렵다. 그래서 순서를 지켰다.

  1. 체결 합계(수량, 수량 가중 평균 단가, 수수료 합)를 계산해 표로 사용자에게 제시하고 확인을 받았다.
  2. 서버 DB의 포지션 세 건을 직접 갱신하되, 파이썬 스크립트가 계산한 값을 그대로 파라미터 바인딩해 수기 전사 오류를 없앴다.
  3. 한 종목은 초과분을 산 전략의 포지션 행이 그 마켓에 없었다(마켓당 하나 제약). 그래서 이미 보유한 다른 전략의 포지션에 합산 편입했다. 손익 귀속이 정확히 그 전략 몫은 아니게 되는 절충이지만, 신규 매도 주문을 내지 않는 가장 안전한 방법이었다.
  4. 세 건 모두 메타 정보에 보정 근거를 남겼다.

문서도 정정했다. 결정 문서(D-142)에 오류 정정 안내를 삽입하고 현재 상태 문서의 서술에 각주를 달았다. 틀린 기록은 지우지 않고 틀렸다고 적어 둔다.

5. 같은 날의 리스크 게이트 문제#

중복 체결 조사 직전, 정기 점검이 한 가지 이상 징후를 보고했다. 한 후보에서 entry_skipped reason=exposure_cap이 4시간 동안 763회 반복됐다. 스킬 지시에 따라 원인 조사나 수정 없이 보고만 했다.

직접 조사하니 포지션 개수 상한(여유 있음)이 아니라 총 노출 캡이 원인이었다. 두 게이트가 로그에 같은 사유 이름(exposure_cap)으로 남아 구분이 되지 않았다. 계정 총자산의 대부분이 캐너리 외 보유 자산이어서 총노출이 이미 거의 한도였다(그 자산의 정체가 위의 중복 체결이었다).

사용자의 지시는 두 가지였다. 동시 보유 상한을 늘리는 것, 그리고 매수 종목 선정 전에 계좌의 보유 종목 수를 확인해 상한에 도달했으면 선정 자체를 수행하지 않는 것. 조사 결과를 보여 주자 총노출 캡에도 같은 사전 차단을 추가하기로 했다.

  • 후보 생성 단계 앞에서 position_cap_blocked와 exposure_cap_blocked를 체크한다.
  • 총노출 계산은 캐너리가 추적하는 마켓만이 아니라 accounts()로 실제 보유한 모든 통화를 조회해 가격을 붙인다. 캐너리 외 보유가 계산에서 빠지면 총노출이 축소되어 게이트가 무력해진다.
  • 각 단계를 테스트 먼저 쓰고 실패를 확인한 뒤 구현했다.

부수적으로, 이날 앞선 구현분(캐너리 리스크 게이트 4종과 백업 보관 정책 결함 수정)의 작업 로그가 누락되어 있던 것도 발견해 소급 기록했다. 배포 사실을 확인한 뒤 할 일 문서의 “배포 대기” 표기도 정정했다.

정리#

발견 교훈
재시작이 경계를 재처리 처리 완료 시각은 메모리가 아니라 DB에
내 기록이 틀렸음 기록을 쓸 때 근거를 거래소 원본으로, 틀리면 정정 각주
주문 후 중복 확인 확인은 주문 전에
게이트 사유 이름 공유 서로 다른 게이트는 서로 다른 사유로
장부 보정 값을 표로 확인받고 바인딩으로 반영

배운 점: 가장 위험한 문서는 “문제없음"이라고 쓴 문서다. 당시 판단은 로그의 한쪽 면만 보고 한 것이었다. 사용자의 단순한 질문이 거래소 원본과 대조하는 계기가 되었고, 그것이 틀린 기록을 바로잡았다. 중요한 주장은 가능하면 자기 시스템의 기록이 아니라 외부 원본(거래소)에 대조해 확인한다.
