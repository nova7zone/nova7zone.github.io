공개 전에 무엇을 검사하나: 보안 스캐너와 게시 파이프라인, 그리고 모바일에서 CSS가 막힌 이유

개발 과정을 공개하는 블로그는 비밀값과 식별자가 글에 섞일 위험이 늘 있다. 원본 Markdown과 빌드된 HTML을 모두 훑는 스캐너, 값을 출력하지 않는 규칙, 허용 목록, 이미지 검토, 게시 점검 순서를 정리한다. 줄바꿈 변환이 무결성 해시를 깨 모바일에서 스타일이 막혔던 사고와 검색 엔진 차단도 함께 다룬다.

들어가며#

자동매매 개발 기록을 공개하는 블로그에서 가장 큰 위험은 글이 아니라 글에 섞여 들어간 값이다. 서버 주소, 토큰, 계좌 정보, 주문 번호, 설정 값은 작업 로그에 자연스럽게 나온다. 이 글은 공개 전에 돌리는 검사 장치와 그 과정에서 겪은 문제를 정리한다. 검사가 무엇을 찾았는지는 값이 아니라 종류로만 말한다.

1. 스캐너의 원칙#

스캐너(scan_public.py)는 원본(content/, static/)과 빌드 결과(public/)를 둘 다 훑는다. 빌드 결과를 보는 이유가 있다. 템플릿이나 테마가 만드는 HTML에도 값이 들어갈 수 있다.

원칙 이유
값을 출력하지 않는다 검사 결과 로그 자체가 새로운 유출 경로가 된다
파일, 줄, 종류만 출력한다 위치만 알면 고칠 수 있다
걸리면 비정상 종료 코드 자동화에서 우회되지 않게
허용 목록은 이유와 함께, 사용자 승인분만 예외가 조용히 쌓이지 않게

차단 대상은 두 가지로 나뉜다.

  • 차단 항목: 비밀값 패턴, 식별자, 네트워크 주소와 포트, 방화벽 규칙, 금융 정보(주문 번호, 종목 코드, 체결 결과, 금액). 하나라도 있으면 게시가 중단된다.
  • 단어 경고: 맥락에 따라 괜찮을 수 있는 일반 단어. 문맥을 확인한 뒤 허용 목록에 이유와 함께 올린다.

패턴 검사는 오탐과의 싸움이었다. 처음에는 빌드된 HTML의 자산 해시 파일 이름, SVG 좌표, 한글 문장 속의 숫자, 시각 표기 같은 것이 비밀값이나 주소로 잡혔다. 그렇다고 검사를 끄지 않았다. 해시 문자열은 정규식에서 제외하고, 긴 문자열 규칙은 숫자와 대소문자가 섞인 경우에만 걸리게 하고, 포트 규칙은 앞 글자 조건을 좁혔다. 남는 정당한 예외는 허용 목록에 이유를 적어 올렸다. 오탐을 줄이는 방향이지, 탐지를 약하게 만드는 방향이 아니다.

스크립트 자체에도 테스트가 있다. 스캐너가 깨져서 아무것도 못 잡는 상황이 가장 위험하기 때문이다.

2. 글을 고치는 방법도 스크립트로#

기존 글에서 민감 후보가 나오면 손으로 한 군데씩 고치지 않았다. 일반화 스크립트(sanitize_posts.py)가 처리한다.

  • 구체 값은 일반 표현으로 바꾼다(“서버”, “대시보드 도메인”).
  • 코드 블록 안의 # 주석 줄을 섹션 제목으로 오인해 지우는 버그가 있었다. 코드 펜스를 인식하는 방식으로 고쳤다.
  • 여러 번 돌려도 결과가 같도록 멱등하게 만들었다.

다운로드로 제공하던 프롬프트 파일도 같은 방식으로 일반화했다(전략 파라미터 값, 방화벽 설명 등).

3. 이미지는 사람이 본다#

스크린샷에는 주소창, 토큰, IP, 식별자, 계좌·매매 화면이 찍힌다. 자동 검사(OCR)는 보조 수단일 뿐이다. 규칙은 이렇다.

  • 이미지는 사용자가 검토한 것만 게시한다.
  • 검토한 이미지와 날짜를 기록 파일에 남긴다.
  • 미검토 이미지가 게시 대상 글에서 쓰이면 중단한다.
  • 클라우드 콘솔 스크린샷은 마스킹 스크립트로 가렸다.

4. 게시 파이프라인#

“게시해"라고 하면 정해진 순서가 돈다. 어느 단계든 실패하면 중단한다. 우회하거나 검사를 끄지 않는다.

  1. 빌드: hugo(초안 제외) 빌드, 글 수 일치, 초안 누출 없음, 깨진 링크·이미지 없음, 외부 스크립트 없음, 시리즈 번호 최신.
  2. 비속어: 원본과 HTML을 목록으로 검사(문맥 확인).
  3. 보안 마스킹: 위 스캐너, 이미지 점검, 스캐너 테스트.
  4. 범위: 공개 저장소에 올라갈 파일이 빌드 결과 확장자뿐인가, 원본 폴더(content, scripts, security 등)가 섞이지 않았는가, 비공개 저장소가 public/을 추적하지 않는가.
  5. 승인: 게시될 글 목록과 점검 결과를 보여 주고 사용자의 명시적 “게시해"를 받는다.
  6. 푸시: 공개 저장소에 커밋·푸시. 강제 푸시는 하지 않는다.
  7. 완료 확인: 원격과 로컬의 커밋 일치, Pages 빌드 상태, 사이트 응답, 배포된 CSS 무결성.

점검 스크립트는 각 단계가 독립 명령(build, profanity, scope, verify-push)으로 있고 테스트가 있다. 에이전트가 “한 번에 다 한다"가 아니라 “각 단계의 결과를 읽고 다음을 진행한다"는 구조다.

5. 사고: 모바일에서 스타일이 통째로 사라졌다#

게시 뒤 사용자가 휴대폰으로 열었더니 스타일이 전혀 적용되지 않은 페이지가 나왔다. 데스크톱에서는 정상이었다.

원인은 서브리소스 무결성(SRI)이었다. Hugo는 CSS 파일에 해시 기반의 integrity 속성을 붙인다. 그런데 윈도우에서 git이 줄바꿈을 LF에서 CRLF로 바꾸는 바람에, 공개 저장소에 올라간 CSS 파일의 바이트가 빌드된 해시와 달라졌다. 브라우저는 무결성이 맞지 않는 스타일시트를 차단한다. 로컬 개발 서버에서는 저 변환이 일어나지 않아 문제가 보이지 않았다.

수정은 세 가지다.

  1. 공개 저장소의 core.autocrlf=false로 설정한다.
  2. .gitattributes로 정적 파일을 * -text(변환 금지)로 지정한다.
  3. 검사를 추가했다. 커밋될 파일(스테이징된 blob)의 해시를 HTML의 integrity와 대조하고, 게시 후에는 실제 배포된 CSS로도 대조한다. 단, integrity 문자열이 HTML 이스케이프(+가 &#43;)되어 있어서 먼저 이스케이프를 풀고 비교해야 했다.

비슷한 사고가 하나 더 있었다. 로컬에서 개발 서버(hugo server)가 켜져 있던 채로 public/을 빌드해서, 라이브 리로드 스크립트가 결과물에 섞였다. 개발 서버를 끈 뒤 빌드하도록 규칙을 정했다. 또 TOML 설정에서 [[cascade]]를 파일 중간에 넣었더니 그 뒤의 키가 모두 그 블록 안으로 들어가 버려서, 파일 맨 끝으로 옮겼다.

6. 검색 엔진에는 나타나지 않게#

이 블로그는 기록용이지 검색 유입을 원하지 않는다. 그래서 모든 페이지에 noindex, nofollow 메타를 넣고(Hugo cascade), robots.txt에 Disallow: /를 둔다. 이것은 기본 설정이고, 해제는 사용자가 지시할 때만 한다. 이미 색인된 페이지는 재방문 전까지 남아 있을 수 있다는 한계는 안내했다. 빌드 점검과 게시 후 확인 단계에서 robots.txt와 메타가 실제로 나가는지 본다.

7. 시리즈와 번호도 스크립트로#

글이 늘면서 같은 프로젝트의 글을 시간 순서대로 묶고 번호를 붙일 필요가 생겼다. 손으로 번호를 매기면 글을 중간에 끼워 넣을 때 전부 다시 써야 한다. 그래서 front matter에는 시리즈 이름과 번호 없는 제목만 쓰고, series.py가 날짜 순으로 번호와 최종 제목을 부여한다. 빌드 점검이 --check로 번호가 최신인지 확인한다. 하나의 기능이 여러 날에 걸쳤다면 마지막 작업 일자를 글 날짜로 쓴다는 규칙도 문서에 못박았다.

정리#

영역 장치
비밀값 값을 출력하지 않는 스캐너, 원본과 HTML 모두
예외 이유와 함께 사용자 승인분만 허용 목록에
이미지 사람이 검토, 기록 파일, 미검토 시 중단
게시 7단계 점검, 실패 시 중단, 명시 승인
무결성 줄바꿈 변환 금지, 해시 대조 검사
노출 noindex와 robots.txt 기본

배운 점: 공개 전 검사의 핵심은 탐지 정확도보다 우회할 수 없는 구조다. 값을 출력하지 않고, 허용 목록은 사람이 승인하고, 단계가 실패하면 멈춘다. 그리고 가장 큰 사고는 보안이 아니라 줄바꿈 문자 하나에서 나왔다. 로컬에서만 통과하는 검증은 배포 환경의 바이트 단위 차이를 보지 못한다. 그래서 배포 뒤에도 실제 서비스되는 파일로 한 번 더 확인한다.
