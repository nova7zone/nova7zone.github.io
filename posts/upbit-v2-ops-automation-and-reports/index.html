자동매매 V2 개발 · Upbit (10) — 운영 점검을 cron으로 자동화하고, 같은 배포 버그를 또 만나다

사람이 하던 서버 점검(헬스체크, 재시작, 경계 점검, 일일 리포트)을 cron 스크립트로 옮기고 웹에 리스크 통제와 보고서 화면을 붙였다. 배포 과정에서 실행 권한 비트, 셸의 변수 확장, 임포트 경로라는 로컬 검증으로 못 잡는 버그 세 개가 다시 나왔다. 같은 날 연구 쪽에서는 판정 단위 추정식이 두 개 있다는 불일치도 찾아냈다.

들어가며#

10월 첫 주에는 개별 캐너리 전략이 일곱 종 가까이 늘었다. 그만큼 사람이 서버에서 확인해야 할 일이 늘었고, 사용자는 반복되는 점검을 자동화해 달라고 요청했다. 이 글은 운영 자동화, 웹의 리스크·보고서 화면, 그리고 같은 날 연구 쪽에서 발견한 통계 추정식 불일치를 다룬다.

1. 앞선 며칠: 미배선 목록을 코드로 대조한다#

10월 1일에 사용자가 이렇게 요청했다. “현재 프로그램에서 미배선 등 부족한 사항을 자세히 파악해서 알려 줘.” 상태 문서에는 “지금 안 되는 것"과 “알려진 위험” 표가 있는데, 이 표의 모든 행을 코드 검색으로 직접 대조했다. 문서가 낡았을 수 있기 때문이다. 진입 리스크 체크 스텁, 호가 조회 미구현, 설정 적용의 메모리 미반영, 실행 기록 테이블 미배선, 보고서 부재, 킬스위치 웹 미구현이 실제로 사실임을 확인했다.

그중 사용자가 5개를 바로 진행하라고 지시했다.

  • 실행 기록 테이블(phase_runs) 신설과 사이클·일일 처리 배선
  • 웹의 “국면”, “시스템” 화면
  • 킬스위치 웹 토글
  • 이전 버전과 API 키를 공유하는 위험의 사실 반영(미가동, 동시 가동 계획 없음 → 위험도 하향)
  • 실행 기록 테이블의 중복 행 정리

킬스위치 토글에서 버그를 하나 찾았다. 데몬이 한 번도 뜬 적 없는 상태에서는 하트비트 행이 없어 UPDATE가 0행에 적용되고 조용히 무시되었다. 시작 시점과 같은 INSERT ... ON CONFLICT DO UPDATE 패턴으로 고쳤다. 그리고 자동화된 테스트와 별개로 로컬 서버를 실제로 띄워 로그인 → 화면 조회 → 토글 → 재조회까지 실제 HTTP로 확인했다.

2. 운영 점검을 스크립트로#

사용자 요청은 구체적이었다. 헬스체크, 재시작, 경계 점검, 일일 리포트를 서버 cron으로 자동화한다. 재시작은 3회 실패 시 텔레그램으로 경고하고 중단한다. 개선 사항은 서버 로컬 로그에만 쌓아서 사람이 수동 검토한다(자동으로 고치지 않는다).

canary_monitor 스크립트, 래퍼, 설정 파일을 만들었다. 이어서 “일간 보고는 별도 스크립트가 파일을 만들고 대시보드에서 보이게, 텔레그램에는 요약만"이라는 요청으로 일일 리포트 생성기를 분리했다. 리포트는 다섯 절이다.

  1. 주요 시장(BTC, ETH)의 거시 시황
  2. 전략별 통계
  3. 일간 수익률 (이전에 입출금 오염을 고친 산식을 재사용)
  4. 점검에서 나온 발견(findings) 건수
  5. 기타

웹에는 목록 화면과 날짜별 상세 화면을 추가했다. 이 보고서 메뉴(일간·주간·월간, 게시판형)는 며칠 앞서 만든 탭 구조를 확장한 것이다.

3. 배포 버그 세 개, 로컬에서는 절대 안 보이는#

스크립트를 서버에 올리고 cron에 매시 15분으로 등록했다. 배포하자마자 세 개의 버그가 나왔다. 모두 로컬 검증을 통과한 상태였다.

# 증상 원인 수정
1 Permission denied (종료 코드 126) 스크립트가 git에 비실행 모드(644)로 커밋됨 git update-index --chmod=+x
2 unbound variable 환경 파일의 값 안에 $로 시작하는 문자열이 있고, set -u가 이를 변수 참조로 해석 -u 제거
3 ModuleNotFoundError 스크립트를 직접 호출해서 sys.path에 저장소 루트가 없음 PYTHONPATH에 저장소 루트 export

이 중 둘은 이미 한 번씩 겪은 문제다. 실행 권한 비트는 V2 첫 서버 배포에서 정확히 같은 원인으로 났고, 결정 문서(D-060)에 해법까지 남겨 두었다. $로 시작하는 값을 셸이 해석하는 문제는 V1에서 15시간 동안 크론을 멈춘 바로 그 버그다. 기록은 있었지만 새 스크립트를 쓸 때 기록을 대조하는 절차가 없었다.

수정마다 4시간 경계 앞뒤 10분을 피해서 재배포했다. 세 번째 수정 후 서버에서 스크립트를 수동 실행해 종료 코드 0과 상태 파일에 두 서비스가 정상 기록된 것을 확인했다. 첫 cron 실행(수정 전 버전)은 버그 1로 실패했고, 그 뒤부터 정상이다. 텔레그램 발송 경로는 “알릴 일"이 없어서 호출 자체가 되지 않았다(설계대로). 실제 발송은 다음 이벤트에서 확인하기로 했다.

개선 방향은 분명하다. 새 셸 스크립트를 만들 때 쓰는 체크리스트(실행 권한, set -u와 환경 파일, 임포트 경로, 환경 파일 로딩 방식)를 문서화해 앞선 사례와 대조하게 하는 것이다.

4. 같은 날, 연구 쪽의 불일치#

사용자가 연구 이력을 보고 질문했다. Phase 2까지 간 전략이 0건이라 “단계 수” 대신 같은 계열의 반복 기각으로 SSL 계열(두 회차)을 골라 분석했다. 대차대조표 항목은 이랬다. 신호 자체의 엣지가 있었고, 선택 효과와 집행 효과가 이를 깎았으며, 최종 값은 통과선 아래였다. 결론은 “진입 개선만으로는 닫히지 않는다"이고 재가동은 권하지 않는다. 아이디어 세 건은 이후 탐색 에이전트 인계용으로만 기록했다.

유니버스 티어 측정#

거래대금 상위 종목이 손실 위험이 적을 것이라는 가설을 신호 없는 배리어(진입 신호 없이 무작위 시점에 같은 청산 규칙을 적용)로 측정했다. 상위 10종은 비용 대비 위험 단위당 비용이 가장 낮았지만 순 기대값이 가장 나빴고 변동성도 낮지 않았다. “상위 종목이 손실 위험이 적다"는 가설은 기각되었다. 한계는 메모에 명시했다. 생존 편향, 학습 구간 유니버스가 작은 점, 신호가 없는 측정이라는 점이다. 이 축을 정식 변수로 쓰려면 폐지 종목 복원 가능성 확인과 사전 등록된 재측정이 선행되어야 한다.

추정식이 두 개였다#

더블 바텀 후보를 다시 검토하다가 같은 1,089건의 거래가 두 가지 추정식으로 부호가 달라지는 것을 발견했다. 평균들의 평균(구간별 평균을 먼저 구하는 방식)으로는 음수였고 t값은 -0.86이었다. 거래 단위 평균으로는 양수였고 t값은 +1.73이었다. 판정 단위를 어떻게 정하느냐에 따라 방향이 달라진다.

영향을 받는 회차는 5회차 재집계 중 1건뿐이었고, 나머지 기각은 두 추정식 모두에서 견고했다. 사용자 승인으로 규칙을 확정했다. 두 추정량을 병기하고 게이트는 더 비관적인 쪽을 따른다. 통계 문턱은 그대로이고 기존 판정도 바뀌지 않는다. 앞선 서술 한 줄(“연구 단계는 가드가 꺼져 있다”)이 두 회차에는 틀렸음도 같이 정정했다.

정리#

영역 내용
미배선 목록 문서의 표를 코드 검색으로 대조 후 5개 항목 진행
자동화 cron 점검 스크립트, 3회 실패 시 경고·중단, 개선 사항은 수동 검토
보고서 일일 리포트 생성기 분리, 웹 화면 신설
배포 버그 실행 권한, set -u와 $, 임포트 경로 (앞의 둘은 재발)
연구 티어 가설 기각, 판정 단위 추정식 병기

배운 점: 같은 버그가 재발한다는 것은 기록이 부족해서가 아니라 기록을 쓰는 시점에 기록이 보이지 않아서다. 해법을 결정 문서에 남기는 것만으로는 새 스크립트를 쓰는 손에 닿지 않는다. 체크리스트나 린터 규칙처럼 작업 흐름 안에서 자동으로 걸리는 장치가 필요하다. 그리고 같은 데이터에 추정식이 둘이면 둘 다 보여 주고 더 비관적인 쪽을 따르는 것이, 판정 단위를 정하는 가장 정직한 방법이다.
